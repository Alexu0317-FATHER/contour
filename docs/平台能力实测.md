# 平台能力实测

**这份文件只装核实过的事实，每条带日期和证据等级。**

它既不是需求（`新知界需求.md` 管"要做成什么"），也不是路线图（`roadmap/` 管"确认要做但还没做"）。它管的是**第三件事：各端和各后端到底能做到哪一步**——因为"支不支持某个后端"这个决定，只能由事实决定，不能由愿望决定。

单独成文的理由：**这个项目最容易犯的错，就是把一句没人验证过的断言当成前提往下盖楼。** 已经犯过至少三次——`@路径` 保证新鲜度、`Stop` hook 等于会话结束、分支保护能做路径级隔离。三次都是盖了一段才发现地基是假的。

## 记法

每条结论后面标证据等级和日期，**不标的不算数**：

| 标记 | 意思 |
|---|---|
| `[实测]` | 我们自己跑过，有可复现的做法。**最强，但只对那一天那个版本成立** |
| `[官方文档]` | 平台官方明写。次强，但文档有滞后，跟实际行为冲突时以实测为准 |
| `[社区]` | issue、第三方项目、社区帖子。只作线索，不作依据 |
| `[未查到]` | **搜过，没搜到相关记载。** 这**不是**"不支持"，只是"没找到证据" |
| `[未验证]` | 还没查过。**空着不写，一律写这个**——空白会被下一轮当成"验过且正常" |

### `[未查到]` 和"官方说不支持"不是一回事

这一档是补出来的，因为**缺了它，"搜不到"会自动滑进"不支持"**。2026-08-12 这一天就栽了三次：

- 说 ChatGPT 的 GitHub 集成只读 → 用户截图证明**插件**里有 `Update file`，我一直在搜"连接器"
- 说 ChatGPT 网页端大概率没有协调资格 → 用户截图里的第一方 GitHub 插件实际暴露了写工具；当时把 ChatGPT 插件、只读连接器和 GitHub MCP 混成了一个东西
- 说 `push_files` 缺条件写入 → 真相是根本不需要它，`update_ref` 的非强制更新就是条件写入

**三次都是"我找到的资料没提"被写成了"它做不到"。** 平台方几乎从不写"我们不支持 X"，所以指望靠搜索拿到否定证据，方法本身就是错的。

**否定结论只有两种来源算数**：官方明确写了"不支持"，或者我们实际跑了一次被拒绝。**除此之外一律 `[未查到]`。**

平台会变。**跟你实际看到的行为不符时，以实测为准，然后回来改这份文件。**

## 一、端能力

### 技能安装

| 端 | 怎么装 | 证据 |
|---|---|---|
| **Claude Code** | `~/.claude/skills/<name>/`（个人）或 `.claude/skills/<name>/`（项目）。也可走 plugin marketplace | `[实测 2026-08-12]` 本机已装的技能就是这个形状 |
| **Codex** | `$CODEX_HOME/skills/<name>/`，默认 `~/.codex/skills`。**格式与 Claude 完全一致**（同样的 `SKILL.md` frontmatter，同样的 `references/` `assets/` `scripts/`） | `[实测 2026-08-12]` 本机 `~/.codex/skills/` 下已有四个用户装的技能 |
| **Codex（从仓库装）** | `.system/skill-installer` 可从任意 GitHub 仓安装，**含私有仓**：`--repo <owner>/<repo> --path <技能子目录>` | `[实测 2026-08-12]` 读了它的 `SKILL.md` |
| **claude.ai** | Settings → Skills → Upload：`.md`（含 YAML frontmatter）或 `.zip` / `.skill`（须含 `SKILL.md`）。上传后有 1–2 分钟安全扫描 | `[实测 2026-08-12]` 用户截图 |
| **claude.ai（marketplace）** | Settings → Plugins → Add marketplace，**可直接从 GitHub 仓库列表选，或粘 URL** | `[实测 2026-08-12]` 用户截图 |
| **ChatGPT** | `[未验证]` ChatGPT 没有对应"技能"的概念 |
| **Zed** | 全局 `~/.agents/skills/<name>/`，项目 `<worktree>/.agents/skills/<name>/`。**同样是 `SKILL.md` + `scripts/` `references/` `assets/`** | `[官方文档 2026-08-12]` |
| **VS Code** | 读 `~/.claude/skills/`，与 Claude Code 同一份 | `[未验证]` 待用标记文件实测 |

#### `.agents/skills/` 是 Codex 与 Zed 共用的项目级路径

- **Codex**：全局 `~/.codex/skills/`，项目 **`.agents/skills/<name>/`**（本机 `migrate-to-codex` 迁移文档明写 `.claude/skills/<name>/SKILL.md` → `.agents/skills/<name>/SKILL.md`）`[实测 2026-08-12]`
- **Zed**：全局 `~/.agents/skills/`，项目 **`.agents/skills/<name>/`** `[官方文档 2026-08-12]`

**所以一个项目里放一份技能，可以同时喂三个端**：真身放 `.agents/skills/contour/`，再从 `.claude/skills/contour` 软链过去（相对路径，可被 git 跟踪）。这正是 `milky_way` 已经在跑的做法。

⚠️ 但**软链不能作为公开分发的依赖**：Windows 上 git 的 `core.symlinks` 常被自动关掉，那时 clone 出来的是一个装着路径字符串的文本文件，**技能静默加载失败**。软链只用于本地开发方便。

### 技能的覆盖范围与同步

- **claude.ai 账号级技能覆盖 chat 与 Cowork**，以及 Excel / Word / PowerPoint / Outlook 加载项。`[官方文档 2026-08-12]`
- **Claude in Chrome 是否覆盖**：`[未验证]`，官方文档未提。
- **本地 `~/.claude/skills/` 与 claude.ai 账号技能互不同步。** 技能分四个层级——企业 / 个人 / 项目 / 插件——本地那两层只在本机加载。`[官方文档 2026-08-12]`
- **plugin marketplace 是唯一能一次覆盖 claude.ai 与 Claude Code 的通道。** `[官方文档 2026-08-12]`

### 显式唤醒

- **技能默认就有 `/skill-name`**，不需要额外配置。自定义命令已并入技能：`.claude/commands/x.md` 与 `.claude/skills/x/SKILL.md` 都产生 `/x`。`[官方文档 2026-08-12]`
- **`disable-model-invocation: true`** 让某个技能**只有用户能唤起**，模型硬调会被 harness 拦截；代价是该技能的 description 不进上下文。`[官方文档 2026-08-12]`
- **`user-invocable: false`** 反过来，只有模型能调。`[官方文档 2026-08-12]`
- 这两个字段在 **Codex / claude.ai 认不认**：`[未验证]`

### 常驻加载（`routing.md` 每轮在场）

| 端 | 机制 | 证据 |
|---|---|---|
| **Claude Code** | `CLAUDE.md` 里 `@路径`，harness 确定性展开全文 | `[实测]` |
| **Codex** | **不展开 `@路径`。** 根 `AGENTS.md` 里只写 `@<探针文件>`，目标文件存随机标记，开禁用文件工具的无上下文 sub-agent → 返回 `NO_TOKEN`；对照组把标记直接写进 `AGENTS.md` → 准确返回。所以 Codex 端贴全文进受管区块 | `[实测 2026-08]` **有对照组** |
| **claude.ai / ChatGPT** | 项目文件 + 指令位一行指针。**但项目文件是确定性进上下文还是按相关性检索召回，未测**——是检索就得降级到粘全文 | `[未验证]` 见 `probe.md` P-2 |
| **Claude Desktop** | `[未验证]` 桌面应用但登 claude.ai 账号，别按"本地"想当然 |

### 全局指令文件位置

- `~/.claude/CLAUDE.md` `[实测 2026-08-12]` 本机存在
- `~/.codex/AGENTS.md` `[实测 2026-08-12]` 本机存在
- **只写全局，不写项目级**——项目里的 `CLAUDE.md` / `AGENTS.md` 可能进 git、有同事、有项目自己的约定

### 钩子预算

- Claude Code `SessionEnd`：1.5 秒共享预算（配置上限 60 秒，但无法阻塞退出）
- Codex `SessionEnd`：默认 1 秒 / 硬上限 3 秒，**且空闲 30 分钟也会触发**
- 两边 `SessionStart`：600 秒

`[实测 2026-08]` 结论：**会话结束钩子结构性地扛不动网络提交**，所以 MVP 不把同步挂在钩子上。

## 二、网页端的数据层可达性

**这一节推翻了早先的一个设计妥协。** 早先认为网页端只能一份份上传文件，所以只传 `routing.md`、数据层靠连接器按需读。实际上两边都有官方的**仓库级**连接。

### claude.ai Projects + GitHub 连接器

- 可以把一个 GitHub 仓库加成 **project knowledge**，**私有仓支持**（官方文档有专门一节讲连私有仓）
- 更新靠手动点 **"Sync now"**；官方建议定期刷新
- **auto-sync on push to `<branch>`** 的每项目开关在开发中，默认关闭

`[官方文档 2026-08-12]` · `[社区]`（auto-sync 部分）

### ChatGPT + GitHub 连接器

- OAuth 之后**索引**仓库内容（代码、README、文档），typically takes a few minutes
- 连接后会问最常用哪些仓，**预先同步以提升速度和质量**
- 尊重 GitHub 既有权限

`[官方文档 2026-08-12]`

### 由此确定的两件事

**一、延迟顾虑不成立。** 不是每轮现场调连接器拉 GitHub，是**预先索引好、提问时在平台自己的服务器检索**。

**二、但连接器解决不了常驻。** 索引是**按需召回**——问到相关内容才出来；而 `routing.md` 要的是"第一句话还没说完它就已经在了"。**两件事机制不同，连接器只解决数据层。**

### 一个必须先想清楚的代价

**把整个实例仓交给连接器索引，等于把 `dumps/` 里的倾倒原文送进两个平台的索引。** 那里面是健康、家庭、职业困境的原话。

"仓库私有"是对 GitHub 说的；连接器索引是另一回事——内容进了平台。可能的缓解是把 `dumps/` 拆到另一个仓，只把统一文件连给网页端，代价是实例仓变两个、协调流程要改。**这是隐私偏好，由用户决定，技能不替他判断。**

### claude.ai 必须按界面拆开，不能再把“网页版”当成一个端

| 界面 / 通道 | 已确认能力 | 对知界意味着什么 |
|---|---|---|
| **Claude.ai Chat / Projects 的内置 GitHub** | 官方文档只描述选择仓库文件、读取与手动同步；只取文件名和内容，不取提交历史、PR 等元数据。当前界面也没有仓库写工具。`[官方文档 2026-08-13]` | 可以读取统一资产，不能提交本端倾倒包；当前只能算消费通道 |
| **普通 Chat 的代码执行环境** | 当前账号实测：在 `/tmp/contour` 克隆后可以改文件、`git add`、本地 `git commit`；`git push` 因环境中没有 GitHub token、SSH key 或 credential helper 而失败，报 `fatal: could not read Username for 'https://github.com'`。任务结束后临时文件不会成为仓库远端状态。`[实测 2026-08-13]` | 本地 commit 发生在一次性沙箱里，不算写入锚点，不能拿来完成倾倒 |
| **左侧 Code 标签** | 这是 **Claude Code 会话入口**。用户当前看到的是本地 CC 会话的远程映射；官方也提供 `/remote-control` 让网页控制本地会话，另有单独的云端 CC 任务。`[实测 + 官方文档 2026-08-13]` | 它的文件、会话和 GitHub 能力属于背后的 Claude Code 环境，**不与 Claude.ai Chat 的原生记忆同步**。Code 能写不等于 Chat 能写，也不能替 Chat 倾倒记忆 |
| **Chat 中的自定义远程 MCP** | Claude.ai 平台允许远程 MCP 暴露读写工具；但 GitHub 官方远程 MCP 能否在当前 claude.ai Chat 账号完成 OAuth、暴露哪些工具，尚未接入验证。`[官方文档 + 未验证 2026-08-13]` | 这是可能补齐 Chat 写入能力的候选路径，不是已经成立的能力 |

证据：[Claude GitHub integration](https://support.claude.com/en/articles/10167454-use-the-github-integration) · [Claude remote MCP connectors](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp) · [Claude Code power-user tips（remote control）](https://support.claude.com/en/articles/14554000-claude-code-power-user-tips) · [Claude Code on the web](https://support.claude.com/en/articles/12618689-claude-code-on-the-web)

**当前结论只对已经看见和跑过的路径负责**：Claude.ai Chat 的内置 GitHub与临时代码环境当前不能向实例仓写入；Code 标签属于 Claude Code，不是 Chat 的替代通道；远程 MCP 仍是待接入候选。不能把这三句话压成“claude.ai 能写”或“claude.ai 不能写”。

### Chat 的写入资格取决于实际接入路径，不取决于平台理论能力

- Claude.ai 支持可执行写操作的自定义远程 MCP。`[官方文档 2026-08-13]`
- GitHub 官方 MCP server 提供 `push_files`，可以把多个文件放进同一个提交。`[官方工具文档 2026-08-13]`
- 但“平台接受远程 MCP”加“GitHub MCP 有写工具”，不能自动推出“当前账号已经连接成功并获得仓库权限”。OAuth、工具暴露和仓库权限仍需在当前接入路径上确认。

| 配置 | 能倾倒 | 能读 | 有协调资格 |
|---|---|---|---|
| Claude.ai Chat / Projects + 内置 GitHub | ❌ | ✅ | ❌ |
| Claude.ai Chat + 当前临时代码环境 | ❌（只能本地 commit） | 视克隆与项目知识而定 | ❌ |
| Claude.ai Chat + **已验证可写**的 GitHub 远程 MCP | 待验证 | 待验证 | 待验证；还要满足安全发布条件 |
| Claude Code 会话（本地、远控或云端） | 取决于该 CC 会话的 GitHub 授权 | ✅ | 按该 CC 接入路径验证；它仍算 Claude Code 端，不算 Chat 端 |
| 本地端（有文件系统和 Git 凭据） | ✅ | ✅ | 仍须验证安全发布路径 |

冷启动因此必须先识别**具体界面 + 具体接入路径**，不能只问“你是不是在用 claude.ai”。当前端只能读取时，初始化必须明确显示“该端尚未完成双向接入”，不能悄悄降级后仍宣称同步成立。

### GitHub 官方远程 MCP `[官方文档 2026-08-13]`

- 远程地址：`https://api.githubcopilot.com/mcp/`（另有 `/mcp/insiders` 试验版）
- GitHub README 列出的支持客户端包括 VS Code、Visual Studio、Copilot CLI、Claude Desktop、Claude Code CLI、Cursor、Windsurf、Zed、JetBrains、Gemini CLI。
- 支持列表没有列 ChatGPT 和 claude.ai Chat。claude.ai 接受远程 MCP URL是平台事实，但该 URL 在 claude.ai Chat 中的 OAuth 兼容性和工具清单仍是 `[未验证]`；README 已撤掉“填 URL 就能用”的确定说法。

### ⚠️ ChatGPT 里有**两个** GitHub 集成，别混

**网上几乎所有"ChatGPT 的 GitHub 只读"的文章，说的都是第一个。**

| | **连接器**（Connectors） | **插件**（Plugins） |
|---|---|---|
| 干什么 | 索引仓库供 deep research 检索 | 带技能的工作流：Review Follow-up / CI Debug / **Publish Changes** |
| 能不能写 | **只读**。官方原话 "cannot push commits, merge pull requests, close issues, or modify anything" | **能写**，见下 |

查证时按 "connector" 反复搜只会拿到第一个的结论，**按界面上的"插件 / Plugins"搜才对**。`[2026-08-12 栽过]`

### ChatGPT 第一方 GitHub 插件，Plus 就能写 `[实测 2026-08-12]`

**入口：设置 → 插件 → GitHub。不需要 Developer Mode，不需要自己填 MCP URL。**

用户在 ChatGPT **Plus** 账号下截图确认：

- 插件描述：*"Use GitHub to inspect repositories, review pull requests, address feedback, debug failing Actions checks, and prepare code changes for review through a **connector-first workflow with targeted CLI fallbacks**"*
- 附带技能：`Review Follow-up` / `CI Debug` / `GitHub` / **`Publish Changes`**
- 工具清单里有写工具，例如 **`Update file`**：*"Replace a UTF-8 text file through GitHub's **contents API**. Returns the resulting **commit SHA** and content blob…"*，另有 `Update issue` / `Update issue comment` / `Update pull request` / `Unresolve review thread`

**由此确定：**

- **ChatGPT Plus 能写仓库。** 早先引用的"写操作只滚给 Business / Enterprise / Edu"（`[社区]`）对这个第一方插件不成立，**已撤销**
- **单文件条件写入存在。** `Update file` 走 contents API，而 contents API 更新已存在的文件必须带被替换文件的 `sha`，不匹配即 409

**还没确认的（同一个界面里就能看，不用实测）：**

- `[未验证]` **有没有多文件原子提交工具**——工具列表按字母序，截图停在 U 段，需要看 `Create` / `Commit` / `Push` 开头的部分
- `[未验证]` `Update file` 的参数里是否显式暴露 `sha`
- `[未验证]` **`Publish Changes` 这个技能是什么**——名字就是"发布变更"，可能正是多文件那条路
- `[未验证]` 插件描述里的 **"targeted CLI fallbacks"** 是不是意味着某种沙箱里能直接跑 git。若是，多文件原子提交不成问题

### Developer Mode 的自定义 MCP（备用路径）`[官方文档 2026-08-12]`

Settings → Connectors → 底部 Advanced settings → 打开 Developer Mode。**Plus / Pro / Team / Enterprise / Edu 都有**；只接远程 HTTPS MCP server；支持 no-auth / API key / OAuth。

**第一方插件够用的话，不需要走这条。** 留着是因为它能挂 GitHub 官方 MCP（有 `push_files`），万一第一方插件缺多文件原子提交，这是补救路径。

### `push_files` 的参数没暴露基础版本，但官方实现使用非强制引用更新 `[官方源码 2026-08-13]`

```
create_or_update_file:  owner, repo, path, content, branch, message
                        + sha（可选，被替换文件的 blob SHA）   ← 有条件写入
push_files:             owner, repo, branch, files[], message
                                                     ↑ 没有任何 base SHA / expected-head
```

工具参数表本身没有 `base SHA` / `expected head`，但这不等于实现没有并发保护。GitHub 官方 MCP 源码中的 `push_files` 会基于当前分支提交创建新 tree 和单个 commit，并用 **non-force / `Force: false`** 更新分支 ref。分支在此期间前进时，非快进更新会被 GitHub 拒绝，而不是静默覆盖。

源码证据：[github-mcp-server `repositories.go`](https://github.com/github/github-mcp-server/blob/2198e8599bbbcb98a0d6cd7cabe9a48629acdf29/pkg/github/repositories.go) `[官方源码 2026-08-13]`

所以，`push_files` 是否具备“一次提交改多个文件”和非强制 ref 更新，不需要再让用户靠破坏性实测去发现。GH-06 仍可以作为**当前连接器版本、当前账号和最终选定适配器的回归验证**，但不再承担查明公开实现事实的任务。

## 三、锚点后端

准入是四条能力，缺一条就不能当锚点：

1. 各端**读得到**
2. 各端**写得进自己的收件区**
3. 各端**读得到最新统一版本**
4. **条件写入统一文件**——基础版本被人动过就得重来

第 4 条是最容易漏的：版本号只提供**观察**，不提供**互斥**。两个端都读到 v5、都确认"仍是 v5"、然后分别覆盖，最后写的仍会静默盖掉前一个。

### GitHub 私有仓（当前 MVP 唯一实现）

| 能力 | 状态 |
|---|---|
| ① 读得到 | `[未验证]` 待逐端跑 GH-01 |
| ② 写得进收件区 | `[未验证]` 待 GH-02 / GH-03 |
| ③ 读得到最新统一版本 | `[未验证]` 待 GH-01 |
| ④ 条件写入 | 机制由 Git / API 层提供（push 非快进被拒；contents API 的 `sha` 参数不匹配即 409）。**但 GH-06 没跑过** |
| 多文件单提交与安全发布 | GitHub 官方 MCP 的 `push_files` 已由工具文档与源码确认；ChatGPT 第一方插件是否暴露等价路径仍待查工具清单；Claude.ai Chat 尚未完成 GitHub 远程 MCP 接入。必须按具体适配器记录，不能笼统写“网页端未知” |

**已实测的边界**（`[实测 2026-08-12]`）：

- **免费账号的私有仓配不了分支保护**：`PUT /repos/.../branches/main/protection` 和 `POST /repos/.../rulesets` 都返回 403，要求升级 GitHub Pro
- **但升级也解决不了**：分支保护是**分支级**粒度，**GitHub 没有路径级 ACL**，做不到"这个协作者只能写 `dumps/inbox/<他自己>/`"
- 加上多数平台的 GitHub 连接是**仓库级授权**，给的就是全仓写权限
- 所以"来源端只写自己的收件区"**在 GitHub 上永远是协议约束，不是技术隔离**。真正的技术隔离只有服务端校验一条路（GitHub App / Action），MVP 不做
- **别为这个升 Pro，升了也没用**

> **MVP 只支持 GitHub。这一节存的是线索，不是结论**，真要评估时从头查一遍，别拿下面这些当依据。

**Google Drive**

- `[未查到]` `files.update` 支不支持 `If-Match`。已知文件级 `etag` 在 v3 仍然存在（需要用 `fields` 显式请求），list 级的被移除了。**没查到不等于不支持**
- `[未验证]` 各端的 Drive 连接器能不能写、能不能一次改多个文件

**Notion**

- `[未查到]` 官方 API 文档里没见到 `If-Match` / ETag / 版本号一类的条件写入。**但这只是没找到**——Notion 几乎不会主动写"我们不支持乐观并发"，靠搜索拿否定证据方法本身就不可靠
- `[未验证]` 多块更新有没有事务语义
- `[未验证]` 各端的 Notion 连接器暴露的是完整 API 还是子集

不管结论如何，**Notion 作为 `sources.md` 里的权威来源指针不受影响**——那是另一回事，不需要条件写入。

## 四、本地 clone 的并发

**多个本地端共用一份 clone 是可以的，不需要每端一个。** 前提是不同时跑同步——`git` 的 `index.lock` 只在并发写时冲突。

（早先说过"共用 clone 会让游标说谎"，**那条是错的，已撤销**：游标记的是"这一端的记忆最后刷新到哪一版"，clone 的 HEAD 记的是"本地文件在哪一版"，两个轴不一样是正常的。）

真撞上了的处理，按成本排序 `[社区 2026-08-12]`：

| 方案 | 怎么回事 | 用不用 |
|---|---|---|
| **重试 + 指数退避** | 锁是瞬时的，重试 3–5 次（200 / 400 / 800ms）几乎总能成 | ✅ **就用这个** |
| **git worktree** | 每个工作目录有自己的 index，共享 object store | ❌ **同一分支不能在两个 worktree 里同时 checkout**，而各端都要读默认分支 |
| **文件锁包装脚本** | 串行化 git 写操作 | 过度设计 |
| **每端独立 clone** | 各有各的锁空间 | 可选，非必需 |

反面证据：`anthropics/claude-code` issue #55724 记录了**在 worktree 隔离下并行 agent 仍然丢工作**（git lock contention）。worktree 不是银弹。

**重试解决不了的一种**：同步中途崩溃留下**孤儿 `index.lock`**，锁不会自己消失。正确做法是**检测到锁但没有活着的 git 进程时报告给用户，不要自动删除**——自动删有可能杀掉一个真在跑的操作。
