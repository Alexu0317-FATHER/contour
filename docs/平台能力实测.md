# 平台能力实测

**这份文件只装核实过的事实，每条带日期和证据等级。**

它既不是需求（`新知界需求.md` 管"要做成什么"），也不是路线图（`roadmap/` 管"确认要做但还没做"）。它管的是**第三件事：各端和各后端到底能做到哪一步**——因为"支不支持某个后端"这个决定，只能由事实决定，不能由愿望决定。

单独成文的理由：**这个项目最容易犯的错，就是把一句没人验证过的断言当成前提往下盖楼。** 已经犯过至少三次——`@路径` 保证新鲜度、`Stop` hook 等于会话结束、分支保护能做路径级隔离。三次都是盖了一段才发现地基是假的。

## 记法

每条结论后面标证据等级和日期，**不标的不算数**：

| 标记 | 意思 |
|---|---|
| `[实测]` | 我们自己在目标账号 / 本机跑过，有可复现的做法。**最强，但只对那一天那个版本成立** |
| `[官方文档]` | 平台官方明写。次强，但文档有滞后，跟实际行为冲突时以实测为准 |
| `[用户观察]` | 用户在真实界面上看见并报告，有截图或现场操作。**比推断强、比实测弱**——复现范围有限，也没走完整流程 |
| `[社区]` | issue、第三方项目、社区帖子。只作线索，不作依据 |
| `[推断]` | 由已知事实推导。**必须把推导链写出来**，否则下一轮会被当成事实引用 |
| `[未查到]` | **搜过，没搜到相关记载。** 这**不是**"不支持"，只是"没找到证据" |
| `[未验证]` | 还没查过。**空着不写，一律写这个**——空白会被下一轮当成"验过且正常" |

**这七类不能互相顶替。** 最常见的三种滑动是：把 `[用户观察]` 写成 `[实测]`（看见界面 ≠ 跑通流程）、把 `[推断]` 写成 `[官方文档]`（推出来的 ≠ 人家写的）、把 `[未查到]` 写成"不支持"（没找到 ≠ 不存在）。三者都会让下一轮把一个没验过的前提当地基。

`docs/新知界需求.md` 的「证据门禁」用的是同一套七类标记，**两份文档的定义必须保持一致**；改一边就要同步另一边。

### `[未查到]` 和"官方说不支持"不是一回事

这一档是补出来的，因为**缺了它，"搜不到"会自动滑进"不支持"**。2026-08-12 这一天就栽了三次：

- 说 ChatGPT 的 GitHub 集成只读 → 用户截图证明**插件**里有 `Update file`，我一直在搜"连接器"
- 说 ChatGPT 网页端大概率没有协调资格 → 用户截图里的第一方 GitHub 插件实际暴露了写工具；当时把 ChatGPT 插件、只读连接器和 GitHub MCP 混成了一个东西
- 说 `push_files` 缺条件写入 → 真相是根本不需要它，`update_ref` 的非强制更新就是条件写入

**三次都是"我找到的资料没提"被写成了"它做不到"。** 平台方几乎从不写"我们不支持 X"，所以指望靠搜索拿到否定证据，方法本身就是错的。

**否定结论只有两种来源算数**：官方明确写了"不支持"，或者我们实际跑了一次被拒绝。**除此之外一律 `[未查到]`。**

平台会变。**跟你实际看到的行为不符时，以实测为准，然后回来改这份文件。**

## 一、端能力

### ChatGPT 桌面应用的模式划分

**这一小节是 2026-08-16 补的，因为把产品、模式和内置浏览器混成一个"ChatGPT 端"，是这份文档此前最容易出错的地方。**

| OpenAI 名称 | 是什么 | 知界怎么用 | 证据 |
|---|---|---|---|
| **ChatGPT desktop app** | Windows / macOS 桌面产品外壳 | 承载下面全部入口；它是壳，不是执行者 | `[官方文档 2026-08-16]` |
| **ChatGPT**（模式） | 应用顶层入口之一 | 读取历史会话与 Projects；生成 / 接收 ChatGPT 端交换物 | `[官方文档 2026-08-16]` |
| **Chat** | ChatGPT 模式内的快速对话方式 | 普通会话验证 | `[官方文档 2026-08-16]` |
| **ChatGPT Work** | ChatGPT 模式内的工作方式 | 需要文件、插件或电脑操作的技能任务 | `[官方文档 2026-08-16]` |
| **Codex**（模式） | 应用顶层入口之一 | 本地仓库、文件、Git、测试、审计与实现 | `[官方文档 2026-08-16]` |
| **In-app Browser** | 应用内的浏览器工具面板 | 网页验证、受监督下载 / 上传 | `[官方文档 2026-08-16]` |

官方来源：[ChatGPT 桌面应用](https://learn.chatgpt.com/docs/app) · [Projects and chats](https://learn.chatgpt.com/docs/projects) · [Skills & Plugins](https://learn.chatgpt.com/docs/skills-and-plugins) · [Integrated terminal](https://learn.chatgpt.com/docs/integrated-terminal)

#### 两个模式看到的东西不一样

- **切换到 ChatGPT 模式后，侧边栏可见网页版历史会话与 Projects。** `[用户观察 2026-08-16]`
- **Codex 模式没有同一份历史会话 / Projects 侧栏。** `[用户观察 2026-08-16]`
- 这个观察与官方对 ChatGPT Projects/Chats 与 Codex 本地项目的分工描述一致。`[官方文档 2026-08-16]`

**由此确定：要读 ChatGPT 历史会话或 Project，去 ChatGPT 模式读，不要绕内置浏览器。**

#### Skill 在两个模式里都能用，调用符号不同

- 同一份 Skill 可供 ChatGPT 与 Codex 使用；**ChatGPT 用 `@` 显式选择 Skill，Codex 用 `$`。** `[官方文档 2026-08-16]`
- 因此 ChatGPT 模式不是"临时绕路"，是 OpenAI 官方支持的 Skill 运行面。知界的 ChatGPT 端测试应当在 ChatGPT 模式里跑。

#### 内置浏览器不等于 ChatGPT 模式

- 内置浏览器打开 `https://chatgpt.com/` 时显示**未登录**，可见"登录"按钮与"登录以获取基于已保存聊天的回答"提示。`[实测 2026-08-16]`
- **内置浏览器不自动继承桌面应用的登录态。** 应用已登录 ≠ 内置浏览器已登录。`[实测 2026-08-16]`
- **内置浏览器登录不是知界读取 ChatGPT 会话和 Projects 的前置条件**，因为那条路径走 ChatGPT 模式。内置浏览器保留给网页交互与端到端验证。

#### Apple 登录失败：VPN 是可信诱因，不是已确认根因

- 点击"使用 Apple 账户继续"后，页面**成功到达** Apple 官方登录页（标题"使用 Apple 账户登录 OpenAI"），OAuth 回调指向 `auth.openai.com`。`[实测 2026-08-16]`
- 所以 VPN **没有**造成"入口完全不可达"。`[实测 2026-08-16]`
- OpenAI 官方登录排障把关闭 VPN / 代理、允许 `chatgpt.com` / `openai.com` / `auth.openai.com` 的 Cookie 与 JavaScript、换网络或干净浏览器会话列为标准检查项。`[官方文档 2026-08-16]` https://help.openai.com/en/articles/7426629
- 最可疑的环节是 Apple 完成认证后回跳 `auth.openai.com` 时，受 VPN 出口信誉、IP / 地区变化、Cloudflare 验证或内置浏览器会话状态影响。`[推断 2026-08-16]` 推导链：入口可达 + 官方把 VPN 列为登录问题标准检查项 + 失败发生在凭据提交之后。
- **`[未验证]` 没有做"同一内置浏览器、仅关闭 VPN"的单变量对照测试。** 因此**不能**把 VPN 写成已确认根因。
- 未代替用户输入 Apple 凭据，所以没有复现凭据提交后的错误；错误发生点仍以 `[用户观察]` 为准。

#### 服务状态查询

- **2026-08-16 查询 OpenAI 状态页，ChatGPT、Codex 等服务显示正常，没有已知全局故障。** `[实测 2026-08-16]` https://status.openai.com/
- 因此当时的登录问题更像本地网络、浏览器会话或 OAuth 回跳问题，**不是全站中断**。`[推断 2026-08-16]` 推导链：状态页无广泛故障 + 入口页可达 + 失败点在回跳阶段。

#### `.agents/skills/` 是 Codex 与 Zed 共用的项目级路径

- **Codex**：全局 `~/.codex/skills/`，项目 **`.agents/skills/<name>/`**（本机 `migrate-to-codex` 迁移文档明写 `.claude/skills/<name>/SKILL.md` → `.agents/skills/<name>/SKILL.md`）`[实测 2026-08-12]`
- **Zed**：全局 `~/.agents/skills/`，项目 **`.agents/skills/<name>/`** `[官方文档 2026-08-12]`

**所以一个项目里放一份技能，可以同时喂三个端**：真身放 `.agents/skills/contour/`，再从 `.claude/skills/contour` 软链过去（相对路径，可被 git 跟踪）。这正是 `milky_way` 已经在跑的做法。

⚠️ 但**软链不能作为公开分发的依赖**：Windows 上 git 的 `core.symlinks` 常被自动关掉，那时 clone 出来的是一个装着路径字符串的文本文件，**技能静默加载失败**。软链只用于本地开发方便。

- **技能默认就有 `/skill-name`**，不需要额外配置。自定义命令已并入技能：`.claude/commands/x.md` 与 `.claude/skills/x/SKILL.md` 都产生 `/x`。`[官方文档 2026-08-12]`

- 这两个字段在 **Codex / claude.ai 认不认**：`[未验证]`

### Codex 对集成 Terminal 的能力边界

**结论先说：Codex 当前不能选择或接管一个已经存在的交互式 Terminal 会话。**

#### 官方能力

- 官方文档写明：ChatGPT 桌面应用中的每个聊天都有一个与当前项目或 worktree 对应的 Terminal；Codex 可以**读取**当前 Terminal 的输出。`[官方文档 2026-08-16]` https://learn.chatgpt.com/docs/integrated-terminal
- 官方文档**没有**公开"列出所有 Terminal 标签页、按标签名选择、向任意已有交互式会话发送 stdin"的用户级接口。`[未查到 2026-08-16]`

#### 本机结果

- 本项目现有的 `Codextest` 标签页**无法被当前任务按名称选择或附着**。`[实测 2026-08-16]`
- 重启 Codex 后再次读取当前任务的 App Terminal，仍返回 `No app terminal session is attached to this thread yet.` `[实测 2026-08-16]`
- Codex 可以另起一个自己管理的 PTY 并在其中启动 Claude Code、发送文本、读取输出——**但那不是用户已有的那个会话**，不能作为"接管已有会话"的证据。`[实测 2026-08-16]`

## 二、网页端的数据层可达性

**这一节推翻了早先的一个设计妥协。** 早先认为网页端只能一份份上传文件，所以只传 `routing.md`、数据层靠连接器按需读。实际上两边都有官方的**仓库级**连接。

> **2026-08-16 读法提示。** 本节里的"能倾倒 / 能读 / **有协调资格**"这组判据是按**旧的 GitHub 多写者架构**写的——那时"能不能安全写 GitHub"就等于"有没有协调资格"。
>
> **当前架构下这个等式不成立了**：协调资格由本地执行门槛十项决定（见第五节），网页与会话界面**永远**没有协调资格，与它们能不能写 GitHub 无关。
>
> 本节的能力事实**仍然准确**，只是不要再拿"有协调资格"那一列当当前判据用。

### claude.ai Projects + GitHub 连接器

- 可以把一个 GitHub 仓库加成 **project knowledge**，**私有仓支持**（官方文档有专门一节讲连私有仓）
- 更新靠手动点 **"Sync now"**；官方建议定期刷新
- **auto-sync on push to `<branch>`** 的每项目开关在开发中，默认关闭

`[官方文档 2026-08-12]` · `[社区]`（auto-sync 部分）

### ChatGPT + GitHub 连接器

- OAuth 之后**索引**仓库内容（代码、README、文档），typically takes a few minutes
- 连接后会问最常用哪些仓，**预先同步以提升速度和质量**
- 尊重 GitHub 既有权限

`[官方文档 2026-08-12]`

### 由此确定的两件事

**一、延迟顾虑不成立。** 不是每轮现场调连接器拉 GitHub，是**预先索引好、提问时在平台自己的服务器检索**。

**二、但连接器解决不了常驻。** 索引是**按需召回**——问到相关内容才出来；而 `routing.md` 要的是"第一句话还没说完它就已经在了"。**两件事机制不同，连接器只解决数据层。**

### 一个必须先想清楚的代价

**把整个实例仓交给连接器索引，等于把 `dumps/` 里的倾倒原文送进两个平台的索引。** 那里面是健康、家庭、职业困境的原话。

"仓库私有"是对 GitHub 说的；连接器索引是另一回事——内容进了平台。可能的缓解是把 `dumps/` 拆到另一个仓，只把统一文件连给网页端，代价是实例仓变两个、协调流程要改。**这是隐私偏好，由用户决定，技能不替他判断。**

### claude.ai 必须按界面拆开，不能再把“网页版”当成一个端

| 界面 / 通道 | 已确认能力 | 对知界意味着什么 |
|---|---|---|

### ⚠️ ChatGPT 里有**两个** GitHub 集成，别混

### Developer Mode 的自定义 MCP（备用路径）`[官方文档 2026-08-12]`

Settings → Connectors → 底部 Advanced settings → 打开 Developer Mode。**Plus / Pro / Team / Enterprise / Edu 都有**；只接远程 HTTPS MCP server；支持 no-auth / API key / OAuth。

**第一方插件够用的话，不需要走这条。** 留着是因为它能挂 GitHub 官方 MCP（有 `push_files`），万一第一方插件缺多文件原子提交，这是补救路径。

### `push_files` 的参数没暴露基础版本，但官方实现使用非强制引用更新 `[官方文档 2026-08-13]`（**源码证据**）

```
create_or_update_file:  owner, repo, path, content, branch, message
                        + sha（可选，被替换文件的 blob SHA）   ← 有条件写入
push_files:             owner, repo, branch, files[], message
                                                     ↑ 没有任何 base SHA / expected-head
```

工具参数表本身没有 `base SHA` / `expected head`，但这不等于实现没有并发保护。GitHub 官方 MCP 源码中的 `push_files` 会基于当前分支提交创建新 tree 和单个 commit，并用 **non-force / `Force: false`** 更新分支 ref。分支在此期间前进时，非快进更新会被 GitHub 拒绝，而不是静默覆盖。

源码证据：[github-mcp-server `repositories.go`](https://github.com/github/github-mcp-server/blob/2198e8599bbbcb98a0d6cd7cabe9a48629acdf29/pkg/github/repositories.go) `[官方文档 2026-08-13]`（官方仓库源码，按官方明写处理）

所以，`push_files` 是否具备“一次提交改多个文件”和非强制 ref 更新，不需要再让用户靠破坏性实测去发现。GH-06 仍可以作为**当前连接器版本、当前账号和最终选定适配器的回归验证**，但不再承担查明公开实现事实的任务。

## 三、锚点后端

准入是四条能力，缺一条就不能当锚点：

1. 各端**读得到**
2. 各端**写得进自己的收件区**
3. 各端**读得到最新统一版本**
4. **条件写入统一文件**——基础版本被人动过就得重来

第 4 条是最容易漏的：版本号只提供**观察**，不提供**互斥**。两个端都读到 v5、都确认"仍是 v5"、然后分别覆盖，最后写的仍会静默盖掉前一个。

### GitHub 私有仓（**已不是当前 MVP 锚点**）

> **2026-08-16 定位变更。** 当前架构的统一锚点是**本地 Git vault**，GitHub 远端降为可选备份或跨设备通道，见 `新知界需求.md`。
>
> 下面这些关于 GitHub 的事实**仍然成立、仍然有用**——它们描述的是 GitHub 这个后端能做什么，跟知界选不选它是两回事。保留是为了将来评估远端备份适配时不必重查；**但它们不再是 MVP 阻塞项。**

| 能力 | 状态 |
|---|---|
| ① 读得到 | `[未验证]` 待逐端跑 GH-01 |
| ② 写得进收件区 | `[未验证]` 待 GH-02 / GH-03 |
| ③ 读得到最新统一版本 | `[未验证]` 待 GH-01 |
| ④ 条件写入 | 机制由 Git / API 层提供（push 非快进被拒；contents API 的 `sha` 参数不匹配即 409）。**但 GH-06 没跑过** |
| 多文件单提交与安全发布 | GitHub 官方 MCP 的 `push_files` 已由工具文档与源码确认；ChatGPT 第一方插件是否暴露等价路径仍待查工具清单；Claude.ai Chat 尚未完成 GitHub 远程 MCP 接入。必须按具体适配器记录，不能笼统写“网页端未知” |

**已实测的边界**（`[实测 2026-08-12]`）：

- **免费账号的私有仓配不了分支保护**：`PUT /repos/.../branches/main/protection` 和 `POST /repos/.../rulesets` 都返回 403，要求升级 GitHub Pro
- **但升级也解决不了**：分支保护是**分支级**粒度，**GitHub 没有路径级 ACL**，做不到"这个协作者只能写 `dumps/inbox/<他自己>/`"
- 加上多数平台的 GitHub 连接是**仓库级授权**，给的就是全仓写权限
- 所以"来源端只写自己的收件区"**在 GitHub 上永远是协议约束，不是技术隔离**。真正的技术隔离只有服务端校验一条路（GitHub App / Action），MVP 不做
- **别为这个升 Pro，升了也没用**

## 四、本地 Git 并发：`index.lock` 与事务锁是两层

**这一节只记 Git 层的底层事实。并发策略不在这一节——它在第五节的事务锁。** 早先版本把 `index.lock` 当成主并发策略，那是在"多端各自读写同一份 clone"的旧架构下写的；新架构的并发边界由整轮事务锁定义，不由 Git 自带的锁定义。

### Git 层的事实

- **`index.lock` 是单条 Git 命令级别的互斥。** 一条写命令开始时创建、结束时删除；另一条并发写命令会因为它已存在而立刻失败。`[社区 2026-08-12]`
- 它的**保护范围是一次 `git` 调用**，不是一段业务流程。
- **`git worktree` 让每个工作目录有自己的 index、共享 object store**；但同一分支不能在两个 worktree 里同时 checkout。`[社区 2026-08-12]`
- 孤儿 `index.lock`：进程中途崩溃时锁文件不会自己消失。`[社区 2026-08-12]`
- 反面证据：`anthropics/claude-code` issue #55724 记录了**在 worktree 隔离下并行 agent 仍然丢工作**（git lock contention）。`[社区]` **worktree 不是银弹。**

### `index.lock` 不能替代整轮事务锁

一次知界协调事务要跨越很多步：取包 → 校验 → 读统一资产 → 合并 → 写多个文件 → `git add` → `git commit` → 回读 → 写回执。

`index.lock` **只在其中那几次 `git` 调用期间存在**。两个执行者完全可以：

```text
执行者 A          执行者 B
读统一资产
                  读统一资产          ← 两边读到同一版
合并（内存中）
                  合并（内存中）
写文件 + commit    ─────────────────  ← index.lock 各自短暂持有，互不冲突
                  写文件 + commit     ← B 基于过期状态覆盖了 A 的结论
```

**全程没有任何一次 `index.lock` 冲突，但 A 的合并结果被静默丢掉了。** 这正是事务锁要防的东西，而 Git 自带的锁在结构上防不了——它保护的粒度不对。

**因此：**

- **重试 + 指数退避不能绕过业务锁。** 重试解决的是"两条 Git 命令撞在一起"，不是"两个执行者基于同一版本各写各的"。把重试当并发策略，只会让上面那张图跑得更顺畅。
- **事务锁是必须的，不是过度设计。** 早先版本把"文件锁包装脚本"判为过度设计，**该判断已撤销**——它当时假设的是"只要 Git 命令不撞就没事"，而这个假设不成立。
- 事务锁的位置、格式与获取 / 释放语义见 `新知界需求.md`；实测状态见本文第五节。

### 仍然成立的两条操作建议

- **孤儿 `index.lock` 的处理不变**：检测到锁文件但没有活着的 git 进程时**报告给用户，不要自动删除**——自动删有可能杀掉一个真在跑的操作。同一原则适用于知界的事务锁。
- **多个本地执行者可以共用同一个本地 vault 目录**，不需要每端一份副本。前提是**串行**——由事务锁保证，不是由"大家别同时跑"这种约定保证。

（早先说过"共用 clone 会让游标说谎"，**那条是错的，已撤销**：游标记的是"这一端的记忆最后刷新到哪一版"，本地 Git 的 HEAD 记的是"文件在哪一版"，两个轴不一样是正常的。）

## 五、本地执行资格与事务锁

**这一节记的是"谁能写 Vault"的实测状态。** 对照的是 `新知界需求.md` 里的本地执行资格门槛十项。

### 一条必须放在最前面的边界

### 现有校验脚本不校验内容完整性

`skills/contour/scripts/validate_dump.py` 做的是 **schema / 身份 / 位置**的确定性检查：

- 必填字段在不在、枚举值合不合法、`captured_at` 是否带时区；
- `dump_id` 是否为 UUID4、批次内是否撞号；
- `endpoint_id` 字符集、包是否放在 `dumps/inbox/<endpoint-id>/` 下；
- 五个必需章节缺不缺。

`[实测 2026-08-16]` 实跑确认：合规包脚本输出 `OK` 标记；重复 `dump_id` 返回退出码 1 并提示"消费 manifest 会记错账"；两端合规 baseline 时 `--cold-start-ready` 输出 `READY` 标记。（这三个是脚本的控制台输出串，不是证据标签。）

**但它不做内容完整性校验。** 在包正文追加一行后，脚本仍然判定合规——篡改只能靠**脚本之外独立维护的 SHA-256 比对**发现。`[实测 2026-08-16]`

**因此新协议必须写清楚三件事**：哈希由谁生成、保存在哪、谁负责在导入前核对。当前 `dumps/processed/manifest.md` 记录了 sha256，但那是**导入之后**写的，不构成导入前的准入检查。
