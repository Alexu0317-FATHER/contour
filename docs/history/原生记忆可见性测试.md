> 原文状态说明：评审草案。测试目标是测量"某个端此刻实际能调用和导出的记忆"，不是证明厂商后台存储的全部内容。本方案用于冷启动、能力实测和阶段性体检，不是每次日常同步都要执行的硬性验收。

## 要回答的问题

- 该端是否能在新会话中调用原生持久记忆？
- 该端能否主动列出这些记忆，还是只能在相关任务中被动召回？
- 自述倾倒能否区分原生记忆、当前会话推断、项目文件、自定义指令和已加载的知界画像？
- 记忆的作用域是全局、项目、工作区还是无法确认？
- 更正、删除和过期信息在倾倒中如何表现？
- 该端能否在不经过用户搬运内容的情况下，把测试结果提交到指定的私有 GitHub 仓库？
- 自动化任务启动的会话是否拥有与普通网页会话相同的跨项目、跨会话召回范围？
- 该端能否独立完成“先倾倒、再协调、后加载”，而不依赖固定协调端？

## 测试原则

- 使用无敏感性的虚构测试事实，不拿真实家庭、健康或账号信息做探针。
- 每条测试事实使用独特且无自然出现可能的标记，避免模型凭常识猜中。
- 可见性测试开始前不加载知界文件，防止把统一画像误认成原生记忆。
- 需要测试污染隔离时，再明确加载知界或项目文件，并要求模型标记来源。
- 每项测试使用新会话；涉及作用域时，分别在同一项目、其他项目和普通会话中运行。
- 所有结果保存原文，不只记录“通过/失败”。
- 不能访问厂商后台时，只能得出“可访问记忆视图”的结论，不能声称导出完整。
- 不以各端逐条输出完全相同作为目标；重点观察原先分散的互补信息是否逐渐能被更多端调用。

## 测试事实准备

由用户为每个测试端准备几类无害事实，内容可以不同，但必须记录预期作用域：

| 类型 | 目的 | 示例形态 |
| --- | --- | --- |
| 稳定偏好 | 检查跨会话持久召回 | “我的测试饮品代号是 `<唯一标记>`。” |
| 项目限定事实 | 检查项目与全局作用域 | “在测试项目中，内部代号是 `<唯一标记>`。” |
| 明确否决及理由 | 检查负向记忆是否被保留 | “不要使用 `<方案代号>`，因为 `<无害理由>`。” |
| 沟通纠正 | 检查程序性记忆 | “遇到测试主题时，先复述事实，不要先给建议。” |
| 临时事实 | 作为负向对照，不应跨会话出现 | “这句话只供当前会话使用：`<唯一标记>`。” |

测试事实是否真的被平台保存，需要使用该端能够提供的保存方式完成。无法确认保存成功时，测试记录必须标为“前置条件未知”。

## 标准自述倾倒提示

在全新会话中使用；运行前不要附加 `Profile.md`、`Now.md` 或其他知界文件。

```text
这是一次原生记忆可见性测试，不是人物总结。

请只输出你在这次新会话开始前就能跨会话调用的、关于我的持久信息。
不要使用当前这条消息推断我的身份、偏好或性格。

对每一条分别标记：
- 内容
- 你判断的来源：原生长期记忆 / 自定义指令 / 项目或工作区上下文 / 无法确认
- 作用域：全局 / 项目 / 工作区 / 无法确认
- 是否可能过期或存在冲突
- 置信说明

请依次检查这些类别，不要只输出最先想到的一类：
- 身份、经历与能力事实
- 正在进行的事
- 判断方式与价值排序
- 明确否决、负向约束及原因
- 沟通偏好与用户纠正
- 在其他场景可能重新有价值的零散信息

如果你不能直接枚举原生记忆，请明确写“不能枚举”，并说明你能做的是回忆、自述还是读取其他上下文。
某一类没有可访问内容时可以写“无可确认内容”。不要补全缺失项，不要写总结性人物小传。
```

## 可见性测试用例

### MV-01 · 干净会话中的直接枚举

**操作**：关闭知界加载，在全新普通会话运行标准自述倾倒提示。

**检查**：输出是否包含已确认保存的稳定测试事实；是否坦白不能枚举；是否凭空生成一份人物小传。

**通过条件**：能够导出至少一条会话前已存在的测试记忆，或诚实声明不可枚举并进入后续被动召回测试；不得把当前提示中的措辞推断成用户画像。

### MV-02 · 被动召回与主动枚举差异

**操作**：不询问“你记得什么”，给出一个确实需要稳定测试偏好才能正确完成的小任务。

**检查**：若任务中正确调用了测试事实，但 MV-01 没列出，说明该端“能召回但不能完整枚举”。

**记录**：分别保存枚举结果与任务行为，不把任务猜中自动等同于记忆可见。

### MV-03 · 当前会话污染负向对照

**操作**：在会话中提供临时事实，并明确不要求保存；结束后在新会话运行标准自述倾倒。

**通过条件**：临时标记不应出现在持久记忆结果中。若出现，记录是平台真的保存、会话泄漏还是模型猜测，不能直接归类。

### MV-04 · 知界回声隔离

**操作**：先完成 MV-01；随后加载一份含独特标记的知界测试画像，再次要求倾倒，并将 `contour_context_loaded` 标为 `true`。

**通过条件**：模型把标记归到“已加载的知界文件”而不是“原生长期记忆”。如果无法区分，记录为反馈回路高风险。

### MV-05 · 项目文件与自定义指令隔离

**操作**：在项目文件或项目指令中放入独特标记，在该项目内和项目外分别运行倾倒。

**通过条件**：项目内能够看到时应标记为项目或工作区来源；项目外不应声称它是全局记忆。

### MV-06 · 作用域穿透

**操作**：分别在保存测试事实的原项目、另一个项目和普通新会话中询问同一问题。

**记录**：标明事实在哪些范围可见。不同范围表现不一致时，不将它提升为全局记忆。

### MV-07 · 更正传播

**操作**：先保存一个测试事实，再通过该端支持的方式明确更正；在新会话倾倒。

**通过条件**：新事实被召回；旧事实要么消失，要么被明确标记为旧版本，不得把两者同时当成当前事实。

### MV-08 · 删除传播

**操作**：删除一条测试记忆后，在新会话运行主动枚举和被动召回。

**通过条件**：被删除事实不再被调用。若仍出现，记录删除延迟、作用域残留或其他上下文来源。

### MV-09 · 负向约束与沟通偏好

**操作**：用包含测试主题的自然问题触发已保存的否决理由和沟通纠正。

**检查**：模型是否只记住“不要做什么”，还是也保留“为什么”和具体执行方式。

### MV-10 · 过期与矛盾识别

**操作**：准备有明确先后关系的旧状态和新状态，然后执行倾倒。

**通过条件**：模型能够指出哪个是当前状态；无法判断时应同时列出并标记冲突，不得无声选择。

### MV-11 · 自动化任务与普通会话的可见性一致性

**操作**：先在普通网页会话中验证几个未归档、来自不同项目的唯一测试事实能够被跨会话召回；随后让该平台的自动化任务在不附加知界文件的情况下运行同一组召回探针。

**记录**：分别保存普通会话与自动化任务能够召回的事实、作用域和来源说明。普通会话能够跨项目召回，只证明网页端具备该能力，不能自动推出自动化任务拥有完全相同的执行上下文。

**通过条件**：自动化任务能看到与普通会话等价的测试范围，或能明确列出缺失范围。若两者不同，只降低该端的自动化级别，不否定自然语言触发的同步能力。

## GitHub 通道测试

### GH-01 · 定位同一私有仓库

**操作**：通过用户提供的仓库所有者与名称或仓库链接访问指定私有仓库，读取仓库中预先创建的连接测试文件及其提交标识。

**通过条件**：不同端从同一默认分支读到同一唯一内容和提交标识，不接受“我能访问 GitHub”的口头回答。

### GH-02 · 提交来源端倾倒文件

**操作**：在该端自己的 `dumps/inbox/<endpoint-id>/` 创建唯一文件，并通过直写提交或端专属分支 / PR 提交。

**通过条件**：文件出现在正确目录，名称、端标识和内容完整，并能取得可回查的提交或 PR 标识。

### GH-03 · 回读验证

**操作**：立即重新读取 GH-02 文件，核对唯一标记和提交或 PR 标识。

**通过条件**：写入内容可读且没有被格式转换或截断到影响解析。

### GH-04 · 协调能力边界

**操作**：逐项测试读取、搜索、创建提交、更新文件、创建 PR、合并 PR、检测基础版本变化和冲突重试。每个计划完整运行知界的端都使用专用测试文件执行一次临时协调发布，不直接修改正式统一画像。

**通过条件**：明确记录每项能力和实际写入路径。能够安全发布并在基础版本变化时停止覆盖、重新读取的端，标记为“可临时协调”；只能搜索或读取、不能提交倾倒文件的连接不算完成接入。

### GH-05 · 私有性与权限边界

**操作**：确认仓库保持私有，并检查端在执行倾倒动作时只能写自己的倾倒收件区、执行临时协调动作时必须遵守基础版本检查这一规则，能否通过权限、分支保护或技能行为约束得到执行。

**通过条件**：测试未把仓库或倾倒内容公开；端没有在倾倒阶段改动统一记忆，也没有在协调阶段强制覆盖其他提交。若平台连接权限过宽，必须记录为行为约束风险，不能假装已被技术隔离。

### GH-06 · 多端并发发布

**操作**：让两个具备协调能力的端读取同一测试基础版本，分别生成不同且可识别的候选变更；先发布其中一个，再让另一个尝试基于旧基础版本发布。

**通过条件**：第二个端的旧候选结果被拒绝或主动中止；它重新读取最新版本、保留第一个端的变更并重新生成结果。任何端都不得通过强制更新覆盖已经发布的提交。

## 完整回路测试

### RT-01 · 基线倾倒直写

各测试端在不经过用户复制粘贴的情况下，把基线倾倒提交到私有仓库中自己的收件区。

### RT-02 · 任意端接任整合与回声排除

任选一个具备协调能力的端读取多端倾倒，排除当前会话推断和知界回声，生成并发布统一记忆；下一轮换另一个端接任，验证系统不依赖固定协调端。

### RT-03 · 读取与自主吸收

参与端从私有 GitHub 仓库读取同一统一版本。知界说明各文件用途和记忆关注方向，并请该端在自身原生记忆规则允许的范围内自主吸收；不要求逐条保存或口头保证“已经全部记住”。

**记录**：保存该端最后成功读取的统一版本和读取通道。该记录只证明材料已送达，不证明后台记忆内容。

### RT-04 · 阶段性收敛观察

在冷启动实测、新增端、更换模型、怀疑漂移或定期体检时，使用相同场景题观察各端能否调用原先分散的互补信息。干净会话召回和再次倾倒可以作为诊断手段，但不要求每次同步后执行。

**判断**：看信息缺口和行为差异是否缩小，不比较逐字输出，也不要求各端后台记忆完全一致。

### RT-05 · 快变信息路由

让用户询问一个已经在项目权威来源中更新、但统一记忆仍保留旧摘要的问题。

**通过条件**：模型按 `Sources.md` 查询权威来源，而不是直接复述旧记忆。

### RT-06 · 异步接力与滞后端追赶

**操作**：端 A 先完成一次同步并发布新统一版本。保持端 B 不运行；之后在端 C 完成一次同步。最后才在仍持有旧记忆的端 B 触发“同步知界”。

**通过条件**：端 B 先倾倒自己尚未同步的原生记忆，再读取当前锚点、临时协调仍待处理的倾倒，最后加载最新统一版本；端 B 不要求 A 和 C 同时在线，也不把自己的倾倒时间当作覆盖新统一版本的依据。

### RT-07 · 一次自然语言触发完成当前端闭环

**操作**：只向当前端发出一次“同步知界”或等价自然语言指令，不分别提示倾倒、合并和加载。

**通过条件**：当前端能根据状态依次完成必要动作；没有本端变化时不创建空倾倒，没有待处理包时不制造无意义统一版本，完成后记录本端最后成功倾倒、处理和读取的版本。

## 结果分级

| 结果 | 含义 |
| --- | --- |
| 无持久召回 | 新会话无法观察到测试事实，或前置保存是否成功无法确认 |
| 可被动召回 | 相关任务中会使用记忆，但主动倾倒无法稳定列出 |
| 可自述倾倒 | 能列出可访问记忆并基本区分来源，但不代表后台存储完整导出 |
| 可核对导出 | 自述结果可以与该端提供的设置页或正式导出交叉核对 |

分级描述能力，不代表产品优劣。知界的倾倒协议必须适应“只能被动召回”或“只能自述”的端，不能假定所有端都有正式导出接口。

## 首轮建议范围

先选择能够代表不同能力边界的端：一个网页端和一个本地端。两端都完成原生记忆可见性、GitHub 通道和完整回路测试，并分别接任一次临时协调后，再决定是否扩大到其他端。

首轮不追求证明“全部记忆都能导出”；只验证以下核心假设：

- 能获得足够诚实的可访问记忆视图；
- 能分离原生记忆与当前上下文；
- 能直接写入共同锚点；
- 不同端能够临时接任协调，并在并发时防止相互覆盖；
- 一次自然语言或技能触发能够完成当前端的“先倾倒、再协调、后加载”；
- 统一结果能够被各端读取，并在后续使用中推动原先互补的信息缺口逐渐缩小。
