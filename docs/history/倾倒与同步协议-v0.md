## 目标

在不让用户反复复制粘贴数据的前提下，让不同 AI 端把各自可访问的原生记忆写入同一个锚点。任意具备完整读写能力的已纳入端都可以在一次同步中临时接任协调，整合待处理内容并发布统一结果，再由当前端和后续使用的其他端读取，供各自的原生记忆系统按平台规则自主吸收。协议追求各端理解逐渐收敛，不要求后台记忆逐字一致，也不依赖固定协调端持续可用。

本协议只统一知界资产。项目进度、任务、日历和原始项目文件仍保留在各自的权威系统中，由 `Sources.md` 按需路由。

## Alex 实例的既定选择

- 统一锚点：待创建的私有 GitHub 仓库。
- 建仓后在 `ContourConfig.md` 中保存仓库所有者与名称、仓库链接和默认分支。
- 每个纳入端必须实际完成读取、创建提交和回读测试，不能因为界面里出现 GitHub 连接就判定接入成功。
- 知界不要求用户在日常同步中搬运倾倒内容。用户可以完成一次性的登录、授权和连接操作。

## 同步动作与写入边界

来源、协调和加载描述的是一次同步中的动作，不是三个固定端。一个端可以在同一次运行中依次完成三种动作；没有任何产品被永久指定为协调端。

### 倾倒动作

当前端执行倾倒动作时只能：

- 读取实例配置、自己的上一份倾倒和必要的版本元数据；
- 在自己的倾倒收件区创建新文件；
- 读取自己刚写入的文件以验证结果。

执行倾倒动作时不得修改 `Profile.md`、`Now.md`、`Evidence.md`、`Interaction.md` 或 `Sources.md`。为了保存尚未同步的本端信息，当前端必须先倾倒，再读取可能更新过的统一记忆。

### 临时协调动作

具备统一锚点读取、倾倒写入、统一文件编辑和冲突重试能力的端，都可以在当前运行中尝试临时接任协调。临时协调者负责：

- 读取尚未整合的倾倒文件；
- 验证格式和来源；
- 合并重复内容、识别冲突和反馈回路；
- 更新统一记忆文件；
- 标记倾倒文件的处理状态。

协调能力按端实测后记录在 `ContourConfig.md`，但不记录永久协调者。用户这次在哪个合格端触发同步，哪个端就可以尝试协调；某一端用量耗尽、离线或连接失效，不得阻断其他合格端接任。

同一基础版本只允许一个协调结果发布成功。候选协调者必须基于明确的仓库版本生成结果，并在发布时再次确认该版本没有变化；如果其他端已经先发布，当前候选结果立即作废，重新读取并重新合并，不得强制覆盖。

### 加载动作

发布成功或确认锚点已经处于最新版本后，当前端读取自上次成功加载以来的变化，并把统一材料及记忆关注方向交给本端原生记忆系统自主吸收。其他未在场端不需要立即启动，在下次使用或自动化运行时执行同一同步流程。

### 用户

用户负责：

- 决定纳入哪些端并授权连接；
- 裁决无法从时间、来源和明确更正中解决的冲突；
- 更正、撤回或删除个人数据。

## 私有 GitHub 仓库结构草案

```text
<private-repo>/
├── ContourConfig.md
├── Profile.md
├── Now.md
├── Evidence.md
├── Interaction.md
├── Sources.md
├── PersonaTests.md
├── dumps/
│   ├── inbox/
│   │   └── <endpoint-id>/
│   └── processed/
├── review/
└── tests/
```

设计理由：每个端执行倾倒动作时只在自己的 `inbox` 中创建独立文件，避免多个端并发修改同一个文档。统一记忆文件不绑定固定写入端，但同一基础版本只接受一次协调发布。

仓库默认分支保存当前统一结果。倾倒动作只能创建唯一的新文件：具备受控直写与冲突重试能力时可以直接提交；否则使用端专属分支或 PR。统一文件只能由完成临时协调流程的端修改，且发布必须检查基础版本，禁止强制覆盖。

提交历史提供变更审查能力，但不能代替倾倒包中的来源元数据。处理过的倾倒包可以保留原位并由清单记录状态，不强制为了归档而移动文件。

## 端标识

每个纳入端获得稳定的 `endpoint-id`，用于区分来源。标识描述产品表面而非具体模型，例如：

```text
chatgpt-web-personal
claude-ai-web-personal
codex-desktop-main
claude-code-main
```

模型名称、版本、账号范围和项目范围属于每次倾倒的元数据，不写入 `endpoint-id`，避免换模型后被误认为一个全新的端。

## 连接握手

每个端首次接入时执行：

1. 通过仓库所有者与名称或仓库链接找到同一个私有仓库，并确认默认分支。
2. 读取 `ContourConfig.md`；文件尚不存在时，任一具备完整读写能力的候选端都可以基于空仓库当前版本创建，发生并发时只接受一次成功发布。
3. 在 `dumps/inbox/<endpoint-id>/` 创建一份唯一的握手文件，并通过直写提交或分支 / PR 提交。
4. 重新读取该文件及其提交标识并核对唯一内容，证明不是模型口头声称“可以访问”。
5. 读取一份已存在的连接测试文件及其提交标识，确认各端看到的是同一仓库和分支状态。
6. 把读取、搜索、创建提交、更新文件、创建 PR、合并 PR、检测基础版本变化和冲突重试的实际能力写入 `ContourConfig.md`，据此判断该端能否临时接任协调。

如果某个端既不能直接提交倾倒文件，也不能通过分支或 PR 提交，则该端尚未完成知界接入。v0 不把用户复制粘贴视为合格的日常通道。

## 倾倒类型

- **基线倾倒**：端首次纳入时执行，描述该端当前可访问的全部原生记忆视图。
- **增量倾倒**：后续执行，输出自上次成功倾倒以来新增、更正、失效或值得重新确认的内容。
- **验证倾倒**：用于测试原生记忆可见性和来源隔离，不进入正式画像，除非用户明确批准。

已有 `Profile.md`、记忆导出文件和自建画像作为独立来源导入，不能替代任何已纳入端的基线倾倒。

## 倾倒文件命名

```text
<captured-at>__<endpoint-id>__<dump-type>.md
```

`captured-at` 使用带时区的 ISO 8601 时间；文件系统不支持冒号时，用连字符替代。每次倾倒创建新文件，不覆盖旧文件。该时间只表示文件生成时间，用于唯一命名和审计，不表示其中事实发生得更晚、更准确或应当覆盖其他端。

## 倾倒包格式

```yaml
---
schema_version: contour-dump-v0
dump_id: <全局唯一标识>
endpoint_id: <稳定端标识>
provider: <厂商>
surface: <web/desktop/code/other>
model: <当前模型；未知则写 unknown>
captured_at: <带时区时间>
dump_type: <baseline/incremental/verification>
memory_scope: <global/project/workspace/mixed/unknown>
source_method: <native-view/model-self-report/export/file-memory/mixed>
contour_context_loaded: <true/false/unknown>
last_contour_revision_read: <最后读取的统一版本或提交标识；没有则写 null>
previous_dump_id: <增量倾倒引用；没有则写 null>
---
```

`last_contour_revision_read` 同时表示本端原生记忆可能受到哪个统一版本影响，是排除知界回声和判断本端信息是否滞后的基础。它不能用倾倒文件的生成时间替代。

正文使用以下固定章节：

```markdown
## 导出边界与已知限制

## 可访问的持久记忆
### 身份与事实
### 正在进行的事
### 判断方式与价值排序
### 明确否决、负向约束与原因
### 沟通偏好与用户纠正
### 零散但可能跨场景复用的信息

## 记忆中的过期项、矛盾与不确定项

## 非原生记忆来源
### 当前会话现场推断
### 已加载的知界文件
### 项目文件、自定义指令或其他外部资料

## 本端无法确认的内容
```

倾倒端必须把“持久记忆”和“当前会话或外部文件中现推的内容”分开。不确定来源时放入“非原生记忆来源”或“无法确认”，不能冒充原生记忆。

## 倾倒覆盖策略

倾倒不是厂商后台数据的完整导出，而是尽量展开该端此刻能够调用的记忆视图。为减少“一个端只想起小说、另一个端只想起社论”这类互补缺口，倾倒时按固定章节依次检查：身份与事实、正在进行的事、判断方式与价值排序、明确否决及原因、沟通纠正，以及跨场景可复用的零散能力证据。

如果该端不能主动枚举记忆，只能在相关任务中被动召回，则允许用不提供答案的主题或场景探针分别触发这些类别，再把确实召回的内容写入倾倒包。探针只负责唤起，不得根据问题本身补全用户画像。无法召回或无法判断来源的内容必须如实标记，不能为了格式完整而编造。

因此，协议能够提高目标信息被倾倒出来的覆盖率，但不能保证取得平台隐藏记忆中的全部内容。后续多轮倾倒和自然使用可以继续补齐第一轮遗漏。

日常同步默认生成增量倾倒。当前端对照自己的 `previous_dump_id`、上一份倾倒和 `last_contour_revision_read` 后，如果没有新增、更正、失效或重新出现的信息，不创建空倾倒文件。基线倾倒只用于首次接入、明确重建基线或诊断测试，不按固定周期重复执行。

## 防止反馈回路

统一画像加载到某一端后，该端可能在下一次倾倒时把知界内容原样吐回。如果再次当作新证据吸收，会形成自我引用并虚增可信度。

执行临时协调动作的端必须：

- 检查 `contour_context_loaded`；
- 检查 `last_contour_revision_read`，识别该端曾经接收过哪些统一内容；
- 识别与统一记忆高度相同的回声内容；
- 将明确来自知界、或与该端已读取版本相同的内容标记为 `contour-echo`，不作为独立证据；
- 只有端内出现新的用户更正、独立事实或新的原生表述时，才把差异部分视为新增信息。

## 整合流程

待处理倾倒包是无序候选集合。文件名和 `captured_at` 不提供新旧优先级，不允许使用“最后上传者获胜”或“最新倾倒覆盖旧倾倒”。

1. 验证倾倒包的唯一标识、来源、时间、`previous_dump_id`、`last_contour_revision_read` 和必填章节。
2. 保留原始倾倒文件，不在原文件内修改模型回答。
3. 分离原生记忆、现场推断、外部资料和知界回声。
4. 对完全重复的内容合并来源引用，不重复制造结论。
5. 判断信息属于 `Profile.md`、`Now.md`、`Evidence.md`、`Interaction.md` 或 `Sources.md`。
6. 按冲突规则处理；无法裁决的内容进入 `review/`。
7. 更新统一记忆并记录本次使用的倾倒文件。
8. 按“并发协调与发布”规则提交；发布成功后再更新处理状态，供其他端加载最新版本。

## 并发协调与发布

每次协调严格执行：

1. 读取默认分支当前提交，记为本轮基础版本。
2. 基于该版本和当时可见的全部待处理倾倒生成候选结果；较晚到达的包可以在下一轮继续处理，不要求等待所有端同时在线。
3. 发布前确认默认分支仍指向本轮基础版本，并使用不允许强制覆盖的提交方式更新。
4. 如果基础版本已变化或提交发生冲突，放弃当前候选结果，重新读取最新统一文件、处理清单和仍待处理的倾倒，再重新合并。
5. 以 `dump_id` 记录已经成功纳入的倾倒包。重复运行时不得再次吸收同一个包；尚未成功发布的包保持待处理状态。

可以使用锚点提供的条件更新、非强制快进、分支 / PR 或串行自动化实现上述约束，但不得把某个固定端在线作为正确性的前提。

## 冲突与更新规则

| 情况 | v0 处理方式 |
| --- | --- |
| 用户明确更正旧信息 | 新信息生效；旧信息保留为已被更正的证据 |
| 同一来源的时间状态变化 | 时间更晚且来源明确的状态进入 `Now.md`；旧状态转为历史证据 |
| 多端描述互补 | 合并为更完整结论，保留各自原始表述和来源 |
| 多端对稳定事实直接矛盾 | 不自动选择；写入 `review/` 等待用户确认 |
| 一条是原生记忆，一条是当前会话推断 | 原生记忆权重更高；推断只能作为待证材料 |
| 内容来自已加载的知界文件 | 标记为回声，不增加证据强度 |
| 项目系统与记忆中的最新进度冲突 | 项目系统作为该领域权威来源；旧记忆标记为过期 |

“时间更晚”指能够追溯到用户陈述、事实发生或权威来源更新的时间，不是倾倒文件的 `captured_at`。只有倾倒时间而没有事实时间和明确更正关系时，不得据此裁决冲突。

确定性操作可以自动执行，例如重复项合并、来源补充和带可靠时间的状态更新。需要形成新的稳定人格结论、改变沟通策略或重定向权威来源时，v0 生成待评审变更，不静默发布。

## 读取与原生记忆引导协议

统一结果发布后，每个端执行：

1. 读取 `ContourConfig.md`，确认实例、最新统一版本和自身接入状态。
2. 冷启动首次同步时读取 `Profile.md`、`Interaction.md`、`Now.md` 和 `Sources.md`；`Evidence.md` 按引用或当前任务需要读取，不把完整证据仓塞进常驻上下文。
3. 后续同步优先读取自该端上次读取版本以来发生变化的统一文件和相关来源，不为确认一处变化而重新灌入全部历史。
4. 明确告诉该端：这些内容是知界整合后的当前材料，请在平台原生记忆规则允许的范围内，自主判断哪些内容有助于未来跨会话理解用户；不要求逐条复制，不要求覆盖系统级规则。
5. 需要最新项目状态时，按 `Sources.md` 查询外部权威来源，不拿 `Now.md` 代替实时查证。
6. 在 `ContourConfig.md` 中记录该端最后成功读取的统一版本和读取通道；这只证明材料已送达，不证明后台逐条保存。
7. 在后续倾倒中声明当前会话是否加载知界，并尽量提供最后读取的统一版本，用于排除反馈回路。

知界不另外生成一份替原生系统决定取舍的“强制记忆更新包”。GitHub 中的统一文件是权威材料；技能负责说明文件职责、变化位置和记忆关注方向，最终保存与压缩仍由原生记忆系统决定。

具备 hook、会话启动指令或文件系统能力的端可以自动读取。不能自动读取的端以平台可用的常驻指令或技能触发能力实现，但仍直接从锚点读取，不要求用户搬运文件内容。

干净会话召回、再次倾倒和场景题可以帮助判断某一端的记忆能力与长期收敛情况，但不作为每次同步的完成门槛。它们在冷启动实测、新增端、更换模型、怀疑明显漂移或定期体检时使用。

## 交互与自动化规则

- 基线倾倒由初始化明确触发，每个已纳入端必须执行。
- 日常同步的跨平台可靠入口是自然语言或技能调用，例如“同步知界”。这属于一次触发，不属于让用户搬运数据。
- 用户不需要分别下达倾倒、合并和加载命令。当前端收到同步请求后，按固定顺序执行：先倾倒本端增量，再读取并协调待处理包，最后加载此时最新的统一版本。
- 支持 hook、会话开始或结束触发器的端，可以自动启动同一套完整状态机，也可以只自动完成安全的前半段并把未完成状态留在锚点中；不得改变“先倾倒、后加载”和并发发布规则。
- 网页端常驻指令可以机会式检查待处理倾倒和未读取版本；工具未被实际调用时不得声称已经同步。用户自然语言触发仍是网页端保底入口。
- 定时任务只用于保底检查待处理包、未读取版本和失败任务。检测到变化后，可以在该端能力已经验证时启动同一同步状态机，否则只生成必要提醒。它不是所有端按同一周期执行完整倾倒的默认方案；没有变化时不得上传空快照。
- 锚点自动化可以验证格式、维护队列、去重标识、串行化发布尝试和生成提醒。MVP 不要求它脱离任一 AI 端自动完成需要语义判断的画像合并。
- 不要求用户同时打开所有端。未在场端在下次使用或自动化运行时执行同一流程并追上最新版本。

各端的变化检测、网页端机会式触发和定时任务可见性仍需实测，但这些差异只影响自动化程度，不改变跨平台主流程。

## v0 验收条件

- 至少一个网页端和一个本地端能在不公开仓库的前提下，向同一私有 GitHub 仓库提交各自的基线倾倒文件并回读。
- 用户不需要复制粘贴倾倒内容。
- 至少两个不同端能够先后临时接任协调，不依赖某个固定端或固定产品持续可用。
- 当前临时协调者能区分原生记忆、现场推断、外部资料和知界回声。
- 任一合格端收到一次同步指令后，能够按“先倾倒、再协调、后加载”的顺序完成当前端闭环。
- 两个端基于同一版本同时准备协调结果时，只允许一个先发布；另一端能识别版本变化并重新合并，不覆盖已发布结果。
- 临时协调者能生成统一记忆，并让参与测试的端在各自下次运行时读取最新版本及其记忆关注说明。
- 验收不要求各端逐条复述同一份记忆；场景测试能够观察到互补信息缺口减少即可。
- 快变项目问题能够按 `Sources.md` 查询权威来源，而不是只回答记忆中的旧状态。
- 无法自动解决的冲突会进入评审，而不是被静默覆盖。

- MVP 采用条件直写、端专属分支 / PR 还是锚点串行自动化来保证并发发布安全。
- 网页端增量倾倒能够自动到什么程度。
- `review/` 采用独立变更文件还是在统一文件中使用待确认标记。
- 原始倾倒文件的保留、归档和彻底删除规则。
