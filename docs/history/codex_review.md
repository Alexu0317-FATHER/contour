## 结论

两边不是二选一。Codex 文档适合做**协议内核和验收依据**，CC 草稿适合做**技能的交互外壳和操作手册**。

最终版本应当保留 Codex 已经确定的几个硬约束：倾倒包不可变、倾倒时间不能代替事实时间、任意合格端都能临时协调、发布必须有真实的并发保护、日常不依赖人工搬运、项目最新状态要路由到外部权威来源。同时吸收 CC 已经做得更好的部分：状态驱动的初始化、可直接运行的自述提示词、`routing.md` 的常驻设计、“装”和“喂”的区分、端能力探测，以及不把测试题喂给被测端的行为体检。

我不建议把任一边全文覆盖到另一边。正确做法是：**以 Codex 协议约束数据流，以 CC 技能组织用户交互，再把两边重复的解释压缩掉。**

## 双方已经对齐的部分

- 知界不取代平台原生记忆。统一文件提供材料、来源和关注方向，平台仍按自身规则决定保存什么。
- 冷启动必须让每个已纳入端至少完成一次基线倾倒；已有 `profile.md` 只能作为一个来源，不能跳过基线。
- 一个实例只有一个统一锚点，但不等于只有一个固定写入端或固定协调端。
- 当前端必须先保护本端尚未同步的信息，再读取统一结果，避免加载新画像后把本端独有信息冲掉。
- 日常同步以变化驱动为主；没有新增、更正、失效或撤回时，不应制造空倾倒包。
- 需要区分原生记忆、当前会话推断、外部文件内容和知界回声。
- 各端不需要同时在线。落后的端在下次自然使用时追上即可。
- “材料已送达”不等于“原生记忆已经按预期吸收”，更不等于各端后台记忆逐字一致。

这些共识已经足以支撑 MVP。现在需要解决的是少数会破坏正确性的细节，而不是继续重谈产品定位。

## CC 草稿应当修改的阻断问题

### 倾倒时间不能获得“例外裁决权”

[`references/consolidate.md`](../../references/consolidate.md) 第 75–78 行和 [`references/dump.md`](../../references/dump.md) 第 40 行认为：由事件或用户触发的倾倒，其捕获时间可以近似代表本端最后产生新内容的时间，因此可以参与时效裁决。

这个推理不成立。一次“刚聊完后的倾倒”仍然可能吐出多年前形成、刚刚才被召回的旧记忆；另一个端晚几分钟倾倒，也可能只是重新描述更旧的状态。触发方式可以表示包的产生背景，不能把包内所有条目变成同一个事实时间。

应改为：

- `captured_at` 和触发方式只用于审计、调试与评估召回条件；
- 只有条目级的事实发生时间、用户陈述时间、权威来源更新时间，或明确的 `supersedes` / `retracts` 关系可以裁决新旧；
- 缺少这些依据时保留并列来源，进入待确认，不以“用户触发”作为最后胜负手。

### 同端新包不能覆盖未处理旧包

[`references/dump.md`](../../references/dump.md) 第 44 行和 [`references/drive.md`](../../references/drive.md) 第 61 行规定，同端新包可以把尚未处理的旧包移入 `processed/`。

这会丢信息。原生记忆自述不是数据库快照：同一端第二次可能想起 A、忘了第一次吐出的 B。较新包只能补充或更正旧包，不能证明旧包已被完整包含。

正确规则是：每个倾倒包拥有唯一 `dump_id` 并保持不可变；只有某次已成功发布的统一版本明确记录“消费了哪些 `dump_id`”，这些包才进入已处理状态。重复内容在条目层去重，旧包不能仅因新包出现而退出合并候选集。

### “任何后端都能乐观并发”说得过头

[`references/drive.md`](../../references/drive.md) 第 73–79 行认为，裸文件只要在台账里留版本号，也能不依赖锁实现乐观并发。这里缺少最关键的一步：**检查基础版本和提交写入必须由后端提供原子性的条件更新，或通过可串行化的发布路径实现。**

两个端都读到 v5、都检查“仍是 v5”、随后分别覆盖普通文件，最后一个写入者仍会静默覆盖前一个。版本号只提供观察，不自动提供互斥。

MVP 已选择 GitHub，因此应明确使用 GitHub 可验证的基础提交检查、非强制更新、端分支/PR 或串行自动化中的一种。其他后端以后各自实现同一并发接口，不能用一行台账版本号假装已经满足。

### 交互入口与已确认方案冲突

[`SKILL.md`](../../SKILL.md) 第 93–102 行把循环拆成“进来追平、出去倾倒”，并坚持用户说“倾倒一下”而不是“同步一下”。进出时机的分析有价值，但不该变成产品入口。

已确认的交互应是：用户在当前端说“同步知界”或调用技能，技能按状态执行当前能够完成的闭环——先保护本端增量，再处理锚点待办，最后让当前端读取最新统一结果。支持 hook 的端可以把捕获、推送、拉取拆到不同事件中，但这些只是同一状态机的实现细节。

### 缺少独立的信息源路由

CC 的五文件模型没有 `sources.md`。这是实质性缺口，不是命名偏好。

`routing.md` 回答“怎样与用户沟通、什么值得关注”；`sources.md` 回答“涉及最新项目状态、任务、日历或外部事实时去哪里查”。没有后者，知界越成功，模型越可能自信地复述一份过期但已广泛传播的 `now.md`。

`sources.md` 不应常驻全文，也不保存完整项目账本；它只保存意图识别线索、权威入口、深入来源、不可用时的退路和最后验证时间。

### `now.md` 不应同时承担用户状态和同步台账

CC 把信源位置、所有端的接入方式、最后加载时间和探测结果放入 `now.md`。这混合了两类变化频率和两类写入者：

- 用户当前状态会由语义合并更新；
- 每端游标和能力结果会由各端独立、频繁更新。

多个端共同修改同一个 `now.md` 会重新制造并发热点，也让“用户最近怎样”夹杂大量基础设施状态。建议把稳定实例配置放入 `config.md`，每端游标与回执拆到 `state/endpoints/<endpoint-id>.yml`；`now.md` 只保存快变的用户状态。

### “只追加、不改不删”侵犯了已确认的数据权利

[`references/schema.md`](../../references/schema.md) 第 71 行和 `assets/templates/evidence.md` 都把 `evidence.md` 定义为永不删除。普通修订采用追加和取代记录是合理的，但用户明确要求更正、撤回或删除个人数据时，技能必须支持。

需要区分：

- 正常演化：保留来源，追加 `superseded` / `retracted` 状态；
- 用户要求从当前资产移除：停止下游使用并写入删除标记；
- 用户要求彻底删除：清理当前文件、倾倒包和仓库历史中的对应数据，并明确说明 Git 历史重写等后果。

没有这条，所谓数据主权只剩“冲突时不替用户裁决”，并不完整。

### 平台装载机制必须实测，不能写成已确认事实

[`references/load.md`](../../references/load.md) 第 57 行把 Codex `AGENTS.md` 的 `@路径` 导入写成确定性能力。当前 OpenAI 官方说明的是 `AGENTS.md` 的逐层发现、作用域与拼接，没有把 Claude 风格的 `@path` 展开列为 Codex 支持能力。因此它最多是待验证适配器，不能成为 Codex 的默认装载基线。参见 [OpenAI Codex：Custom instructions with AGENTS.md](https://developers.openai.com/codex/guides/agents-md)。

Codex 端应优先使用官方的 `AGENTS.md` 层级与生成的受管内容块；任何 `@path`、网页项目文件是否每轮确定性注入、黑盒记忆是否读取上下文等假设，都放进端能力测试，验证后再启用。

### 人工搬运只能是恢复路径

[`references/dump.md`](../../references/dump.md) 第 30 行和 [`references/drive.md`](../../references/drive.md) 第 91 行仍把用户手动搬运视为“可用但不能自动化”的端。

产品边界应更严格：写不进统一锚点的端可以读取统一结果，属于只读或部分接入；它没有完成双向知界同步。用户手工复制可以用于首次诊断、授权受阻时的临时恢复，但不能成为日常支持矩阵中的正常通道，否则会回到用户最初明确拒绝的工作方式。

## Codex 文档应当吸收 CC 的部分

### 直接采用自述提示词骨架

CC 的 [`assets/prompts/self-report.md`](../../assets/prompts/self-report.md) 是当前双方材料里最接近可运行资产的部分。它要求逐条输出、区分 `[记]` 与 `[推]`、保留用户原话、专门寻找否决理由和沟通纠正，并在末尾确认是否还有更多。这正好补足 Codex 协议“列了字段但没有足够强的召回手段”的问题。

需要增加的是包级元数据、条目级来源/事实时间/更正关系，以及一份更短的日常增量提示词。冷启动可以深挖，日常每次都跑完整基线提示会造成噪音和重复。

### 采用“装”和“喂”的区分

CC 对加载动作的拆分是对的：

- “装”解决文件或规则能否进入当前上下文；
- “喂”只是把高质量材料交给原生记忆系统参考。

Codex 文档目前把“读取统一结果”和“供原生记忆吸收”写得正确但偏抽象。最终技能应把两步写成明确动作，同时继续保持低承诺：完成标准是材料已读取、来源与用途已说明、回执已记录；不是模型口头说“全记住了”。

### 用 `routing.md` 取代含义偏窄的 `Interaction.md`

CC 的 `routing.md` 同时容纳沟通路由和记忆关注策略，并且为规则保留“为什么”。这比 `Interaction.md` 只让人联想到文风更准确，也更贴合最早确认的“给原生记忆一个用户专属关注背景”。

但要保持边界：`routing.md` 不承载外部信息源路由；后者仍属于 `sources.md`。

### 采用状态驱动的初始化

CC 的“先读锚点，再判断是冷启动、新端接入还是日常维护”比让用户回答一串系统状态更可靠。最终技能的第一步应先检查锚点及本端回执，只有读不到或权限不明时才询问用户。

### 采用隐藏行为体检

CC 明确要求 `tests.md` 不进入被测端上下文，并用场景判断测试沟通和决策行为，而不是考“女儿几岁”之类的知识背诵。这一设计应直接并入 Codex 的测试文档。

但 [`references/audit.md`](../../references/audit.md) 第 115 行所说“没有产生改动的体检就说明没必要跑”需要删除。无变化可能恰恰证明一次路由改动没有引入回归，或多个端仍维持可接受的趋同。体检产物可以是“无需修正，证据更新”，不必强迫每次都改文件。

### 保留探测思想，补控制组与清理动作

CC 的 P-1、P-2、P-3 把平台能力当作待测假设，这个方向完全正确。执行时还需要：

- 使用无害、独特、可删除的测试事实；
- 测试后清除污染并验证删除传播；
- P-2 测完撤掉会改变所有回答方式的临时规则；
- P-3 增加未写入记忆路由的相似控制事实，否则“后来记住了”不能证明是路由造成的。

Codex 的可见性测试负责来源隔离和删除传播，CC 的探测负责平台适配，二者组合后才完整。

## Codex 自身文档需要修正的地方

### GitHub 状态已经过期

[`新知界需求.md`](../新知界需求.md) 第 261 行和 [`倾倒与同步协议-v0.md`](倾倒与同步协议-v0.md) 第 13 行仍写“待创建的私有 GitHub 仓库”。当前工作区已经连接 `https://github.com/Alexu0317-FATHER/contour.git`，并保留旧版标签。下一轮应改成“复用现有仓库还是另建 MVP 私仓待确认”，同时实际核验远端可见性和默认分支，不能继续写成尚无仓库。

### 规范强，但还不够像一个可执行技能

Codex 三份文档把正确性条件写得很完整，却没有 CC 那样明确的状态入口、提示词、模板和加载适配器。若直接从 Codex 文档开发，模型仍需要现场发明大量操作细节。应把协议中的确定性部分转成：

- 倾倒包 schema 与唯一 ID 生成；
- 待处理包清单和已消费 manifest；
- 基础版本检查与重试；
- 端状态回执；
- 最小的冷启动、日常同步和失败恢复提示。

能够机械执行的部分最好由小型脚本或 GitHub 自动化验证，不要全靠语言模型每次重新理解 Markdown。

### 中央 `ContourConfig.md` 也会成为并发热点

Codex 协议同样把“各端最后倾倒与读取版本”集中在 `ContourConfig.md`。这与 CC 把台账放进 `now.md` 是同一个问题。稳定配置与每端游标应拆开，否则一次正常同步可能同时修改统一画像、处理状态和中央台账，冲突面过大。

### 测试方案需要分层运行

[`原生记忆可见性测试.md`](原生记忆可见性测试.md) 适合作为完整验证目录，但不应要求每个新端一上来顺序跑完所有测试。最终技能应按风险触发：

- 接入必测：来源隔离、GitHub 读写回读、一次完整同步、基础版本冲突停止；
- 能力探测：只运行该端计划启用的加载或自动化能力；
- 行为体检：冷启动基线、路由变化后回归、用户怀疑偏差时复测；
- 深度诊断：删除传播、自动化上下文差异、污染与回声问题。

这不是减少测试覆盖，而是避免初始化被测试流程吞掉。

## 建议的合并后 MVP 结构

```text
contour/
├── config.md                       # 稳定实例配置：锚点、纳入端、权限边界
├── profile.md                      # 慢变用户画像
├── now.md                          # 快变用户状态
├── routing.md                      # 常驻的沟通路由 + 记忆关注策略
├── sources.md                      # 外部权威来源路由
├── evidence.md                     # 证据、来源、取代与撤回关系
├── tests.md                        # 隐藏测试定义，不加载给被测端
├── state/
│   └── endpoints/<endpoint-id>.yml # 本端能力、游标、最后读取/倾倒/加载回执
├── dumps/
│   ├── inbox/<endpoint-id>/<dump-id>.md
│   └── processed/manifest.yml      # 哪个统一版本消费了哪些不可变包
└── review/                         # 冲突、待确认、删除与失败恢复记录
```

名称全部使用小写，避免技能文件与锚点资产在不同平台上出现大小写差异。若未来证明 `config.md` 需要机器严格解析，可以再换成 YAML；MVP 不必为了“像系统”而过早增加格式数量。

## 建议的唯一同步状态机

用户只需要触发“同步知界”。当前端内部按以下顺序运行：

1. 读取稳定配置和本端状态；验证当前端对 GitHub 的实际能力。
2. 在加载任何新统一材料之前，生成本端增量倾倒；无变化则不创建包。
3. 将不可变倾倒包提交到本端 inbox；失败则保留明确的未提交状态，不伪造成功回执。
4. 读取当前统一版本、全部未消费倾倒和处理 manifest。
5. 当前端能力足够时临时协调；不足时跳过发布，但仍可读取已发布的最新结果。
6. 发布前验证基础版本；发生变化就重新读取和重新合并，不强行覆盖。
7. 让当前端读取 `routing.md` 及本轮相关变化，按需读取其他层；向原生记忆说明用途和关注方向。
8. 只更新当前端自己的状态文件，并报告本轮完成、跳过和失败的动作。

本地 hook、会话开始/结束事件、网页自动化或 GitHub 自动化都只能调用这套状态机的安全子步骤，不能另造一套定时同步规则。

## 对 CC 技能包装的具体建议

- 缩窄 `SKILL.md` 的 `description`。目前“只是抱怨 AI 不了解我也必须触发”会让技能在普通对话中大量误触发；应聚焦于用户明确表达跨会话记忆、画像建立、跨端同步、记忆导出/合并或知界维护意图。
- `SKILL.md` 正文只保留边界、不变量、状态机和资源路由；详细论证留在 `references/`。当前正文与 `dump.md`、`drive.md`、`load.md` 重复较多，不符合 `skill-creator` 强调的上下文节约。
- 增加机器校验工具：schema 校验、唯一 ID、pending/processed 状态、基础版本检查和回执更新最值得脚本化。
- 最终发布前补齐 `agents/openai.yaml` 等分发元数据，并运行技能验证脚本。
- 文件层记忆、会话史和外部资料只能作为用户授权的补充来源；“能做就必须做”会扩大隐私和实现范围，应改成按授权与端能力启用。
- “跨项目重复出现的就是人格，只在一个项目出现的就是项目知识”只能作为证据强度提示，不能作硬分类。一条只出现一次但由用户明确确认的长期偏好，仍然可以进入画像。
- `now.md` 超过固定一个月就降权、行为题固定为 8–12 道等阈值没有通用依据。应根据字段的预期变化频率、来源验证时间和覆盖面决定，不把示例数字写成产品规则。

## 下一轮文档合并顺序

1. 先修改协议中的数据正确性：时间规则、不可变包、消费 manifest、并发原语、每端状态和删除语义。
2. 再统一资产模型：采用 `routing.md`，补回 `sources.md`，拆出 `config.md` 与 `state/endpoints/`。
3. 然后把 CC 的冷启动、自述提示词、装载/喂入和探测流程接到唯一同步状态机。
4. 最后重组测试：保留完整测试目录，但把接入必测、适配探测、行为体检和深度诊断分开。
5. 协议和交互稳定后再压缩 `SKILL.md`，生成脚本、模板与分发元数据。

## 合并前仍需明确的事项

- 当前 `contour` 远端仓库是否就是 MVP 锚点，以及它现在是否为私有仓库；不要再同时保留“待创建”和“已经复用”两种说法。
- GitHub 上具体采用条件直写、端分支/PR，还是仓库自动化串行发布。必须选择一种可实际验证的路径。
- 端状态文件使用 Markdown 还是 YAML，以及端 ID 如何稳定生成。
- 用户要求彻底删除时，是否允许改写 Git 历史；如果不允许，产品必须明确说明“从当前资产撤回”和“从所有历史彻底删除”的差别。
- 各平台加载适配器的实测结果，尤其是 Codex `AGENTS.md`、网页项目文件和自动化任务的实际上下文范围。
- 隐藏行为测试由哪个端保管和发起，避免被测端提前读到答案。

这些事项不会推翻当前架构，但会决定第一版能否诚实地声称“完成跨端同步”，而不只是生成了几份看起来很完整的 Markdown。
