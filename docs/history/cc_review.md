三份文档质量排序：**可见性测试 > 需求文档 > 协议 v0**。

- **可见性测试**是三份里最成熟的，MV 系列的污染隔离设计（MV-03/04/05）是我方 `probe.md` 没有的，应整体保留并与我方探测合并。

- **协议 v0 已被需求文档甩在身后**：固定协调端、"复制粘贴不算合格通道"的硬措辞等，需求文档都已改写，协议还停在旧立场。协议需要一次跟进改版，否则两份 Codex 自己的文档互相矛盾。

一个值得记录的独立收敛信号：**"先倾倒、后读取"的顺序两边各自独立得出**（需求 :236 "读取更新的统一记忆之前先倾倒本端"；我方 `drive.md` "先推自己的 buffer，再拉最新"）。理由也一致——先倒出去的内容保证不含本轮刚读进来的统一版本，从源头压回声。这条可以直接冻结为共识。

## 三、Codex 侧需要修的问题

### 严重

**S-1 · `PersonaTests.md` 躺在共享锚点根目录，没有任何隔离规则。**
协议 :53-68 的仓库结构把 `PersonaTests.md` 放在根目录，而所有纳入端都被要求能读锚点（需求 :133-136）。题库对被测端可见，体检从此测的是背诵不是判断——**而且分数会很好看，整套验证机制静默作废**。协议、需求两份文档里都没有"测试文件不得被被测端读取"的规则。
修法建议见第四节 C-1——这个问题我方也只解了一半，值得两边一起定。

**S-2 · 协议 v0 的协调端模型已被需求文档否定，协议未跟进。**
协议 :40 "选定并记录在 ContourConfig.md，更换协调端必须由用户明确确认" vs 需求 :110-116 "任意端可以接任协调……不是固定单一协调端"。后者与我方立场一致（固定协调端是单点阻塞，而"配额用完要换端"正是本技能的起因之一）。协议的角色定义、握手流程 :92-101、待评审决定 :249 里所有"协调端由谁担任"的内容都要按需求文档重写。

**S-3 · "会话结束触发器"已被实测数据否定。**
需求 :106 "本地能力更强的端可以使用 hook、会话开始或**结束**触发器"，协议 :230 "支持 hook 或**会话结束自动化**的端"。2026-08 官方文档实测：Claude Code 的 SessionEnd 钩子默认 **1.5 秒共享预算**（配置后上限 60s，不能阻止退出）；Codex 的 SessionEnd 默认 **1 秒、硬上限 3 秒**。3 秒内完成一次带认证的网络提交不可靠——**结束钩子结构上不能承载倾倒**。且 Codex 的 SessionEnd 还会在会话闲置 30 分钟后触发，时间戳与真实使用时刻脱钩，连"事件驱动"的资格都没有。
可行替代（我方 `drive.md` 已写）：每轮 Stop 往本地 buffer 追加（便宜、可中断），推送挪到下一次会话启动（两端启动钩子都给 600s）。两份文档中所有"会话结束"字样应改为这个模型。

### 中

**M-1 · `ContourConfig.md` 的单一写入者矛盾。**
协议 :28 规定来源端"不得直接修改"统一文件，:98 与 :216-217 又要求每个端把握手能力、最后读取版本写进 `ContourConfig.md`——它就是统一文件之一。需求 :224 延续了这个矛盾。修法二选一：ContourConfig 按端分节、每端只写自己那节（把"单一写入者"细化到节级）；或端状态记录也走 inbox、由当轮协调者合并。

**M-2 · [分歧] "倾倒时间只用于审计"一刀切过严。**
需求 :237 "倾倒时间只用于审计，不代表其中事实比其他端更新或更可信"。方向对——按文件日期裁决是我方也禁止的。但全禁扔掉了一个真实信号：**倾倒跟着使用走的时候，捕获时间约等于"这一端最后一次产生新内容的时间"**。用户刚在 claude.ai 聊完求职就倾倒，这个包在求职话题上就是比三周没碰过求职的 Codex 新。
我方方案：倾倒包标触发方式（`事件` / `用户` / `轮询`），前两种的捕获时间可参与时效裁决，轮询包降权只作 tie-breaker。全禁的代价是大量本可自动解决的时效冲突涌进评审——评审一旦拥挤，用户就会开始批量点"同意"，评审机制自己失效。

**M-3 · 协议只有"喂"，没有"装"。**
协议的读取协议 :211-222 覆盖了"各端读取统一结果并自主吸收"（喂），但 `Interaction.md` 怎么进各端的**常驻**上下文、确定性怎么保证，只有一句":222 不能自动读取的端以平台可用的常驻指令或技能触发能力实现"。这一句下面全是深坑：技能是渐进披露的，description 没匹配上就不加载；"会话开始时读 X"是把动作交给模型自觉，概率性的；项目文件可能是检索召回而非确定性注入。行为层的整个价值建立在"每轮都在"上，装的机制不写，沟通路由就是纸面资产。我方 `load.md` 有三种装法 + 各自失效模式，可直接引用或吸收。

**M-4 · 记忆路由没有家。**
需求 :85-92 的常驻清单包含"用户专属的记忆关注原则"，但七文件结构 :210-231 里没有它的文件——`Interaction.md` 只管沟通路由，`Sources.md` 管查证路由。记忆关注策略（"对这个用户什么值得记"）是需求 :17-23 立的核心问题域之一，落地时却没有载体。我方放在 `routing.md` 下半张表。统一阶段需要给它定个家。

### 轻

**L-1 · Google Drive 默认推荐与已实测的套餐限制相撞。**
需求 :145 "普通用户默认推荐 Google Drive"。已实测：ChatGPT 的 Drive synced connector 只给 Pro / Business / Enterprise，**Plus 只能提示时读、不监控文件夹**。"普通用户"恰恰最可能是 Plus。推荐本身可以留（需求 :148 也写了"必须在初始化时验证"），但应加一句已知限制，否则用户按默认走到一半才发现锚点对自己的主力端是半瞎的。

**L-2 · 同端包积压没有 supersede 规则。**
协议 :116 "每次倾倒创建新文件，不覆盖旧文件"是对的（不可变审计），但缺配套：同一端连续多次倾倒、前几次未被处理时，合并者应只取最新、旧包标记 superseded 后归档。否则日常自动化跑一个月，inbox 里堆三十个几乎相同的包，每轮合并都要重嚼。

**L-3 · 协议的 GitHub 目录结构写在通用章节里。**
协议 :51-75 仓库结构、:134-159 GH 系列测试都以 GitHub 为前提。这些属于 Alex 实例的验证方案（需求 :261 已明确锚点是实例选择），放协议通用正文里会让"锚点由用户选"的原则打折。建议标注为"锚点 = git 类后端时的参考实现"。

## 四、双方共同悬而未决的（谁的文档都没解干净）

**C-1 · 题库的"身份隔离"两边都只写了一半。**
我方 `audit.md` 有硬规则"tests 绝不喂给任何一端"，但 tests 本身也存在信源里，能读锚点的端物理上够得到它；Codex 侧连规则都没有（见 S-1）。真正需要的区分是**身份而非端**：同一个端，作为"主持体检者"必须读题库，作为"被测者"绝不能见题库。落地选项：题库放锚点内的独立目录并在装载指令里显式禁读；或题库根本不放共享锚点、只留在用户手里。需要一起定。

**C-2 · "平台细节写不写进技能"两边方向相反，各有道理。**
需求 :108 "不维护一份容易过时的平台连接方式清单，初始化时实测"；我方 `load.md` 写死了 2026-08 调研结论（带时效声明）。对方的原则可持续性更好，我方的做法省掉每个用户重查一遍的成本。可能的折中：技能正文只写**验证方法**，结论清单作为带日期的附件（`references/` 下单独一份，明确标注"会过期，以实测为准"），过期就整份换。

**C-3 · [分歧] 写不进锚点的端算什么。**
协议 :100 "既不能直接提交也不能通过分支或 PR 写入，则该端尚未完成知界接入"；需求 :122 措辞软化但立场未变（"初始化状态必须标记为未完成"）。我方立场：**读 / 写是两级门槛**——读得到就能受益（装 + 喂都成立），写不进只是进不了自动化、倾倒靠人搬且台账如实记。
实质影响场景：Gemini / 千问 / 豆包这类大概率没有任何锚点通道的端。Codex 方案下它们永远"接入未完成"，用户读到的是"知界不支持"；我方方案下它们降级可用。用户的真实端列表里恰好有这几个，这条值得当面裁。
