# 锚点适配路线图

> 状态：roadmap，不是当前技能的可执行说明
>
> 最近核对：2026-08-11
>
> 当前产品范围仍以 [`docs/新知界需求.md`](../新知界需求.md) 为准：MVP 只实现 GitHub 私有实例仓，Google Drive 是后续适配方向。

## 这份文件解决什么

知界的同步协议不应绑定某个存储产品，但不同锚点的发布、并发和版本恢复机制不能假装相同。

这份路线图负责：

- 固定所有锚点都必须满足的共同契约；
- 说明 GitHub 当前如何满足这份契约；
- 说明 Google Drive 的版本模型与 Git 有什么不同；
- 定义 Google Drive 进入技能运行包之前必须通过的验证。

它不改变当前 MVP 范围，也不代表 Google Drive 已经可用。

## 两套锚点指南怎样进入技能

未来支持第二种锚点时，后端专属内容按需加载，不把两套细节都塞进 `SKILL.md`：

```text
references/anchors/
├── github.md
└── google-drive.md
```

- `github.md`：当前支持后端的实际操作说明。
- `google-drive.md`：只有通过本文的准入验证后才创建并接入技能路由。
- 现有 `references/drive.md` 继续表示“驱动与控制面”，不改名；Google Drive 始终写全名。

`SKILL.md` 只读取 `config.md` 中选定的锚点类型，再加载对应指南。共同的倾倒格式、合并语义、权限门槛和原生记忆加载规则仍各自只保留一份，不在后端指南里复制。

## 所有锚点必须满足的共同契约

无论后端叫什么，都必须经过真实操作验证，而不是根据产品名称推断：

| 能力 | 验收含义 |
|---|---|
| 共同访问 | 所有纳入端都能访问同一个用户控制的私有位置 |
| 端内收件区写入 | 每端能创建自己的不可变倾倒包，不覆盖其他端的包 |
| 最新版本读取 | 每端能定位并读取当前已发布的完整知界资产 |
| 条件发布 | 协调端只能基于自己实际读取过的版本发布；基础版本变化时必须被拒绝或进入串行队列 |
| 一致版本 | 一次发布涉及的多个统一文件必须被识别为同一组结果，不能让读取者拿到半新半旧的一组文件 |
| 审计与恢复 | 能知道谁在何时发布了什么，并能回到一个完整的旧版本 |
| 权限边界 | 用户知道谁能读、谁能写；写入和读取失败不得伪装成成功 |

版本号只能帮助观察变化，不能单独满足条件发布。两个端都看到版本 5，再各自覆盖一次，仍可能丢掉其中一端的结果。

## GitHub 锚点指南：当前基线

GitHub 是当前 MVP 唯一实现的锚点。个人实例仓必须与知界技能代码仓分开，并设为私有。

### 版本与发布模型

| 知界概念 | GitHub 机制 |
|---|---|
| 当前统一版本 | 默认分支当前 commit hash |
| 不可变倾倒包 | 新文件进入端专属收件区，并由 commit 保存 |
| 一致的多文件版本 | 一次 commit 同时记录统一文件、消费清单和端状态 |
| 基础版本 | 协调开始时读取并记录的 `base_commit` |
| 条件发布 | 发布前比较远端默认分支是否仍指向 `base_commit`；不一致就重新拉取、合并和提交 |
| 审计 | commit 历史、作者、提交说明和 diff |
| 恢复 | 通过正常的新 commit 恢复旧内容，不自动改写历史或强制推送 |

### 初始化与日常运行

1. 新建用户私有实例仓，不复用技能代码仓。
2. 在 `config.md` 记录仓库、默认分支、发布路径和发布策略。
3. 每个端分别验证读取、创建倾倒文件、提交、推送和回读；只读连接不算完成接入。
4. 同步开始时先取得远端最新默认分支，并记录 `base_commit`。
5. 当前端先把自己的增量写进端专属收件区，再读取全部待处理包。
6. 合并完成后，把统一文件、消费清单和端状态作为一个提交候选。
7. 只有远端基础版本未变化时才能发布；变化后重新读取和合并，不强行覆盖。
8. 发布成功后，各端按自身使用节奏读取新版本并更新原生记忆。

“分支已 push”不自动等于“统一版本已发布”。是否发布由实例配置中的发布策略决定：默认分支条件直写、端专属分支经 PR 合并，或者由仓库自动化串行发布。一个实例只能选定并记录一种当前策略。

## Google Drive 的版本模型

### Drive 确实有版本历史

Google Drive 会为文件保留修订历史，也提供逐文件递增的 `version` 字段。Google Docs、Sheets、Slides 的版本历史与上传到 Drive 的普通文件（例如 Markdown、PDF、图片）的文件版本不是同一种机制。

对普通上传文件，未标记为 **Keep forever** 的旧版本通常保留 30 天；当未固定版本达到 100 个时，旧版本也可能更早被清理。固定版本占用存储空间，最多可固定 200 个。Drive API 返回的 Google 文档修订列表还可能省略较老的修订。

因此，Drive 的版本历史可以用于单个文件的查看和恢复，但不能默认承担知界的长期完整审计。

### 它不是 Git 式仓库版本

Drive 的版本属于单个文件：

- `profile.md` 有自己的版本；
- `now.md` 有自己的版本；
- `manifest.md` 也有自己的版本；
- 文件夹本身没有一个等价于 Git commit 的“整组文件版本”。

Drive API 的 batch 只是把多个独立请求装进一个 HTTP 请求。Google 明确说明服务器会把各部分当作独立请求处理，而且执行顺序不能依赖。它不是跨文件事务，也不能保证其中一部分失败时其余部分一起回滚。

由此得到几个约束：

- 不能用文件的最后修改时间裁决哪一组统一资产更新；
- 不能把每个文件各自的最新版本直接拼成“当前统一版本”；
- 不能因为看到了 Drive 版本记录，就声称并发发布已经安全；
- 文件名写日期或 `v2` 只提升可读性，不提供互斥和原子性。

### Google Drive 适配需要额外的发布层

Google Drive 进入知界前，必须验证一种能产生“完整统一版本”的发布方法。可以研究的方向包括：

- 把一次统一发布封装成单个不可变包，再用一个头指针指向当前包；
- 先写不可变版本目录，最后以可验证的条件写入更新唯一头指针；
- 让一个用户控制的自动化队列串行处理发布请求。

以上都是待验证方案，不是已经选定的实现。关键不在目录长什么样，而在于两个端同时发布时，系统能否让其中一个明确失败或排队，而不是静默覆盖。

## Google Drive 进入技能前的准入验证

只有下面各项都有实际证据时，才把 `google-drive.md` 放进运行中的技能并宣称支持：

- 所有目标端都能读取同一个 Drive 位置；
- 每个端都能向自己的收件区创建文件，而不只是搜索或读取已有文件；
- 当前端能取得可用于发布判断的基础版本或等价令牌；
- 两个端基于同一基础版本同时发布时，只能有一个成功，另一个会被拒绝或进入队列；
- 发布中途失败后，读者仍只能看到上一个完整版本或新的完整版本；
- 失败端能够重新读取、重新合并并重试；
- 可以从当前版本定位到同一轮发布产生的全部文件；
- 版本保留和恢复方式已经实测，不依赖可能自动清理的普通旧版本；
- 日常运行不要求用户反复复制粘贴文件；
- 每个端的权限、连接器限制和失败表现都记录在自身能力状态中。

只要条件发布或一致版本仍未解决，Google Drive 就只能作为只读来源、手工诊断通道或 roadmap 候选，不能作为知界的权威统一锚点。

## 仍待回答的问题

- 用普通 Markdown 文件、单一归档包，还是 Google 原生文档承载统一资产？
- 用户实际使用的各端连接能力是否暴露创建、更新、版本令牌和条件写入？
- 如果连接器不暴露条件写入，用户控制的串行发布服务应放在哪里？
- 哪些版本必须长期保留，如何避免依赖 Drive 自动清理的普通修订？
- Google Drive 适配是否仍能保持“用户说一次同步，其余步骤由技能完成”的交互承诺？

这些问题没有实测答案之前，不进入当前需求的验收条件。
