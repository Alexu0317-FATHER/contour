# 知界（Contour）产品需求文档

> 本文定义知界要解决的问题、产品目标、交互要求、功能需求和验收标准。
>
> 平台当前具备哪些能力，见 [`平台能力实测.md`](平台能力实测.md)；具体文件结构、执行步骤和技术规则，见 [`../skills/contour/`](../skills/contour/)；开发进度由 GitHub Issues 和 Project 管理。

## 1. 项目背景

同时使用多个 AI 的用户，通常会在 ChatGPT、Claude、Codex、Claude Code、VS Code、Zed 等不同环境中进行对话和工作。每一端只能看到自己接触过的内容，并按照各自的机制形成记忆。

这会产生三个直接问题：

1. **记忆割裂**：用户在一个端讲过的经历、偏好、能力和当前处境，换到另一个端后需要重新解释。
2. **理解片面**：不同端分别看见用户的不同侧面，任何单一端都可能据此形成不完整甚至互相矛盾的判断。
3. **使用方式不一致**：各端不知道在不同场景下应调用哪些用户信息，也不知道应当采用怎样的沟通方式。

例如，一个 AI 可能了解用户的小说创作经历，另一个 AI 了解用户的评论写作经历。两边都知道用户会写作，但都无法独立形成完整的能力判断。知界需要把这些分散的信息合并起来，再让各端逐渐获得更完整的理解。

## 2. 产品目标

知界的目标是：**让多个 AI 端对同一用户的理解随着持续使用逐渐趋同，降低用户换端时反复解释自己的成本。**

知界通过一个持续循环实现这一目标：

1. 从各端取得该端当前能够提供的用户记忆和相关信息；
2. 保留来源，对信息进行去重、合并、分类、更新和冲突处理；
3. 把整理后的结果按各端能够使用的方式送回；
4. 在后续使用中继续取得新增信息，重复以上过程。

AI 的记忆调用具有渐进性。一次导出不一定包含该端掌握的全部内容，因此知界不把首次同步视为完整终点，而是依靠多轮积累，让原本分散的信息逐步在各端之间流动。

### 2.1 预期结果

- 用户切换 AI 端时，不再需要反复说明已经被其他端了解的稳定背景。
- 不同端掌握的互补信息能够合并成更完整的用户画像。
- 已经过期、被更正或互相冲突的信息不会被静默混在一起。
- 各端能够根据当前场景调用相关信息，而不是每次加载全部档案。
- 用户能够查看、修改、迁移和追溯自己的统一记忆档案。

## 3. 目标用户与使用场景

### 3.1 目标用户

知界面向同时使用两个或更多 AI 端，并希望这些 AI 对自己形成较一致理解的用户。

用户可能：

- 同时使用网页端、桌面端和本地开发工具；
- 因配额、模型能力或任务类型频繁切换 AI；
- 已经维护个人画像、沟通偏好或其他记忆文件；
- 没有任何现成档案，只依赖各端已经形成的记忆；
- 希望个人资料由自己掌控，而不是再交给一个新的托管记忆服务。

### 3.2 核心使用场景

- 第一次建立知界，并纳入两个或更多 AI 端；
- 在已有个人画像文件的基础上初始化；
- 将新端加入现有知界；
- 定期取得各端新增或修正的记忆并完成同步；
- 处理不同端之间的冲突、过期信息和互补视角；
- 查看本轮同步完成到哪一步，以及哪些端尚未取得更新；
- 更正或撤回统一档案中的内容；
- 检查各端对用户的理解是否正在趋同。

## 4. 成功标准

知界满足以下条件时，才算实现产品目标：

1. **跨端信息能够流动**：至少两个不同 AI 端的信息可以进入同一份统一档案，并重新提供给已纳入端使用。
2. **重复解释明显减少**：用户在新会话或另一个端中，不需要反复说明已经被其他端了解的稳定背景。
3. **多端理解渐进收敛**：经过多轮同步，各端在相同场景下对用户的关键判断和沟通方式趋于一致，而不是持续积累新的矛盾。
4. **统一档案始终由用户控制**：用户能够查看、更正、撤回、追溯和迁移自己的资料。
5. **日常使用不依赖长期人工搬运**：反复复制大段内容不是默认操作方式。

## 5. 产品范围

当前版本解决两个或更多 AI 端之间的用户记忆取得、整理和送回，并维护一份用户可控、可追溯、可迁移的统一档案。没有现成个人档案的用户可以从零开始；已有个人画像、记忆导出或其他资料的用户可以将其作为额外来源。

当前优先覆盖 ChatGPT、Claude 系列产品和本地 AI 开发环境。具体已验证端组合以 [`平台能力实测.md`](平台能力实测.md) 和对应验收结果为准。

当前版本不要求所有平台具备相同的原生记忆能力，也不要求实现完全自动同步。后续范围见第 10 节 Roadmap。

## 6. 核心产品流程

```text
各端已有的用户记忆和用户提供的资料
                    ↓
        取得本轮能够访问的信息
                    ↓
       去重、合并、分类、处理冲突
                    ↓
          形成用户可审查的统一档案
                    ↓
      按各端适合的方式送回并加载
                    ↓
       后续使用中继续取得新增信息
                    ↺
```

| 阶段 | 目的 | 用户应看到的结果 |
|---|---|---|
| 取得 | 收集各端当前能提供的记忆和相关资料 | 取得了哪些端、哪些范围，哪些内容暂时无法取得 |
| 整理 | 将分散内容变成可信、可使用的统一档案 | 新增、合并、冲突、待确认和被更正的内容 |
| 送回 | 让各端在当前上下文或自身记忆机制中使用整理结果 | 哪些端已收到、已读取，哪些仍待处理 |

## 7. 功能需求

### 7.1 初始化与范围确认

用户通过自然语言或所在端的显式技能入口发起操作。知界根据当前请求、已有配置和实际同步记录判断需要完成的工作；已知信息直接复用，只询问影响本轮操作的必要缺项，不要求用户按固定顺序回答整套问题。

首次使用需要明确纳入的 AI 端、已有资料、授权读取范围、档案保存位置和送回范围。由 Skill 引导补齐并保存配置，后续会话继续使用。用户没有现成个人档案也可以开始。

已有知界档案时继续使用原档案。临时访问失败不得清除已有配置或改变已有初始化状态；受影响的操作应如实向用户说明。

已有个人画像只会让初始化多一个上游来源，不改变“取得各端信息—整理—送回”的整体流程。系统需要在初始化时将该文件与各端信息一起比较，而不是直接把它当成最终结果。

如果用户没有现成档案，知界应根据实际取得的信息建立第一版。信息不足时可以形成较薄的初始档案，但不能通过长问卷或一次性推断虚构完整画像。

至少取得两个不同端的有效输入后，才能把结果称为跨端基线。只有一个端时，可以保存准备结果，但需要明确说明尚未形成跨端统一档案。

### 7.2 从各端取得信息

知界需要支持以下来源：

- 各端能够导出的原生记忆；
- 用户明确指定的历史会话或项目内容；
- 本地端可访问的记忆文件；
- 用户已有的个人画像、正式数据导出或其他授权资料；
- 后续使用中新增、更正、失效或撤回的信息。

每次取得信息时都要记录来源和范围。AI 一次没有输出某条记忆，不代表该端从未保存它；一次重新输出某条旧信息，也不代表它是本轮新形成的内容。

当端内记忆无法一次完整导出时，知界允许通过多轮同步逐步补充。产品不能把单次输出包装成该端全部记忆的完整副本。

### 7.3 整理统一档案

整理过程需要满足以下要求：

- 合并重复内容，但保留其来源；
- 识别上次由知界送回、这次又被原样带回的内容，避免把它当成新的独立证据；
- 将可以同时成立的不同视角合并为更完整的结论；
- 对有明确时间或更正依据的信息更新旧状态；
- 对无法判断的矛盾并列保留，交给用户确认；
- 区分稳定画像、近期状态、沟通策略、信息来源和原始依据；
- 为重要结论保留来源，使用户能够追溯其形成过程；
- 没有有效变化时不制造新的档案版本。

统一档案至少需要承载以下内容：

| 内容 | 作用 |
|---|---|
| 稳定画像 | 保存较长期成立的能力、偏好、判断方式和重要背景 |
| 近期状态 | 保存可能变化的目标、精力、活跃事项和生活状态 |
| 沟通与记忆策略 | 告诉 AI 在不同场景下怎样沟通、哪些信息值得留意 |
| 信息来源 | 告诉 AI 遇到最新进度或具体事实时去哪里查证 |
| 依据与历史 | 保存结论来源、更正、取代和撤回关系 |

具体文件拆分和写作格式属于 Skill 的实现设计，不在本文重复规定。

### 7.4 按需提供记忆

统一档案不能作为一份长文档在每轮对话中全文读取。知界需要将信息分成不同用途和变化速度的部分，并让 AI 根据当前场景逐步读取：

- 每轮都需要的内容保持简短，只提供沟通原则、记忆关注方向和读取入口；
- 稳定背景只在需要深入理解用户时读取；
- 近期状态只在问题涉及当前情况时读取；
- 原始依据只在需要核对来源或处理冲突时读取；
- 最新项目进度、任务和日历等事实仍从对应的权威来源查询。

按需读取的目标不是减少档案内容，而是让完整档案在不同场景下以合适的部分进入上下文。

### 7.5 将整理结果送回各端

知界应根据目标端当前可用能力，以其能够实际读取的方式提供整理结果。

送回过程需要：

- 为不同端准备其能够读取的内容形式；
- 说明这些材料代表当前统一结果，并指出需要覆盖的旧信息；
- 让目标端在当前会话中实际读取，而不是只完成文件上传；
- 无法观察原生记忆变化时，不把模型口头表示“记住了”当成确认。

送回结果统一使用 7.8 定义的状态报告。无法观察平台后台记忆变化时，不以模型口头表示“记住了”作为确认依据。

知界追求的是各端后续表现逐渐趋同，不要求各端保存相同措辞或相同数量的条目。

### 7.6 日常同步

用户可以从当前正在使用的端发起同步，不需要先判断这次应当执行哪一个内部步骤。

日常同步沿用第 6 节的“取得—整理—送回”流程，并遵守以下要求：

- 在接收新结果前，先取得来源端尚未整理的新增或修正信息；
- 其他端不需要同时在线，未在场的端可以在下次自然使用时取得最新结果；
- 允许部分完成，并按照 7.8 的状态分别报告实际结果和待处理事项；
- 中断后从已有结果继续，不要求重新执行已完成步骤。

### 7.7 新增端

用户将新端加入知界时，知界应在当前可用能力范围内：

- 取得该端能够提供的首次输入；
- 将其与当前统一档案比较并整理；
- 向该端提供当前统一结果；
- 向用户说明本轮未完成或无法确认的部分。

### 7.8 状态与结果报告

知界不能只给出笼统的“同步成功”或“同步失败”。至少需要区分：

| 状态 | 回答的问题 |
|---|---|
| 信息已取得 | 是否真的从来源端拿到了本轮内容 |
| 已完成整理 | 内容是否已经影响统一档案 |
| 已保存版本 | 本轮结果是否已经形成可追溯版本 |
| 已准备送回 | 是否已经为目标端准备好材料 |
| 已送达 | 文件或消息是否真正到达目标端 |
| 当前会话已读取 | 目标端是否已经在当前上下文中使用材料 |
| 平台记忆状态 | 是否有证据表明原生记忆已更新；没有时明确写不可观察 |

部分完成是合法结果。例如，可以报告“Claude 的信息已完成整理，ChatGPT 的材料已准备但尚未送达”，而不是把整轮压缩成失败。

### 7.9 更正、撤回与冲突确认

用户需要能够：

- 更正已经过期或错误的信息；
- 指定新内容取代旧内容；
- 要求某条信息停止继续使用；
- 查看无法自动判断的冲突并作出确认；
- 了解已经进入版本历史或平台后台的信息是否能够彻底删除。

知界只能承诺停止在后续统一档案中使用被撤回内容。涉及历史版本、旧副本或平台已经吸收的记忆时，需要说明实际可删除范围，不能承诺无法验证的彻底清除。

### 7.10 一致性检查

知界需要提供独立于日常同步的检查方式，用于观察多个端在相同场景下是否表现出接近的用户理解和沟通方式。

检查重点是判断与行为，不是要求各端背诵同一段档案。检查结果应帮助发现：

- 哪类用户信息只在部分端可用；
- 哪类场景仍存在明显沟通差异；
- 哪些旧信息仍在影响判断；
- 问题来自取得、整理、送回还是端内调用。

一致性检查用于评估和改进，不作为每次日常同步的强制步骤。

## 8. 非功能需求

### 8.1 隐私与授权

- 未经用户明确确认，不读取跨会话内容，不上传、发送或保存私人资料。
- 默认使用最小读取范围；扩大到整个项目、账号历史或目录前再次确认。
- 不要求用户提供密码、会话 Cookie 或其他可复用凭据。
- 上传或发送前，需要让用户知道目标端、目标位置和内容范围。
- 随技能分发的代码、模板和示例与用户的私人记忆资料必须分开。

### 8.2 数据主权与可迁移性

- 统一档案由用户控制，并使用用户可查看和修改的格式保存。
- 用户能够知道资料存放位置，并能够迁移或备份。
- 重要变化需要保留版本记录，支持查看差异和恢复。
- 更换某个 AI 平台不应导致统一档案一并丢失。

### 8.3 可靠性

- 同一时间不能有多个程序互相覆盖统一档案。
- 中途失败不能把未完成结果报告为成功，也不能破坏上一份可用版本。
- 重试后不能重复处理同一份输入。
- 每次更新后需要核对实际保存的结果，而不是只依赖执行过程中的口头判断。

具体如何避免并发覆盖、恢复失败和验证文件，属于 Skill 的技术设计。

### 8.4 平台适应性

- 各端当前可用能力及其验证依据由 [`平台能力实测.md`](平台能力实测.md)维护。

### 8.5 可理解性

- 用户看到的流程和报告使用日常语言，不要求理解数据库、Git 或并发控制术语。
- 技术错误需要转化为用户可以行动的说明：发生了什么、哪些结果仍然有效、下一步需要什么。

## 9. MVP 验收标准

当前版本至少需要通过以下验收用例：

| 编号 | 验收场景 | 操作 | 通过条件 |
|---|---|---|---|
| AC-01 | 用户没有已有档案 | 纳入两个端并完成初始化 | 系统基于实际取得的信息建立第一版跨端统一档案，不要求用户先填写完整画像 |
| AC-02 | 用户已有个人画像或记忆文件 | 将已有档案与两个端的输入共同用于初始化 | 已有档案被作为一个来源参与比较和整理，而不是直接成为最终结果 |
| AC-03 | 两个端提供部分重复、部分互补的信息 | 建立跨端基线 | 重复信息只形成一条结论并保留多个来源；互补信息被合并且不互相覆盖 |
| AC-04 | 两个来源提供无法自动判断的矛盾信息 | 执行整理 | 冲突被并列保留并标记为待用户确认，系统不擅自选择其一 |
| AC-05 | 输入包含稳定画像、近期状态、沟通策略、信息来源和原始依据 | 更新统一档案 | 五类内容能够分开保存和读取，重要结论可以追溯到来源 |
| AC-06 | 当前问题只涉及近期状态 | 目标端按需读取统一档案 | 目标端无需加载完整档案即可取得相关内容；无关的稳定画像和原始依据不进入当前上下文 |
| AC-07 | 整理结果需要送回已纳入端 | 执行送回 | 系统分别报告已准备送回、已送达、当前会话已读取和平台记忆状态，不以文件上传或模型口头确认代替其他状态 |
| AC-08 | 某个端或某一步骤执行失败 | 继续完成其余可执行步骤并在恢复后重试 | 其他已完成结果仍然有效；上一份可用版本未被破坏；恢复后不会重复处理同一份输入 |
| AC-09 | 一轮同步只有部分步骤完成 | 查看结果报告 | 用户能够看到本轮范围、各步骤状态、实际变化、失败原因和待办事项，系统不把部分完成压缩成整体失败 |
| AC-10 | 用户更正、取代或撤回一条信息 | 更新统一档案 | 后续档案使用新状态；历史关系可追溯；无法从旧副本或平台记忆彻底删除的部分被如实说明 |
| AC-11 | 更新产生有效变化 | 保存、查看差异并恢复上一版本 | 变化形成可追溯版本；用户能够查看差异、恢复和迁移档案；没有有效变化时不产生新版本 |
| AC-12 | 检查技能分发内容 | 对比分发代码、模板、示例与用户档案 | 私人记忆资料没有进入随技能分发的代码、模板或示例 |

## 10. Roadmap

### 10.1 平台能力更新跟踪

定期获取 OpenAI 与 Anthropic 的官方 Changelog、Release Notes 和功能更新文章，识别可能影响以下能力的变化：

- 记忆读取与导出；
- 会话和 Project 访问；
- 文件、连接器与 MCP 能力；
- Skill 的安装、调用和上下文加载方式；
- 自动化、浏览器操作和跨应用交互；
- 不同系统、账号等级和产品入口之间的差异。

发现更新后，先更新待验证项并完成实测。

### 10.2 后续能力

- 更多 AI 端和本地开发环境；
- 更多统一档案存储方式；
- 用户主动开启的定时或事件触发同步；
- 更成熟的一致性评估与偏差诊断；
- 降低网页端送回过程中的人工操作；
- 在平台开放新接口后，减少对界面操作和中间文件的依赖。

## 11. 文档职责与维护规则

| 文档 | 职责 |
|---|---|
| 本文 | 产品目标、用户场景、功能需求和验收标准 |
| [`平台能力实测.md`](平台能力实测.md) | 各端当前能做什么，以及结论的日期和证据 |
| [`../skills/contour/`](../skills/contour/) | 具体执行流程、文件结构、数据格式和技术规则 |
| [`NOTES.local.md`](NOTES.local.md) | 当前交接状态 |
| [`roadmap/`](roadmap/) | 不属于当前版本的后续能力 |
| GitHub Issues / Project | 开发任务、依赖、进度和验收证据 |
| [`../README.md`](../README.md) / [`../README.zh.md`](../README.zh.md) | 面向技能使用者介绍已经可用的能力 |

同一项内容只保留一个权威位置。需求、平台事实、实现规则和当前进度不在多个文件中重复维护。

官方公告只用于触发复审，不直接自动改写 Skill，也不自动改变产品支持范围。具体端组合只有完成对应的端到端验证后，才能在 README 中标记为支持；README 不把需求目标或单步测试写成已实现功能。
