# 知界 Contour

一个人同时在用 Claude Code、Codex、Claude.ai、Claude Desktop、ChatGPT……每一端都对他有一份记忆，每一份都残缺、都不一样。换端等于重新教一遍——记忆成了平台转移成本。而且没有任何一端对「该怎么跟这个人说话」有可携带的定义。

知界解决这个。

---

## 零、被触发不等于可以动手

**这是最重要的一条，先看它。**

这个技能的 description 故意写得宽——用户抱怨"这个 AI 根本不了解我"的时候，他往往并不知道存在"跨端记忆同步"这回事，需要被识别出来。但宽的发现范围绝不意味着宽的执行权限：

> **description 匹配上 ≠ 立即执行同步。**

分两档，**读实例仓属于第二档，不属于第一档**：

| | 语义软命中<br>（他抱怨"这个 AI 根本不了解我"） | 明确要求<br>（"同步知界" / "看下知界状态" / 回答了同意） |
|---|---|---|
| 解释知界能解决什么、诊断他的处境 | ✅ | ✅ |
| 当前任务结束后问一句"要现在更新知界吗" | ✅ 每轮最多一次 | —— |
| **读实例仓 / 调 GitHub 连接器** | ❌ | ✅ |
| 倾倒、写文件、提交、合并、加载 | ❌ | ✅ |

**软命中时连读都不许。** 用户随口抱怨一句，技能就去访问他的私有仓库——即便只是读，那也是一次他没要求的、指向私人数据的网络调用，可能还会弹授权。**没读到就没读到，先问。**

反过来，他明确要状态或要同步时，读取本身就是他要的动作，不必再确认一次。

**未获确认时保持零外部操作。** 用户明确表示过：无法接受技能在未经确认时突然执行倾倒、commit、push 或合并——技术上的后台运行不等于用户感知上的无感。

## 三条不变量

流程覆盖不到的情况你会遇到，那时靠这三条自己判断。

### 一、单一信源：一个权威锚点，读之前必须追平，写入必须条件化

副本一旦有了独立的写入权威，就各自演化、版本分裂、一致性丧失——那这个技能就没有存在意义了，因为「各端表现趋同」本身就是它要满足的需求。

但**副本本身不是问题**，git clone 就是副本。纪律是三条：

> **只有一个权威锚点。**
> **任何一端读之前，必须先追平到它。**
> **写回必须是条件写入——基础版本被人动过就得重来。**

**"一个锚点"说的是地方，不是端。** 多个端都可以临时接任协调、往锚点写；被串行化的是**单次发布**，不是写入资格。固定协调端在这里是反模式——那一端配额用完或没开机，整个循环就停摆，而"配额用完要换端"本来就是用户需要这个技能的起因之一。

第三条是最容易漏的：版本号只提供**观察**，不提供**互斥**。两个端都读到 v5、都确认"仍是 v5"、然后分别覆盖同一份文件，最后写的仍然会静默盖掉前一个。所以**锚点必须提供可验证的条件写入**，这是锚点准入的第三条能力，机制见 `references/protocol.md`。

由此还引出一个必须分清的差别：**「能确定性读到本地那一份」和「本地那一份是最新的」是两个不同的保证。** 混用它们会让人以为文件导入白送了新鲜度，其实没有（见 `references/load.md`）。

**当前 MVP 的锚点是新建的 GitHub 私有实例仓。** 抽象接口是四条能力（读得到 / 写得进自己的收件区 / 读得到最新统一版本 / 条件写入统一文件），将来适配别的后端时实现这四条即可。

**实例仓必须和技能代码仓分开。** 实例仓装的是倾倒物——健康、家庭、职业困境。技能仓是要公开分发的代码。混在一起，第一次 push 就把私事推到了一个有公开发布史的地方。

### 二、知界不持有记忆，知界刷新记忆

每一端本来就有原生记忆系统在自动工作（ChatGPT 记忆、Claude.ai 记忆、`CLAUDE.md`、`AGENTS.md`、用户自建的记忆目录）。知界不跟它们抢活，也不取代它们。**各端原生记忆是信源的下游缓存，写入权威始终在信源。**

知界做两件事：

- **装**：把路由表放进模型可见的常驻上下文，告诉这一端什么场景用什么策略、什么信息值得留
- **喂**：整合完之后，把统一结果送到各端面前，让它自己按自己的机制归类吸收

**喂这一步是闭环的最后一段，没有它整个技能不成立。** 倾倒把分歧收上来，喂把共识发下去——只倾倒不喂，你每个月认真合并出一份漂亮档案，五个端该怎么错还怎么错。

但要清楚边界：**具体存什么、怎么压缩，是原生系统的自主权。** 知界给的是材料和关注方向，不是指令；不生成强制保存清单，不要求模型绕过平台规则。**而且模型口头说"我记住了"不算验证**——那只证明材料送达，真验证要开新会话看它还在不在（见 `references/probe.md`）。

### 三、收敛的对象是表现，不是记忆内容

各端记忆永远不会字节级一致，也不需要。需要一致的是**同一个场景下各端给出同类反应**——用户的痛点是"换端要重新解释自己"，痛的是行为不是存储。所以不要向用户承诺"各端记忆一样"，那是物理上做不到的承诺。

而且收敛不是自然规律，这个循环既能收敛也能发散。**发散的机制很具体：只加不删。** 各端原生记忆是追加式的，旧的错条目不会因为你喂了新的就消失——"他在找工作"和"他入职了"并排躺着，召回哪条看运气，倾倒出来更乱，越跑越糟。所以喂的时候必须显式要求覆盖，不能只交新的。

**真正保证收敛的是体检。** 不测，你没有任何理由相信它在往一起走而不是在原地转圈。

## 实例资产

```text
config.md      稳定实例配置：锚点位置、纳入端、权限边界、发布路径
profile.md     慢变画像：价值排序、判断路径、能力画像、负向约束
now.md         快变用户状态：活跃项目、目标进度、健康精力、家庭动态
routing.md     ★常驻★ 沟通路由 + 记忆关注策略
sources.md     去哪拿答案：动态信源路由 + 知识资产路由
evidence.md    证据仓：按"支持哪条结论"组织，含取代与撤回关系
tests.md       隐藏题库与体检记录，不进被测端上下文
state/endpoints/<id>.md   每端能力与游标，只由该端自己写
dumps/         inbox（各端收件区）+ processed/manifest.md（消费记录）
review/        冲突、待确认、撤回、失败恢复
```

完整结构与写入者划分见 `references/protocol.md`，写作规范见 `references/schema.md`，空白模板在 `assets/templates/`。

**文件名不绑用户名。** 技能是通用的——是 `profile.md`，不是 `AlexProfile.md`。

### 路由表管三件不同的事

| | 回答什么 | 不回答什么 |
|---|---|---|
| `routing.md` | 该怎么跟这个人说话；对他来说什么值得记 | 去哪拿答案 |
| `sources.md` 动态信源区 | 涉及项目进度、任务、日历、外部事实时去哪里查证 | 怎么说话 |
| `sources.md` 知识资产区 | 这件事我们已经沉淀过一份东西，在哪 | 那份东西里写了什么 |

**动态信源区不是可选项。** 没有它，知界越成功越危险——模型会用越来越自信的语气复述一份过期但已经传遍各端的 `now.md`。统一记忆可以当近期状态的缓存，**不能替代快变信息的权威来源**。

**知识资产区只登记具有跨会话复用信号的外部产出物，并维护其唯一指针；不接管资产内容或写回行为。** 准入、更新与待复核规则见 `references/consolidate.md` 第五节。

### 只有 `routing.md` 进常驻

其余全部走指针、按需读取——全塞进常驻上下文会挤掉用户真正要干的活，而且档案越完整挤得越狠，做得越好越难用。

注意是**全文**不是指针。写一句"会话开始时读 `routing.md`"，等于把一个动作交给模型自觉执行，那是概率性的；用户第一句是"修这个 bug"，模型直奔 bug，路由表当场蒸发。**指令位里确定性生效的只有它自己的字节。** 各端具体怎么装见 `references/load.md`。

## 唯一同步状态机

用户只需要触发一次。当前端在**取得确认之后**按下面的顺序跑，能跑到哪一步跑到哪一步：

1. **读配置和本端状态**，实测当前端对锚点的实际能力（不接受口头声称）
2. **先保护本端增量**：在加载任何新统一材料之前，先生成本端倾倒包。没有变化就不创建包
3. **提交包到本端收件区**。失败就留明确的未提交状态，**不许伪造成功回执**
4. **读取**当前统一版本、全部未消费的包、消费 manifest
5. **能力够就临时接任协调**，把待处理的包合并；不够就跳过发布，但仍然可以读已发布的最新结果
6. **发布前验证基础版本**。被别人抢先就重新读取、重新合并，**不许强行覆盖**
7. **让当前端读取** `routing.md` 与本轮变化，按需读其他层；向原生记忆说明用途和关注方向
8. **只更新当前端自己的状态文件**，报告本轮完成、跳过、失败的动作

第 2 步在第 4 步之前，这个顺序是硬的：**先倒出去的内容保证不含本轮刚读进来的统一版本**，从源头压住回声。

**协调者按能力产生，不按产品身份指定。** 不要设固定协调端——那一端没开机、配额用完、或者用户那天没打开它，整个循环就停摆；而"配额用完了要换端"本来就是用户需要这个技能的起因之一。

本地钩子、平台自动化都只能调用这套状态机的安全子步骤，**不能另造一套定时同步规则**（见 `references/drive.md`）。

## 判断用户在哪一步

**过了确认门槛之后**，第一个动作是读实例仓，不是问用户——他上次干这事可能是三周前，答不上来或者答错。

（还没过门槛时不许读，见第零节。这一节讲的是拿到许可之后怎么定位。）

| 读到什么 | 走哪条 |
|---|---|
| 实例仓不存在 / 接不上 | **冷启动**（下一节），第一件事是定锚点 |
| 存在，但 `state/endpoints/` 里没有这一端 | **新端接入** → `references/load.md` + `references/protocol.md` 的通道验证 |
| 本端游标落后于当前统一版本 | **追平**：拉最新，喂原生记忆 |
| inbox 里有未消费的包 | **整合** → `references/consolidate.md` |
| 用户刚在这一端聊完，要交作业 | **倾倒** → `references/dump.md` |
| 没有体检记录，或距上次已过几轮循环 | **体检** → `references/audit.md` |

读不出来再问用户，别猜。**这一节是"用户只需说一句话"的前提**——状态从实例仓推，他就不用交代上下文。

## 冷启动

### 倾倒是无条件的第一步——即便用户已经有一份档案

如果他手上那份档案是准的、各端也一致，他不会需要这个技能。**已有档案是原料之一，不是起点。**

而且它很可能已经馊了。一份写于一年前的 profile 会用完全的自信告诉你用户在用什么工具、孩子几岁、目标是什么——全部过期，而且没有任何一条带时间戳让你察觉。这是这类档案最常见的死法，也正是 `now.md` 分层和时效标记存在的原因。

**先倾倒，再看已有档案，最后才写。** 把已有档案当成"某一端的倾倒物"平等参与冲突消解，不给它特权。

### 步骤

**1. 摸清战场。** 问用户在用哪些端、哪些是主力。这份清单决定后面每一步各跑几遍。

**2. 定锚点并验证。** 先问用户是否已有**专用于知界数据**的 GitHub 私仓：有就验证隐私、权限和目录结构后使用；没有 GitHub 账号或专用仓库，就引导完成注册和授权，并在获得权限后代为创建私仓与初始化结构。登录、验证码和授权确认由用户本人完成，其余能代办的不要甩给用户。**不要复用技能代码仓或装有其他项目的仓库。** 然后逐端验证实际接入路径；公开文档、官方源码和工具清单能确认的能力由 Agent 先查，只有当前账号权限、OAuth 和黑盒行为才让用户参与实测。**能看见仓库不等于能写进去**；**能提交也不等于能当协调者**，还要满足协议规定的安全发布条件。

选完把位置、纳入端、发布路径写进 `config.md`。

**3. 每个纳入端跑一次基线倾倒。** 手法见 `references/dump.md`。**不许跳过**——没有真实倾倒物就去写 `profile.md`，等于让模型拿当前这一次会话瞎编一个人，那正是档案变馊的机制。

暂时接不上的端标记为"待完成基线倾倒"。在全部完成之前，产出的画像是**暂定版本**，不能对用户声称已经实现跨端一致。

**倾倒结果为空也是合法结果。** 用户既没有画像、当前端也没有可倾倒的原生记忆时，只建立一份可信但可以很薄的初始资产：他明确确认的身份、目标、授权来源、当前未知项。**不要用长问卷或单次推断伪造一份完整人格画像。**

**第一版发布有一道硬门槛：至少两个不同的已登记端各提交一份格式合规的 baseline。** 两份来自同一 `endpoint-id` 的包只算一端；已有 profile、记忆导出或其他旧资产都不算第二端。空内容的 baseline 只要格式合规也算——它证明那一端当前确实没有可输出的记忆。

先跑 `python scripts/validate_dump.py --cold-start-ready <实例仓路径>`。门槛没过时，只保存 `config.md`、端状态和未消费的倾倒包；**不进入第 4 步，不生成或发布 `profile.md`、`routing.md`、`sources.md`、`evidence.md`、`tests.md`，也不把任何包写进消费 manifest。**

这条只拦**第一次**统一发布。第一版已经建立后，日常只有一个端交来 incremental 也可以立刻合并——那是在已有的多端基底上更新，不必等另一个端一起交作业。

**4. 整合。** 规则见 `references/consolidate.md`。三条最要紧的：

- **每条进 `profile.md` 的结论都必须能追到 `evidence.md` 里的出处。** 追不到的不是结论，是猜测。这条是整个档案可信度的地基
- **冲突不许偷偷选一个。** 有条目级时间依据的按依据裁；没有就并列写下来进待确认。替用户做无声的裁决，是在偷他的数据主权
- **每条都带"何时为真"。** 没有时效标记的档案会在一年后以满分自信撒谎

**5. 建 `routing.md` 和 `sources.md`。** 这几张表是知界区别于"记忆导出工具"的地方，也是最容易做得敷衍的一步——详见 `references/consolidate.md`。要点：每条都要写清"为什么"，因为真实场景永远超出你列的清单，模型得靠"为什么"泛化。

`sources.md` 知识资产区**允许为空**：用户没有存到会话之外的产出物，这一区就空着，不要为了填满去把普通回答登记成资产。

**6. 加载：先装，再喂。** 见 `references/load.md`。**两件事都要做。** 装是把路由表接进常驻上下文，喂是把整合结论送进各端自己的记忆系统——后者才是"各端表现趋同"真正发生的地方。硬规矩：**`tests.md` 绝不进被测端的上下文**，进了等于把答案给考生。

**7. 跑接入必测，出一版 `tests.md`，跑第一次体检。** 见 `references/probe.md` 和 `references/audit.md`。第一次体检的结果就是基线。

### 冷启动的验收清单

分两档，别混：**能不能开始用** ≠ **冷启动完成了**。

**最小可用**（达到就能开始日常使用）：

- [ ] **至少两个不同的已登记端**能在不公开仓库的前提下各自提交格式合规的基线倾倒包并回读；纯网页组合只有在每个端的实际写入路径都已经验证后才算，不能因平台理论上支持写工具就提前宣称成立
- [ ] 至少一个端通过了多文件原子提交，具备协调资格
- [ ] 用户没有被要求复制粘贴倾倒内容
- [ ] 统一版本已发布，参与端读到的是同一版本

**冷启动完成**（在最小可用之上，还要）：

- [ ] **每一个已登记的端都完成了基线倾倒**，一个不缺
- [ ] 协调者能区分原生记忆、现场推断、外部资料和知界回声
- [ ] 快变问题能按 `sources.md` 查权威来源，而不是复述旧摘要
- [ ] 无法自动解决的冲突进了 `review/`，没有被静默覆盖

**差别不是形式主义。** 只倒了两个端就宣布完成，剩下三个端的独有记忆一条都没进来——**而"每端只见过他的一部分"正是用户来找这个技能的原因**，漏掉的恰好是这个技能存在的理由。

所以还有端没倒时：产出的画像是**暂定版本**，要在 `config.md` 里标出哪些端"待完成基线倾倒"，**并且明确告诉用户还没实现跨端一致**。

**验收不要求各端逐条复述同一份记忆。** 能观察到互补信息缺口缩小就够了。

---

## 分寸

**这是用户的档案，不是你对用户的观察报告。** 你会在倾倒物里读到很多东西——健康状况、家庭矛盾、职业困境、他对自己的负面判断。整合时保持中性记述，不加评价、不作诊断、不替他升华。

**不确定就标不确定。** 一条标为"待确认"的信息，比一条听起来笃定但其实是你推的信息有价值得多。后者会被下游每一端当成事实反复使用，错误会复利。

**倾倒物里有敏感信息是常态。** 别自作主张往公开的地方放。锚点准入里明确问一句：这个位置是私有的吗？

**删除是用户的权利，不是你的判断题。** 不要主动评估什么算"敏感"该删——只在用户明确提出时执行更正或撤回，规则见 `references/consolidate.md`。
