# 驱动 · 控制面

谁在什么时候让知界跑起来，以及跑之前必须先过哪道门。

数据面（包长什么样、发布怎么保证原子）在 `protocol.md`，语义面（合并怎么判）在 `consolidate.md`。

---

## 一、确认门槛

**默认：技能被触发后，不经用户明确同意，不做任何外部操作。**

外部操作指：写实例仓文件、提交、推送、合并发布、向各端原生记忆写入、跑倾倒。读实例仓做诊断不算。

### 三档触发，权限完全不同

| 触发形式 | 允许做什么 |
|---|---|
| **description 匹配**（用户抱怨"这个 AI 根本不了解我"之类） | 诊断 + 解释 + **最多问一次**。零外部操作 |
| **模型自己察觉本轮有值得同步的信息** | 在**当前任务结束后**问一句。零外部操作 |
| **用户明确说"同步知界" / "倾倒一下" / 回答同意** | 进入完整状态机 |

前两档合并成同一句问法：

> 本轮似乎有值得同步的信息，要现在更新知界吗？

**一轮对话最多问一次。** 用户说不要之后，本次会话不再问。

### 为什么门槛设在这里

用户明确表示过：无法接受技能在未经确认时突然执行倾倒、commit、push 或合并。**技术上的后台运行不等于用户感知上的无感**——他打开一个会话是要干活的，不是来等基础设施跑完的。

而且这件事本身也不适合无声进行：同步会改动他的个人档案，会向远端提交，会影响之后五个端对他的理解。这类动作要么他知情，要么不该发生。

### 那一问是 best-effort，必须写明

**"察觉到本轮有值得同步的信息"这件事是概率性的。** 它就是让模型自觉执行一个元任务，会时不时静默不触发——这是模型的固有行为，不是可以修好的 bug。

**这在 MVP 里是可接受的，因为有保底路径**：用户随时可以自己说"同步知界"。漏一次提醒只是延迟，不是丢失。

但不要向用户承诺它每次都会提醒。文档里、对话里都说清楚它是尽力而为，否则以后会被当成故障报上来。

### 驱动这一问的正是常驻的记忆关注策略

`routing.md` 里那张记忆关注策略表，在这个设计下有了明确的直接消费者：**常驻上下文里的模型自己**。

它原本被寄望于影响平台隐藏的记忆引擎（那条链路能不能通至今没有定论），现在它多了一个确定成立的用途——模型读到"用户纠正 AI 的说话方式值得记"，在本轮真的发生了这件事时，就更可能在收尾时提一句。

**这也让它变得可测**：路由信号命中时模型有没有提议同步，是能直接观察的行为。见 `probe.md` 的 P-3。

## 二、重型同步在哪里跑

同步会把自述 prompt、记忆召回结果、合并过程全部塞进上下文。用户本来在这个会话里干别的事——**这些内容对他的主任务是纯污染**。

**能开隔离上下文的端，优先在隔离里跑**：独立 worker、sub-agent、专用任务。主会话只留一句结果摘要。

**开不了隔离的端**，必须先说明"将在当前会话执行，会占用不少上下文"，**再取得一次确认**。

这条不是洁癖。同步跑完之后用户还要接着干原来的活，而那时上下文里已经堆满了他半年前的家庭状况和五个端的记忆倾倒物——模型的注意力被拽走了，他自己也得往回翻。

## 三、hook 和自动化：不进 MVP 默认

**逐轮 hook、会话启动自动同步、定时任务全部不是默认行为。** 它们只作为**未来由用户主动开启的高级选项**存在。

### 为什么否掉"每轮 Stop 攒 buffer、下次启动推送"

这个方案技术上跑得通（老 Contour 的架构就是它），但不该因为跑通过就继承成默认体验：

1. **`Stop` 是每轮回复结束都触发**，不是用户真正结束会话时触发
2. 如果在 Stop 里调模型判断"本轮什么值得存"，**每轮都加延迟和额外推理**
3. 如果不判断、只机械保存，**buffer 快速积累噪音**，清洗成本只是被推后了
4. 会话启动时自动推送 / 拉取 / 检查，**让用户刚打开会话就先等基础设施**
5. **未经确认的 commit / push 违反第一节的门槛**
6. 它会把倾倒和合并过程塞进本来无关的工作会话，**污染上下文**

还有一条只对本地端成立、但足以单独否掉 buffer 的理由：**Claude Code 的会话史本来就落在 `~/.claude/projects/` 里**，harness 已经存了。用户同意倾倒时直接回头挖会话史就行——buffer 从头到尾没买到任何东西，只是把同一份内容抄了第二遍。

### 将来真要开启时的硬约束

**逐轮 hook 不得调用模型、不得碰 Git、不得联网。** 只允许做极便宜的本地标记（例如往一个本地文件追加一行"这个会话有过实质交互"）。

会话结束钩子**结构上不能承载同步**，这有实测数据：

| | 会话启动钩子 | 会话结束钩子 |
|---|---|---|
| **Claude Code** | 600s，可配 | 默认 **1.5s** 共享预算；配了更长超时才上调，**上限 60s**；不能阻止退出 |
| **Codex** | 600s，可配 | 默认 **1s，硬上限 3s** |

（2026-08 官方文档，会变，与实测不符时以实测为准。）

3 秒里完成一次带认证的网络提交不可能可靠，而且失败是静默的——用户以为交上去了。**Codex 的会话结束钩子还会在会话闲置 30 分钟、没有客户端打开时触发**，那时"结束"早已跟真实使用时刻脱钩。

**任何自动化只能调用同步状态机的安全子步骤，不能另造一套规则。** 尤其不能绕过第一节的确认门槛和 `protocol.md` 的并发约束。

装钩子时还有一步别忘：**Codex 要求非托管钩子先经 `/hooks` 审阅并信任**，装完没信任等于没装，而且是静默的。

## 四、频率

**没有默认周期。** 频率跟这一端的**使用频率**走：用得多的端新记忆长得快，同步该密；一个月开一次的端，按月都嫌频繁。

正确的问法是"哪些端你几乎每天用"，不是给用户一个"建议每周"。

**不要为所有端配置同一时刻的周期性完整倾倒。** 就算将来开了自动化：没有新增、更正、失效或撤回时，不得制造空倾倒包。

## 五、失败怎么报

状态机跑不完是常态——权限不够、连接掉了、版本被抢先。规矩只有一条：

**如实报告完成了什么、跳过了什么、失败了什么。绝不伪造成功回执。**

具体地说：

- 包提交失败 → 在 `state/endpoints/<id>.md` 留明确的未提交状态，下次同步重试
- 发布被基础版本检查拦下 → 这是协议正常工作，重新读取重新合并，不是错误
- 某一端接不上 → 标记为"待完成"，并告诉用户这意味着画像仍是暂定版本

"写了但没读"的基础设施比没有更糟，**"报了成功但其实没成"比它还糟**——前者你至少还会怀疑，后者你连怀疑的理由都没有。
