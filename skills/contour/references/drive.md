# 驱动 · 请求与执行范围

## 一、确认门槛

根据用户本轮请求及已有授权确定操作范围。

| 请求 | 执行动作 |
|---|---|
| 表达跨端理解不一致的困扰，尚未要求操作 | 解释相关能力，必要时询问是否开始；不访问私人档案 |
| 查看知界状态 | 读取配置和相关状态记录并报告 |
| 初始化、倾倒或同步 | 在已确认范围内执行对应步骤，复用已有配置和授权 |
| 明确暂不执行 | 停止相关操作，本次会话不再重复提议 |

读取私人档案、生成倾倒包、修改或发布档案、向其他端发送材料均属于实际操作。兴趣表达和技能自动匹配不构成这些操作的授权。

模型在处理其他任务时发现值得同步的信息，可以在任务结束后提议一次；每轮最多一次。此提醒不是可靠的自动采集机制，用户可以直接说“同步知界”。

`routing.md` 的记忆关注策略用于帮助模型识别值得同步的信息。是否影响平台的原生记忆保存机制，按该端实际能力和观察结果记录。

## 二、执行上下文

倾倒按记忆存储进行。一次操作可以采集本轮范围内的多个存储。

**本轮范围**依据用户本轮请求和 `config.md` 权限边界中已保存的授权确定。已登记不等于本轮已授权采集；配置中已明确的日常采集授权直接复用，不重复询问；本轮请求超出已保存的授权时再确认。

**采集方式**由执行者根据授权和该存储当前实际可访问的途径选择，例如直接读取文件、在平台对话中自述、官方导出、接口或 MCP。本地或云端只描述存储位置，不决定用哪种方式，也不预设哪种方式可用。授权不等于已经具备访问能力。

**各存储分别处理**：每个存储各自生成包，保留自己的 `store_id`、`collected_via`、`source_method` 和覆盖范围，再统一整理。某个存储本轮取不到时，记录缺口和原因，不写成“没有变化”，也不阻塞其他存储。

按实际读取的来源标注存储、读取者与上下文，区分原生记忆、会话内容和已加载的知界材料。执行者读不到的来源不代为自述，不将自身的空白上下文或记忆冒充其他存储的记忆，也不把部分可见的资料说成完整记忆。

整合和发布只依赖已保存材料，可由任何有满足发布条件方式的执行者完成。结果加载应在目标端可用的上下文或接口中完成，分别记录执行位置和实际结果。

执行位置由模型按当前工具与请求选择。若会明显影响用户正在进行的其他工作，说明影响后再安排执行。

## 三、自动化

当前版本由用户请求触发初始化、倾倒和同步。授权依据记录在 `config.md` 的权限边界中；倾倒包的 `trigger` 只记录这次由什么发起，含义见 `protocol.md`。

用户主动开启定时任务或钩子时：

- 复用现有同步规则和授权范围。
- 可用于提醒同步，或整理、发布已提交的包；将耗时的整理与发布交给可持续运行的任务，不依赖短生命周期的会话结束回调。
- 自动发起的倾倒属于后续范围：`contour-dump-v1` 的 `trigger` 没有对应取值，不能把这类包记为 `user` 或 `probe`。在 schema 增加取值前，倾倒包仍在用户请求或探测检查时生成。
- 记录实际完成结果，失败时保留可恢复的状态。

配置自动化前先使用当前端已有的能力记录。仅缺少必要信息时查询当前官方说明；不要将历史版本的超时、接口或权限结论作为永久规则。

## 四、同步频率

用户主动决定同步时机。需要建议时结合各端实际使用频率和记忆变化，不预设统一周期。

## 五、失败怎么报

报告已完成、未完成、失败原因和下一步，不把请求已发送视为操作成功。汇报格式见 `report.md`。

- 开始前连不上档案位置：初始化和同步都一样，报告原因和需要用户处理的事项后停止，不倾倒。档案位置的确定与连接见 `SKILL.md`「一个权威档案位置」。
- 已取得记忆、提交时失败，或发布失败：先判断原因。可恢复的（如连接过期、临时网络错误）恢复后重试，也可在同一授权范围、同一目标位置和相同数据语义下改用等效通道。仍未完成时，把包和续办依据保存在当前实际可写、且在授权范围内的位置，并说明位置；没有可以持久保存的位置时如实说明，不报告已保存。
- 发布冲突：重新读取当前版本，再合并和提交；不覆盖他人已保存的结果。
- 某个存储本轮取不到：记录缺口和原因，不写成“没有变化”；其他存储照常采集和整理。
- 某个使用端不可用：记录待接入或待送达状态，保留其他已完成结果。
- 加载无法确认：分别报告材料是否送达、当前会话是否读取、原生记忆状态是否可观察。

恢复时优先核对实际档案、消费记录与存储、使用端状态，避免重复处理。扩大账号、数据范围或发送对象不属于恢复，需要用户重新确认。

失败原因是技能本身的缺陷而不是环境时，报告完成后按 `feedback.md` 起草反馈并询问用户是否提交。
