# 整合 · 把倾倒物变成档案

将按端区分的倾倒包整理为统一档案，保留来源、时间、更正关系和待确认事项。

包格式、消费 manifest、发布怎么保证不互相覆盖，都在 `protocol.md`。本文只管**语义判断**。

---

## 零、第一次整合先验门槛

若 `config.md` 尚无统一版本，先按 `protocol.md` 的「第一版发布门槛」核对；本地能运行 Python 时可用 `scripts/validate_dump.py --cold-start-ready`，不能运行时用能给出同样结果的其他方式。

只有至少两个不同的已登记记忆存储各有一份格式合规的 baseline，才进入下面的语义整合。同一存储的多个包只算一个，无论由哪个端读取；v1 旧包按 `protocol.md` 换算成存储后再计数，存储身份待确认的不计入；能核对出自某个存储的记忆文件、官方导出或接口返回可以作为该存储的 baseline；用户自己的画像和来源不明的旧资料不算记忆存储；格式合规但内容为空的 baseline 可以计入。

检查不通过时，只保留 `config.md`、端状态和 inbox 里的未消费包。**不要生成统一文件，不要写消费 manifest，也不要把单个存储的倾倒包装成“暂定统一版本”或草稿画像。**

这道门只守第一版。已经存在统一版本时，一个存储的新 incremental 可以正常进入本轮整合。

无论是否首发，不合规或 `dump_id` 撞号的包都不进入本轮整合，原因记入 `review/`；其他相互独立的有效包照常处理。

## 一、分层：这条信息归哪儿

按信息用途分层，必要时以来源回指连接相关内容：

1. **它是"该怎么跟这个人说话"的指令吗？** → `routing.md` 沟通路由
2. **它是"什么信息值得留下"的判据吗？** → `routing.md` 记忆关注策略
3. **它是"这类问题该去哪拿最新事实"吗？** → `sources.md` 动态信源区
4. **它是"我们已经沉淀过一份东西，落在某处"吗？** → `sources.md` 知识资产区
5. **它是原始素材吗**（具体事件、原话、某次对话里的观察）？ → `evidence.md`
6. **它是从素材里提炼出的结论**——那就问一句：**这条一年后还成立吗？**
   - 有依据表明长期稳定 → `profile.md`
   - 大概率不成立 → `now.md`
   - **不确定 → `now.md`**

不确定时先放入 `now.md`，并标明时间或待确认状态；后续有稳定证据时再移入 `profile.md`。

### 把不变的核和会变的表述拆开

同一条包含稳定事实和近期状态时分别保存，例如：

> ❌ profile：「女儿 9 岁，小学三年级」
> ✅ profile：「有一个女儿，2016 年生」 + now：「三年级下学期（2025-07 时点）」

> ❌ profile：「核心工具是 X」
> ✅ profile：「重度自建 AI 工作流，工具选择随生态迁移」 + now：「当前主力：X（2026-08 时点）」

逐条判断信息应进入慢变层还是快变层。把短期状态写入慢变层会增加后续误用的风险。

## 二、消解：先做差集，再处理冲突

### 差集：回声不是证据

**档案里已经有的条目，在倾倒物里再次出现，不增加置信度。**

```
新证据 = 本轮倾倒物 ⊖ 上一版档案
```

对照上一版档案识别知界送回后再次出现的内容，不将重复表述计作新的独立证据。来源标记、元数据与语义差集都可能不完整；不能确认独立来源时，不因重复出现提高置信度。


### 跨项目频次：这条是人格还是项目知识

出现频次可以帮助确定复核顺序，但信息性质仍由内容和来源决定：

> 跨项目重复出现的，多半是人格。只在一个项目里出现的，多半是项目知识。

**但它只是提示，不是硬分类。** 一条只出现过一次、却被用户明确确认过的长期偏好（"我一直讨厌被鼓励式开场"），照样该进 `profile.md`——**用户的明确陈述比出现频次强**。反过来，一个说法在三个项目里重复出现，也可能只是同一个技术栈的口头禅。

用频次排优先级，用来源定性质。

---

排除回声后，按时效、事实和互补视角处理差异。

### 时效冲突：同一件事，一端记的是旧状态

**裁决依据必须是条目级的。包级的时间信息一律不参与裁决。**

可以裁的四种依据：

| 依据 | 例子 |
|---|---|
| **事实发生时间** | 条目自带的时效标记：`三年级（2025-07 时点）` |
| **用户陈述时间** | 这句话是用户什么时候说的（倾倒时要求保留原话就是为了这个） |
| **平台给出的记忆创建时间** | 少数端的记忆管理界面能给 |
| **明确的 `supersedes` / `retracts` 关系** | 条目自己声明它取代了哪一条 |

**不能裁的：`captured_at` 和 `trigger`。** 它们只用于审计、调试和分析召回条件。

理由：一次"刚聊完之后的倾倒"照样会吐出多年前形成、只是刚被召回的旧记忆；另一个端晚几分钟倾倒，也可能只是重新描述更旧的状态。**包的产生背景不能变成包内每个条目的事实时间。**

**增量包也不例外。** "这条第一次出现在增量包里，所以它属于这两次倾倒之间"——不成立。自述倾倒是概率性召回：上次没吐出 B、这次吐出了 B，只证明**本次召回了 B**，不证明 B 是这段时间新形成的。

**四种依据都没有时**：并列保留、标明各自来源、进待确认。不要拿"用户触发的"当最后胜负手。

被取代的旧状态保留在 `evidence.md`，标注 `superseded by X`，用于追溯变化。

### 事实冲突：两端说的直接矛盾，且都没有可用的时间信息

**并列写进 `evidence.md`，标明各自来源**，`profile.md` / `now.md` 里对应那条打 `[待确认]`。

依据不足时不选择其中一条作为当前事实。整合完成后汇总待确认项，提供建议处理和理由；用户确认前维持待确认状态，不把建议视为已经接受。


### 视角冲突：看起来矛盾，其实是互补

检查不同来源是否描述了可以同时成立的视角。例如：

> Claude.ai 只读过他的小说范本，记的是「有文学写作能力」。
> Codex 只读过他的社论范本，记的是「有评论写作能力」。

这不是矛盾，是**两端各自只见过部分证据**。合并成一条更完整的结论（「跨文体写作能力，覆盖虚构与评论」），并在 `evidence.md` 里**保留两端各自的原始表述与出处**——因为下游某个场景可能只需要其中一面，保留出处才能精确取用。

判别方法：问"有没有一种情况让两条同时为真？"有，就是互补，不是冲突。

合并时保留各自来源，使后续场景仍可单独核对和使用其中一面。

## 三、反向链接：让碎片能在别的场景被调出来

`evidence.md` 不按时间流水组织，**按"支持哪条结论"组织**。每条证据带编号、日期、来源，末尾列出它支持的结论；每条结论在 `profile.md` / `routing.md` 里带回指编号。

```
### E-023 · 2025-07-16 · 来源：Claude Code 会话史
观察朋友操作 Claude Code 的效率，意识到专业开发者与产品经理在工具使用上的差距，
对"low-code 降低门槛"这个说法产生怀疑。
→ 支持：profile#学习焦虑, profile#工具怀疑主义, routing#技术教学场景
```

一条证据可以支持多条结论。只建立有依据的关系，避免将一次观察过度推断为稳定人格或能力。


### 硬规矩：`profile.md` 里每条结论都得有出处

追不到证据的不是结论，是猜测。把它放进 `evidence.md` 标为待证，别放进 `profile.md`。

来源回指让后续更正、冲突处理和复核有据可查。

## 四、`routing.md`：两张表

这份文件用于常驻上下文，内容应限于日常沟通和记忆关注所需的规则。

### 沟通路由

| 场景线索 | 策略 | 为什么 |
|---|---|---|

**线索必须可观察。** "当用户情绪化时"不是线索，那是判断结果。可观察的是：他在谈什么话题、句子突然变短、出现脏话、开始反复自我否定、连续追问同一点。

**策略必须可执行。** "温和一点"不可执行。可执行的是："先复述他描述的事实并确认理解无误，再给建议；第一轮不要给方案清单。"

**写明“为什么”。** 它帮助模型在未完全覆盖的相近场景中判断是否应采用该策略。

理由依据用户明确陈述、纠正或可追溯的行为证据，不推断未被确认的心理原因。

只建立有真实证据的路由，优先覆盖高频情境和明确的沟通纠正。

### 记忆关注策略

这张表供当前模型识别值得整理的记忆。是否影响端侧原生记忆保存，取决于可用接口与实际结果，不能仅凭指令存在作出保证。

| 信号 | 归哪层 | 为什么值得留 |
|---|---|---|

分两段写：

**通用采集判据**：

- 记录明确否决及其理由，保留适用场景。
- 记录与持续沟通偏好有关的纠正；单次任务事实纠错按原任务处理。
- 记录可跨场景复用的专业判断及依据。
- 每条带时间与出处。

**个性化判据**（从这个用户的 `profile.md` 推出来，必须具体到人）：写清楚对**他**来说什么信号值钱。这部分是倾倒和整合的产物，冷启动第一遍写不出多少是正常的，后面每跑一遍循环补一点。

这张表同时服务于常驻上下文和端侧记忆流程。实际效果按 `probe.md` 的相关观察记录判断；无论是否被端侧记忆吸收，表中的判据仍可用于本轮整理。

## 五、`sources.md`：两个分区

`routing.md` 回答"怎么跟他说话"，`sources.md` 回答"**去哪拿答案**"。两件事，别混。

`sources.md` 分别记录动态事实的查询入口和已有知识资产的位置：

| 分区 | 回答什么 | 典型条目 |
|---|---|---|
| **动态信源路由** | 去哪拿**最新的事实** | 项目进度去 Notion 项目库查 |
| **知识资产路由** | **我们已经沉淀过什么** | Git 操作有一份自己的指南，在 Notion |

两区共用"指针 + 保质期"这套机制，也共用本节末尾「和项目管理系统的边界」。但**识别方式不同**：动态区认**问句形态**（当前 / 最近 / 下一步），资产区认**主题命中**。混成一张表，两种线索会互相稀释。

### 5.1 动态信源路由

涉及当前事实时查询对应来源；统一记忆中的近期摘要不能代替实际查证。

| 信息领域 | 识别线索 | 首选权威来源 | 需要时深入 | 来源不可用时（可空） | 最后验证 |
|---|---|---|---|---|---|

各列用途：

- **识别线索**要可观察。问句里出现"当前""最近""最新进度""下一步"这类词，就是快变意图的信号
- **来源不可用时**只在该领域有指定的备用来源或特殊处理时填写。查不到时的共同要求是**说明"这是基于哪次同步的结果"**，不拿旧记忆冒充最新
- **最后验证时间**记录最近实际确认入口可用的时间；目录、页面或权限变化后需要重新核对

典型几条（照抄之前先确认用户真的这么用）：

| 用户意图 | 首选来源 | 深入 |
|---|---|---|
| 项目最近做到哪、下一步是什么 | 项目索引或项目管理系统 | 项目计划与详细记录 |
| 某个功能怎么实现、错误怎么修 | 当前项目文件与代码 | 项目索引用于定位工作区 |
| 用户最近在做什么 | `now.md` | 对最新性有要求时查项目索引 |
| 这段经历说明他有什么能力 | `profile.md` + `evidence.md` | 反查项目事件或原始文件 |

**不要求所有问题先过项目管理系统。** 已经在正确的工作区里、问的又是具体实现，就直接读当前项目；只有需要确认位置、最新状态或跨项目信息时才先查索引。

### 5.2 知识资产路由

**这一区回答的不是"去哪拿最新事实"，是"我们已经沉淀过什么"。**

这一分区记录可复用资产的位置和适用范围，减少跨端重复创建或遗漏已有资产。

知界维护资产的路由，不接管资产内容或其所在系统的写入规则。

#### 准入：存下来，还要有复用信号

登记知识资产时需要同时满足：

1. **已经存到会话之外**，有稳定位置；
2. **有跨会话复用信号**：被独立命名、放进知识库 / 模板库，或用户明确说以后还要继续使用。

一次性回答、普通项目实现、代码修改、项目配置和当前工作区本来就能定位的交付物不进。它们继续由当前项目文件和动态信源路由负责。不要因为文件是 AI 写的，就把整个仓库变成知识资产表。

#### 用记录块，不用宽表

使用带编号的记录块，容纳多条来源和较长的覆盖说明。编号从 `A-001` 递增，不复用；字段见 `schema.md`。


#### 各键怎么写

**`调用线索` 不是关键词表。** 它要装三种东西：主题词和同义说法（`worktree` / 工作树 / "同时开两个分支"）、场景（在配 CI 的时候）、以及用户对这份资产的模糊指称（"你上次给我整的那个流程"）。写成纯关键词，模型就退化成字符串匹配，而用户的真实说法几乎从不命中你预设的词。

**但"我记得以前问过你"这类泛指称不写进行内。** 它对每一条资产都成立，写进行内就是每条重复一遍同样的话。它属于**区头的一条规则**（见 `assets/templates/sources.md`）：命中时扫整个区，不依赖任何一条的线索。

**`覆盖范围` 同时写适用内容和已知限制。** 例如“覆盖 commit、branch、worktree 的日常操作，不含 CI 和 submodule”。超出这些范围时另行查证。

**超出覆盖和来源不可用是两种独立的情况，不要合并。**

| | 状况 | 怎么处理 | 对用户怎么说 |
|---|---|---|---|
| **超出覆盖** | 资产读得到，只是不含这块 | 另行查证，例如官方文档或当前项目仓库 | "指南没覆盖这块，下面是我另查的" |
| **来源不可用** | 原位置打不开（改名、移动、权限掉了） | 记录原位置失效；可在授权范围内寻找同一份资料的其他有效入口，例如新链接、文件副本或其他接口 | "你沉淀过一份，但原位置现在读不到"，并提示检查这条路由；从其他入口读到时说明入口 |

通过其他入口读到的必须是同一份资料（核对标题、内容或版本）；读到的是不同资料时按其实际来源说明，不归因于原资产。路由位置的更新仍按下文“修改报告”流程，实际核对后才刷新。

这两种情况的通用处理由模型现场判断；只有某份资产有指定的下一跳、备份位置或恢复方式时，才写进该条的可选键 `超出覆盖时` 或 `来源不可用时`。

**`来源记录` 记端 + 日期 + 倾倒包指针，不记作者名。** 只写"某个端写的"，一年后既复核不了这条路由当初为什么建立，冲突时也没法裁决。指到 `dump_id` 才接得上 `evidence.md` 那套追责链。

**`最后验证` 在这一区比动态区更吃重。** 动态区的条目是系统级的（"项目进度去项目库查"），指针稳定；资产是**页面级**的，会改名、移动、归档。而烂掉的资产路由比没有更糟：模型会以十足的把握说"你写过一份在 X"，打开是 404——或者更坏，打开的是一份他自己都忘了已作废的旧版，然后照着讲。

#### 资产会被取代

重写了一份、换了平台、拆成了两份——这跟 `evidence.md` 的演化语义一样，直接复用 `schema.md` 里那两条标记：

```text
superseded by A-007 · 2026-08-12      # 旧记录留着，标明被谁取代
[已撤回 2026-08-12] · 主题：<粗粒度>   # 用户要求移除
```

保留旧编号与取代关系，便于其他端从旧位置找到当前资料；用户撤回时按撤回规则处理。

#### 写侧不在这一区的职责里

外部资产仍由所在系统和用户请求管理。知界只维护位置、覆盖范围、来源与变更关系。

已登记资产的创建或改动应随倾倒上报，以便更新来源记录、覆盖范围和最后验证。自述 prompt 为这类信息提供单独字段。

收到修改报告后分两种处理：

- **整合执行者能实际读取资产**：核对变化，更新覆盖范围，追加来源记录，把 `最后验证` 刷新为本次实际读取日期。
- **整合执行者只能看到操作报告**：追加来源记录，状态标成 `待复核`，保留旧的覆盖范围与最后验证。操作发生时间不是验证时间，不得拿倾倒自述冒充读取证据。

后续任一整合执行者成功读取并核对后，才能移除 `待复核` 状态。读取失败时按来源不可用处理，不能静默刷新保质期。

### 和项目管理系统的边界

项目库、日志、任务和日历保留在原系统；知界仅按授权提取与用户记忆有关的结论和来源指针。

判断一条信息归谁：

- 主要回答"**项目**发生了什么、何时、下一步" → 留在项目系统
- 主要回答"这说明**用户**是什么样的人、有什么能力、当前扛着多少" → 进知界
- 两者都是 → **详细事实留在项目系统，知界只存提炼后的结论 + 反向指针**

## 六、负向约束：`profile.md` 里那节"不是他"

负向约束单列，便于加载、体检和后续更正。

从倾倒物里专门捞这几类：

- 他明确拒绝过的做法、工具、说话方式
- 别人贴在他身上但他不认的标签
- 他做过但失败并总结出教训的尝试（写清楚"为什么不再这么做"）

写成断言句，不要写成建议。「不要用鼓励式话术开场」比「他可能不太喜欢鼓励」有用。

## 七、更正与撤回：用户的删除权

根据用户明确请求执行更正、撤回或脱敏，不自行决定删除用户信息。

### 更正 —— 内容被取代

新内容取代错误或过期内容。旧条目在 `evidence.md` 中保留，并标注 `superseded by <新编号> · <日期>`。

### 撤回 —— 停止使用

1. 从 `profile.md`、`now.md`、`routing.md` 和 `sources.md` 移除相关当前内容。
2. 在 `evidence.md` 中将原文替换为不含明文的撤回标记：`E-023 · [已撤回 <日期>] · 主题：<粗粒度>`。
3. 在 `review/` 记录撤回范围，供后续整合识别再次出现的内容。

当前文件布局中的原始倾倒包仍可能保留该内容。回执说明“已停止在统一档案中使用，原始包仍可能可读”，不将撤回等同于彻底删除。

### 脱敏 —— 处理原始包中的明文

用户要求进一步移除原始包内容时，单独确认处理范围及以下影响，然后：

1. 定位相关包和条目，用 `[已脱敏 <日期> · 主题：<粗粒度>]` 替换明文。
2. 在 manifest 的 `redaction_events` 中记录事件，并按 `protocol.md` 更新内容修订。
3. 按同一安全发布流程保存包、依据、撤回记录、manifest 和版本信息。
4. 已消费这些包的历史统一版本不重新计算。

### 回执范围与影响

- 报告本次实际定位和替换的内容；不能保证已经找出所有改写或转述。
- 处理限于档案的当前版本；档案位置保留的历史版本、备份或副本可能仍有明文，本操作不改写它们，需要时向用户说明。
- 对目标端原生记忆、平台缓存等未实际处理的位置，说明未完成或无法确认。
- 原始内容被替换后，当前档案不再能用该明文复核原结论；历史记录的可见范围另行说明。
- 撤回标记会保留粗粒度主题，用于识别以后重新出现的内容。语义匹配可能遗漏；用户要求连主题也移除时，说明将失去这部分识别依据。

按用户决定处理，并分别记录操作结果与未覆盖的位置。
