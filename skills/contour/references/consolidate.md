# 整合 · 把倾倒物变成档案

输入是一堆按端分开的倾倒包，输出是实例仓里那几份统一文件。这一步决定档案能不能用，也是最容易做成"把几份文本拼一块"的一步。

包格式、消费 manifest、发布怎么保证不互相覆盖，都在 `protocol.md`。本文只管**语义判断**。

---

## 一、分层：这条信息归哪儿

按顺序问，第一个"是"就落定：

1. **它是"该怎么跟这个人说话"的指令吗？** → `routing.md` 沟通路由
2. **它是"什么信息值得留下"的判据吗？** → `routing.md` 记忆关注策略
3. **它是"这类问题该去哪查证"吗？** → `sources.md`
4. **它是原始素材吗**（具体事件、原话、某次对话里的观察）？ → `evidence.md`
5. **它是从素材里提炼出的结论**——那就问一句：**这条一年后还成立吗？**
   - 一定成立 → `profile.md`
   - 大概率不成立 → `now.md`
   - **不确定 → `now.md`**

最后那条不是和稀泥。`now.md` 有强制的"最后更新"时间戳，一条放错层的信息在那里会随时间自己暴露出过期；放进 `profile.md` 则会一直以满分自信被下游各端引用。**放错方向的代价不对称，所以往有时间戳的那边偏。**

### 把不变的核和会变的表述拆开

倾倒物里大量的条目是两者的混合体，直接整条塞进任何一层都是错的：

> ❌ profile：「女儿 9 岁，小学三年级」
> ✅ profile：「有一个女儿，2016 年生」 + now：「三年级下学期（2025-07 时点）」

> ❌ profile：「核心工具是 X」
> ✅ profile：「重度自建 AI 工作流，工具选择随生态迁移」 + now：「当前主力：X（2026-08 时点）」

这个拆法值得在每一条上都过一遍。一份档案变馊，多半不是因为写错了，是因为把有保质期的东西写进了没有保质期的层。

---

## 二、消解：先做差集，再处理冲突

### 差集：回声不是证据

**档案里已经有的条目，在倾倒物里再次出现，不增加置信度。**

```
新证据 = 本轮倾倒物 ⊖ 上一版档案
```

必须先做这一步，因为知界每一轮都会把整合结论**喂**回各端的原生记忆（见 `load.md`）。下一轮倾倒会把它们原样倒出来，标着 `[记]`，跟真正学来的东西长得一模一样。不做差集，档案里最虚的那几条会被自己的回声"确认"成硬结论——**档案自己给自己背书，跑几轮就再也拆不开了。**

信源带版本（git / Notion 历史），上一版随时拿得到。这条规矩不依赖标记能不能在压缩中活下来，所以比"打个标签让倾倒跳过"结实——标签会被平台吃掉，差集不会。

代价：用户真心重复强调的东西也不算加分。这个保守方向是对的——**宁可漏认一次真确认，不能收一次假确认。**

### 跨项目频次：这条是人格还是项目知识

本地端的倾倒物里混着大量项目知识，整条塞进 `profile.md` 会把档案撑成一锅粥。频次是个好用的**证据强度提示**：

> 跨项目重复出现的，多半是人格。只在一个项目里出现的，多半是项目知识。

**但它只是提示，不是硬分类。** 一条只出现过一次、却被用户明确确认过的长期偏好（"我一直讨厌被鼓励式开场"），照样该进 `profile.md`——**用户的明确陈述比出现频次强**。反过来，一个说法在三个项目里重复出现，也可能只是同一个技术栈的口头禅。

用频次排优先级，用来源定性质。

---

差集做完，剩下的才是真正要消解的。各端记的东西对不上是常态，不是异常——它正是用户来找这个技能的原因。三种冲突，处理方式不同：

### 时效冲突：同一件事，一端记的是旧状态

**裁决依据必须是条目级的。包级的时间信息一律不参与裁决。**

可以裁的四种依据：

| 依据 | 例子 |
|---|---|
| **事实发生时间** | 条目自带的时效标记：`三年级（2025-07 时点）` |
| **用户陈述时间** | 这句话是用户什么时候说的（倾倒时要求保留原话就是为了这个） |
| **平台给出的记忆创建时间** | 少数端的记忆管理界面能给 |
| **明确的 `supersedes` / `retracts` 关系** | 条目自己声明它取代了哪一条 |

**不能裁的：`captured_at` 和 `trigger`。** 它们只用于审计、调试和分析召回条件。

理由：一次"刚聊完之后的倾倒"照样会吐出多年前形成、只是刚被召回的旧记忆；另一个端晚几分钟倾倒，也可能只是重新描述更旧的状态。**包的产生背景不能变成包内每个条目的事实时间。**

**增量包也不例外。** "这条第一次出现在增量包里，所以它属于这两次倾倒之间"——不成立。自述倾倒是概率性召回：上次没吐出 B、这次吐出了 B，只证明**本次召回了 B**，不证明 B 是这段时间新形成的。

**四种依据都没有时**：并列保留、标明各自来源、进待确认。不要拿"用户触发的"当最后胜负手。

**裁完旧的不删**，转写进 `evidence.md` 标注 `superseded by X`。旧状态本身是证据——它记录了变化轨迹，而轨迹能推出"这个人在往哪走"，那是新状态给不了的。

### 事实冲突：两端说的直接矛盾，且都没有可用的时间信息

**并列写进 `evidence.md`，标明各自来源**，`profile.md` / `now.md` 里对应那条打 `[待确认]`。

不要替用户裁决。你手上的信息不足以判断哪一端对——你只知道它们不一样。悄悄挑一个写进去，用户不会发现，然后这条会被五个端反复使用。**替用户做无声的裁决，是在偷他的数据主权。**

**但记录不等于当场问。** `[待确认]` 是异步的，反问是同步的——后者会打断用户正在干的事，而他被突然问住时手上的信息比读文件时还少。摆在文件里，他下次读到自然会处理。

整合跑完可以把本轮新增的 `[待确认]` 汇成一张清单给用户看一眼，**每条带一个默认处理**，让他能一次回"除了第 3 条，其余按你说的"。给默认值不违反数据主权：**默认可见可否决，静默裁决不可见**——被禁止的是后者。

### 视角冲突：看起来矛盾，其实是互补

这类最重要，也最容易被误当成事实冲突处理掉。

> Claude.ai 只读过他的小说范本，记的是「有文学写作能力」。
> Codex 只读过他的社论范本，记的是「有评论写作能力」。

这不是矛盾，是**两端各自只见过部分证据**。合并成一条更完整的结论（「跨文体写作能力，覆盖虚构与评论」），并在 `evidence.md` 里**保留两端各自的原始表述与出处**——因为下游某个场景可能只需要其中一面，保留出处才能精确取用。

判别方法：问"有没有一种情况让两条同时为真？"有，就是互补，不是冲突。

**这类合并是这个技能最主要的产出价值。** 用户跨端使用的直接后果就是每端只见过他的一部分，谁也拼不出全貌。合并的时候留意找它们。

## 三、反向链接：让碎片能在别的场景被调出来

`evidence.md` 不按时间流水组织，**按"支持哪条结论"组织**。每条证据带编号、日期、来源，末尾列出它支持的结论；每条结论在 `profile.md` / `routing.md` 里带回指编号。

```
### E-023 · 2025-07-16 · 来源：Claude Code 会话史
观察朋友操作 Claude Code 的效率，意识到专业开发者与产品经理在工具使用上的差距，
对"low-code 降低门槛"这个说法产生怀疑。
→ 支持：profile#学习焦虑, profile#工具怀疑主义, routing#技术教学场景
```

一条证据可以挂在多条结论下，这是关键：

> 用户在聊游戏时提到对某个游戏的深刻见解。这条信息看上去没有记忆价值，但当用户求职时，这可能是他自己都没发现的针对游戏行业的潜在优势。

按时间流水存，这条永远只在"聊游戏"的语境里被召回。挂到 `profile#行业洞察力` 和 `profile#游戏领域知识` 两条结论下，求职场景激活「行业洞察力」时它就跟着出来了。**链接不是索引，是跨场景的调用通道。**

### 硬规矩：`profile.md` 里每条结论都得有出处

追不到证据的不是结论，是猜测。把它放进 `evidence.md` 标为待证，别放进 `profile.md`。

这条是整份档案可信度的地基。一旦允许无出处的结论进入人格层，档案就退化成"AI 对用户的印象"，而那种东西每一端本来就有，用户不需要再要一份。

## 四、`routing.md`：两张表

这份文件是唯一要常驻各端上下文的，也是知界区别于"记忆导出工具"的地方。写得敷衍，整个技能就只剩一个导出器。

### 沟通路由

| 场景线索 | 策略 | 为什么 |
|---|---|---|

**线索必须可观察。** "当用户情绪化时"不是线索，那是判断结果。可观察的是：他在谈什么话题、句子突然变短、出现脏话、开始反复自我否定、连续追问同一点。

**策略必须可执行。** "温和一点"不可执行。可执行的是："先复述他描述的事实并确认理解无误，再给建议；第一轮不要给方案清单。"

**"为什么"必须写。** 这一列不是注释，它是功能件——真实场景永远超出你列的清单，模型碰到没覆盖的情况时，靠这一列泛化。只有"场景→策略"两列的路由表，出了清单范围就废了。

写的时候把理由落到人格层：不是"因为他情绪化"，是"因为他的焦虑源于对未来的悲观预测，直接给方案会被读成敷衍——他要的是先承认判断的合理性"。

**起手别贪多。** 五到八条来自真实证据的场景，比二十条编出来的强得多。编的场景会让模型在真实情况下匹配到错的行，那比没有路由表更糟。素材从自述的第 4、5 类（负面项、沟通偏好）和会话史里"用户纠正 AI"的时刻来。

### 记忆关注策略

这张表的目标读者是各端的**原生记忆系统**——告诉它们，对这个用户什么算"值得记"。

但这条链路有前提：**原生记忆系统读的不一定是上下文。** 保存动作由模型主动发起时，常驻判据直接有效；换成平台后台抽取，它就只能影响模型在对话里主动提一句"这条值得记"。各端不同，冷启动时按 `references/probe.md` 的 P-3 实测——结果决定这张表值不值得占常驻预算。

| 信号 | 归哪层 | 为什么值得留 |
|---|---|---|

分两段写：

**通用判据**（对任何人都成立，冷启动时就能写）：

- 记否决，**连理由一起记**。「他否决了方案 A」几乎没用，「他否决方案 A 因为它把审查责任推给了他自己」能推出一大片行为。
- 记用户对 AI 的每一次纠正。这是沟通路由的一等原料，而原生记忆系统几乎从不主动保存它。
- 记在非专业场景里露出的专业判断。它跨场景可复用，而且用户自己往往没意识到。
- 每条带时间与出处。

**个性化判据**（从这个用户的 `profile.md` 推出来，必须具体到人）：写清楚对**他**来说什么信号值钱。这部分是倾倒和整合的产物，冷启动第一遍写不出多少是正常的，后面每跑一遍循环补一点。

这张表有两个消费者，别只想着第一个：

- **各端的原生记忆系统**——这条链路能不能通取决于平台机制，未定，见 `probe.md` 的 P-3
- **常驻上下文里的模型自己**——这条**确定成立**。模型读到"用户纠正 AI 的说话方式值得记"，本轮真发生了这件事时，就更可能在收尾时提议同步（见 `drive.md` 的确认门槛）

所以就算 P-3 测出平台链路不通，这张表也不白写。

## 五、`sources.md`：哪类问题去哪查

`routing.md` 回答"怎么跟他说话"，`sources.md` 回答"**去哪拿最新的事实**"。两件事，两张表，不要混。

**没有这张表，知界越成功越危险。** 档案做得越好、传得越广，模型就越自信地复述一份过期的 `now.md`——而它听起来完全像真的。统一记忆可以当近期状态的缓存，**不能替代快变信息的权威来源**。

| 信息领域 | 识别线索 | 首选权威来源 | 需要时深入 | 来源不可用时 | 最后验证 |
|---|---|---|---|---|---|

每一列都有用途：

- **识别线索**要可观察。问句里出现"当前""最近""最新进度""下一步"这类词，就是快变意图的信号
- **来源不可用时**必须写。查不到时的正确行为是**说明"这是基于哪次同步的结果"**，不是拿旧记忆冒充最新
- **最后验证时间**是这张表自己的保质期。指针也会烂——项目挪了目录、数据库改了名

典型几条（照抄之前先确认用户真的这么用）：

| 用户意图 | 首选来源 | 深入 |
|---|---|---|
| 项目最近做到哪、下一步是什么 | 项目索引或项目管理系统 | 项目计划与详细记录 |
| 某个功能怎么实现、错误怎么修 | 当前项目文件与代码 | 项目索引用于定位工作区 |
| 用户最近在做什么 | `now.md` | 对最新性有要求时查项目索引 |
| 这段经历说明他有什么能力 | `profile.md` + `evidence.md` | 反查项目事件或原始文件 |

**不要求所有问题先过项目管理系统。** 已经在正确的工作区里、问的又是具体实现，就直接读当前项目；只有需要确认位置、最新状态或跨项目信息时才先查索引。

### 和项目管理系统的边界

用户的 Notion 项目库、工作日志、任务系统、日历**首先服务于他自己**——记录发生了什么、下一步做什么、一段时间里精力投在哪。它们是**外部操作记忆**，不是知界要复制和接管的东西。

判断一条信息归谁：

- 主要回答"**项目**发生了什么、何时、下一步" → 留在项目系统
- 主要回答"这说明**用户**是什么样的人、有什么能力、当前扛着多少" → 进知界
- 两者都是 → **详细事实留在项目系统，知界只存提炼后的结论 + 反向指针**

## 六、负向约束：`profile.md` 里那节"不是他"

单独说这一节，因为它最容易被漏掉：**原生记忆系统几乎不记否定。** 模型会记住"他喜欢 X"，不会记住"他明确说过不要 Y"。而对行为的约束力，后者比前者强得多——正向偏好只是加权，负向约束是边界。

从倾倒物里专门捞这几类：

- 他明确拒绝过的做法、工具、说话方式
- 别人贴在他身上但他不认的标签
- 他做过但失败并总结出教训的尝试（写清楚"为什么不再这么做"）

写成断言句，不要写成建议。「不要用鼓励式话术开场」比「他可能不太喜欢鼓励」有用。

## 七、更正与撤回：用户的删除权

**删除只由用户提出，不由你判断。** 不要主动评估什么算"敏感信息"该清理——那是替他做决定，而且判错的方向是不可逆的。

MVP 支持两档：

### 更正 —— 内容被取代

错误或过期的内容被新内容取代。旧条目留在 `evidence.md`，标 `superseded by <新条目编号> · <日期>`。这是正常演化，前面时效冲突那节讲的就是它。

### 撤回 —— 从当前资产移除

用户明确要求某条内容不再出现在档案里。做三件事：

1. 从 `profile.md` / `now.md` / `routing.md` / `sources.md` 里删掉
2. `evidence.md` 里的原条目替换成**不含敏感原文的撤回标记**：`E-023 · [已撤回 2026-08-11] · 主题：<粗粒度主题>`
3. 在 `review/` 留一条撤回记录，供下次整合时拦截

**撤回标记要拦截的正是它自己拒绝保存的内容**，这里有个绕不开的矛盾，必须对用户讲明白：

- **哈希匹配挡不住换了措辞的复现**——自述每次都会重新表述同一件事。MVP 唯一可行的是**按主题的语义过滤**（"凡涉及〈某主题〉的条目，丢弃且不再询问"），而语义过滤**会漏**
- **墓碑本身以粗粒度泄露了主题**（"用户撤回了关于健康的条目"）。想连主题都不留，就只能接受下次倾倒可能把它重新带回来

两个代价都是真的，让用户自己选，别替他选一个然后不说。

### MVP 不做的

- **不自动重写 Git 历史。** 撤回是"从当前资产移除"，不是"从所有历史彻底清除"
- **不承诺清除**旧克隆、平台缓存，或各端已经形成的原生记忆

**这两句话必须原样告诉用户**，否则他会以为撤回等于抹掉了。彻底清除以后作为需要单独确认的特殊管理功能。

---

## 八、收尾

- `now.md` 文件头写上"最后更新"时间戳，以及本次整合消费了哪些倾倒包
- 更新 `dumps/processed/manifest.md`：本次发布的版本消费了哪些 `dump_id`
- 没解决的冲突进 `review/`，不要埋进正文
- **倾倒包原件保留，永远不删**（`protocol.md` 的不可变规则）——它们是回溯的唯一依据
