# Google Drive · 档案介质适配

本文件只规定 Google Drive 作为**档案位置**时的接入和发布规则。它不替代 `drive.md`：后者仍是请求范围、执行上下文与失败处理的控制面；`protocol.md` 仍是逻辑对象、包身份、消费记录和发布条件的唯一规范。

这里的 Adapter 是缺少 Google Docs 原地编辑能力时，对同一逻辑档案的介质实现要求；不是另一份档案，也不是把档案永久转换为某一种格式的授权。

## 每次操作先选路径

每个执行端在需要**读取、整合或发布** Google Drive 档案时，都重新检查自己当前实际可用的连接能力。不能按 OpenAI、Anthropic、Google 等厂商身份、账号身份，或档案初始化时的一次探测结果推定本轮路径。

`config.md` 可以记录档案位置、存储布局／格式约定，以及已实际使用过的接入与发布结果；这些记录只提供定位和复用依据，不能锁定其他执行端。

### 路径 A：有 Google Docs 原地编辑能力

当前端有 Google Docs MCP、插件或等效能力，能够在同一份 Drive 档案中原地读取和编辑 Docs 时：

- 优先使用该原生能力；
- 不启用 Google Drive Adapter fallback；
- 仍按 `protocol.md` 的版本、完整性、冲突与回读规则执行。

判断的是本端实际能否原地读写，而不是某个模型或用户通常“应该有”什么能力。

### 路径 B：没有原地编辑能力，但具备基础 Drive 文件能力

当前端没有可用的 Google Docs 原地编辑能力，但能够列出目录、读取文件、只新建文件或目录，并回读新建对象时，自动使用 Google Drive Adapter。

Adapter 不依赖 Google Docs MCP。它负责读取和安全发布同一份统一档案，因此“没有 Google Docs MCP”不等于“只能读取和提交倾倒包、不能发布”。在实际启用前，先核对本端具备完成本轮所需的列目录、读取、新建和回读能力；缺少其中任何一项时，不能把 Adapter 标为可用。

### 路径 C：两条路径都不能完整使用

当前端既没有原地编辑能力，也缺少 Adapter 所需的基础 Drive 文件能力时，按实际可达范围处理：可以读取的已发布对象照常读取；能够提交的倾倒包照常按包的不可变规则提交；不能完成的整合或发布保留待处理状态。

不要因为本端不能发布就把包说成已消费，或把旧版本说成新版本。向用户明确报告缺少的是哪一种具体能力（例如无法列目录、读取、创建版本对象或回读），并按 `drive.md` 的失败处理保留续办依据。

## 两条路径只操作一个逻辑档案

无论走原生 Docs 路径还是 Adapter，都使用同一个 Drive 档案位置、同一套逻辑对象和同一组包／版本语义。不得因接入方式不同创建两套相互独立的 `config.md`、统一档案或收件区。

`protocol.md` 展示的是逻辑目录树。Google Drive 可使用适合其介质特性的等价物理布局，但必须保留逻辑对象的名称与关系、`dump_id`、消费记录、基础版本检查、完整发布和冲突处理。`config.md` 应如实记录采用的布局，不把“可检测分叉”描述成“具有互斥锁”或“不会发生并发”。

## Adapter 发布统一档案

Adapter 只在路径 B 下使用。它发布的是当前协议规定的一整组逻辑对象：`config.md`、`profile.md`、`now.md`、`routing.md`、`sources.md`、`evidence.md`、`tests.md` 和 `dumps/processed/manifest.md`。日后协议新增或删减统一对象时，以 `protocol.md` 为准，不能因本节列举而漏发。

### 等价的版本化布局

推荐在档案根目录下将每次统一发布作为一个全新的版本对象组，例如：

```text
<Drive 档案根目录>/
└── releases/
    ├── v12--<发布组标识>/
    │   ├── config.md
    │   ├── profile.md
    │   ├── now.md
    │   ├── routing.md
    │   ├── sources.md
    │   ├── evidence.md
    │   ├── tests.md
    │   ├── dumps/processed/manifest.md
    │   └── COMPLETE.md
    └── v13--<发布组标识>/
```

`<发布组标识>` 必须在同一逻辑版本内唯一，避免两个并发发布者相互覆盖。名称只是一个可读示例；只要能表达相同关系，Adapter 可以使用其他物理布局。

### 发布步骤

1. 列出已完成的版本对象组，读取当前唯一版本作为基础；若当前最大版本已分叉，先进入冲突处理，不得继续发布。
2. 基于该基础版本整合，创建一个此前不存在的新版本对象组。所有对象都只新建，不原地修改旧版本。
3. 将本次完整对象组写入新位置，包括新的 `config.md` 和消费 manifest；旧版本原地保留。
4. 回读每个已写入对象，核对对象齐全、内容与本次意图相符，以及 manifest 和配置所述版本相互一致。
5. 只有第 4 步全部成功后，最后新建 `COMPLETE.md` 完成标记。标记至少写明逻辑版本、发布组标识和完成时间；它是“整组已通过回读”的发布凭据，不替代 manifest。

发布中途失败时，不补写完成标记，不重用或覆盖这个失败对象组。读取端只承认有完成标记且对象齐全、可读取的对象组，因此只能看到上一个已完成版本。失败组保留为恢复与诊断依据，但不视为已发布。

### 读取当前版本与分叉

读取端通过列出 `releases/` 确定当前版本：

- 只考虑带完成标记、对象完整且可读取的对象组；
- 当前版本是这些对象组中的最大逻辑版本，不设置、也不反复覆盖一个“当前版本”指针文件；
- 同一最大逻辑版本只有一组已完成对象时，读取该组；
- 同一最大逻辑版本存在多组已完成对象时，标记为并发分叉，保留全部结果，进入冲突处理／整合流程，并向用户报告；不得任选一组继续发布。

逻辑版本必须可以比较；若布局中的版本格式不能可靠比较，Adapter 不得猜测当前版本，应保留待处理并报告该布局缺少的规则。

两个端同时从同一基础版本发布时，都可能产生相同的新逻辑版本。Adapter 的保证是两组结果都保留、读取端能发现分叉；这不是互斥锁，也不能承诺并发不会发生。处理分叉后再创建后续版本，不能由后写入者静默覆盖前者。

## 倾倒包与更正

无论当前端采用哪条路径，正式提交的倾倒包都遵守 `dump.md` 与 `protocol.md` 的只新建、不可变规则。写包前用户确认产生的信息写入「当前会话内容与推断」，同时保留来源端原有矛盾或不确定状态；提交后出现的更正以新更正包处理，不改写已经提交的包。

## 验收要求

以下是 Adapter 与路径选择的验收场景，不是已经完成实测的声明。实际验证日期和实际能提供的保证写入档案的 `config.md`。

- 当前端具备 Google Docs 原地编辑能力时，走原生 Google Docs 路径，不启用 Adapter。
- 当前端没有原地编辑能力、但具备 Adapter 所需 Drive 文件能力时，自动使用 Adapter，并能完成同步与发布。
- 当前端缺少两种能力时，读取和提交所有实际仍可完成的内容，保留待处理状态并明确报告缺口。
- 同一逻辑档案不会因不同执行端分别走原生路径和 Adapter 而分裂成两套统一档案。
- Adapter 发布中途失败后，读取端只能看到上一个已完成版本。
- 两个端同时经 Adapter 发布时，两组结果均保留，且读取端识别同号分叉，不静默覆盖。
- Adapter 发布后能回读并核对新版本。
- 正式提交后的倾倒包不会被修改。
- 写包前的用户确认同时留下当前会话陈述与原记忆矛盾／不确定状态，且不伪装为可访问的持久记忆。
- 正式提交后用户提供更正时，以新的更正包处理，不删除或重建旧包。
