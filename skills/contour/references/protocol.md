# 协议 · 数据面

这份文件管**格式与原子性**：倾倒包长什么样、什么时候算被处理、发布怎么保证不互相覆盖。

它是 `dump.md`（写方）和 `consolidate.md`（读方）共享的唯一规范——两边有分歧时以本文为准。语义判断（这条归哪层、冲突怎么解）在 `consolidate.md`，触发时机（谁在什么时候跑）在 `drive.md`。

---

## 实例仓结构

```text
<私有实例仓>/
├── config.md                          # 稳定实例配置
├── profile.md                         # 慢变画像
├── now.md                             # 快变用户状态
├── routing.md                         # 常驻：沟通路由 + 记忆关注策略
├── sources.md                         # 动态信源路由 + 知识资产路由
├── evidence.md                        # 证据、来源、取代与撤回关系
├── tests.md                           # 隐藏题库，不进被测端上下文
├── state/
│   └── endpoints/<endpoint-id>.md     # 每端能力与游标，只由该端自己写
├── dumps/
│   ├── inbox/<endpoint-id>/<captured-at>__<dump-type>__<dump-id>.md
│   └── processed/manifest.md          # 哪个统一版本消费了哪些包
└── review/                            # 冲突、待确认、撤回、失败恢复
```

文件名全小写——技能资产和实例资产会在多个平台间流转，大小写差异是纯粹的自找麻烦。

**分开两类写入者，这是整个结构的骨架：**

| | 谁写 | 冲突面 |
|---|---|---|
| `config.md` + 七份统一文件 | 只有当轮协调者 | 靠基础版本检查串行 |
| `state/endpoints/<id>.md` | 只有该端自己 | 端之间无冲突；**同端并发见下** |
| `dumps/inbox/<id>/` | 只有该端自己，且只新建 | 无冲突——只新建，不改旧的 |

把每端游标塞进任何一份共享文件（`now.md` 或 `config.md` 都一样）会制造并发热点：一次正常同步同时改统一画像、处理状态和中央台账，冲突面无谓地扩大。**游标是端的私产，就该住在端自己的文件里。**

**"该端自己写"不等于没有并发。** 同一个产品可以同时开两个会话——两个 Claude Code 窗口各跑一次同步，写的是同一份 `state/endpoints/claude-code.md`，后写的会盖掉先写的游标，于是有一次倾倒的记录凭空消失，下一轮该端看起来落后了一版。

所以**状态文件的写回也要走条件写入**，跟统一文件同一条规矩：读的时候记下基础版本，写的时候带上，被拒就重读重写。它比统一文件便宜得多——冲突时直接重取当前状态、重新填自己这一轮的字段即可，不需要重新合并任何东西。

倾倒包不受影响：它只新建、不改旧的，两个会话各产一个包都进候选集，正是想要的行为。

## 端标识

每个纳入端有一个稳定的 `endpoint-id`，描述**产品表面**，不描述模型：

```text
chatgpt-web
claude-ai-web
claude-desktop
claude-code
codex-cli
```

模型名、版本、账号范围、项目范围都是**每次倾倒的元数据**，不进 `endpoint-id`。换个模型不是换了一个端——把模型写进 ID，换模型时全部历史游标会突然失配，看起来像新端接入。

同一产品用两个账号（个人 / 工作）算两个端，后缀区分。

## 倾倒包

### 身份：`dump_id`，不是文件名

**包的唯一身份是 frontmatter 里的 `dump_id`，一个 UUID4。** 文件名、时间戳、路径都只是让目录可读，**任何地方记账都用 `dump_id`**——消费 manifest、`previous_dump_id`、状态文件里的游标，一律如此。

文件名把它带上，是为了肉眼也能对上号：

```text
dumps/inbox/<endpoint-id>/<captured-at>__<dump-type>__<dump-id>.md
```

`captured-at` 用带时区的 ISO 8601；文件系统不接受冒号时用连字符替代。

**`endpoint-id` 会被拼进路径，所以字符集必须封死**：小写字母、数字，单个连字符分隔（`\A[a-z0-9]+(?:-[a-z0-9]+)*\Z`）。不限制的话 `../escaped` 这种值会把包写到收件区之外，而校验只扫收件区，看不见它。`scripts/new_dump.py` 和 `scripts/validate_dump.py` 都强制这条。

**`dump_id` 撞号是静默故障**：manifest 会记错账，导致重复消费或漏包，而单看任何一个文件都合规。所以查重必须在批次层面做——`validate_dump.py --inbox` 干的就是这件事。

**包一旦写入就不可变。** 不改内容、不删除、不因为有了新包就退出候选集。

**唯一的例外是用户明确要求的脱敏。** 不可变是**合并流程的纪律，不是对抗数据所有者的权利**——用户要清掉自己的数据时必须能清。

它是一个需要单独确认的独立动作，走完整的发布流程（同一提交 + 基础版本检查），并在 manifest 的 `redaction_events` 里留痕。代价和保证边界见 `consolidate.md` 的撤回一节。**脱敏过的包，`content_revision` 会 +1**（首次入库隐含为 1）——它让"内容与首次入库不同"成为一件被声明过的事，至于那次变更合不合法，查 Git 历史和用户确认记录。

理由值得写清楚，因为它反直觉：**自述倾倒不是数据库快照，是概率性召回。** 同一端第二次可能想起 A、却忘了第一次吐出的 B。新包不能证明包含旧包——按"新的覆盖旧的"处理会静默丢掉 B，而且丢得毫无痕迹。

**去重在条目层做，不在文件层做。** 重复条目合并来源引用，包本身各自留着。

### frontmatter

```yaml
---
schema_version: contour-dump-v1
dump_id: <全局唯一>
endpoint_id: <稳定端标识>
provider: <厂商>
surface: <web / desktop / code / cli>
model: <当前模型；未知写 unknown>
captured_at: <带时区时间>
dump_type: <baseline / incremental / verification>
trigger: <user / probe>
memory_scope: <global / project / workspace / mixed / unknown>
source_method: <native-view / model-self-report / export / file-memory / mixed>
contour_context_loaded: <true / false / unknown>
last_contour_revision_read: <最后读到的统一版本；没有写 null>
previous_dump_id: <增量包引用上一个；没有写 null>
---
```

三类 `dump_type`：

- **baseline** —— 端首次纳入，描述该端当前可访问的全部记忆视图
- **incremental** —— 后续，输出自上次成功倾倒以来新增、更正、失效或值得重新确认的内容
- **verification** —— 探测用，不进正式画像，除非用户明确批准

`trigger` 只有两个值。**没有 `event` 和 `poll`**——MVP 不做逐轮 hook，也不做定时倾倒，所有倾倒都由用户确认后发起（见 `drive.md`）。

### `captured_at` 和 `trigger` 不能裁决事实新旧

**这两个字段只用于审计、调试和分析召回条件。** 写进 schema 是为了能回答"这个包是怎么来的"，不是为了给它裁决权。

理由：一次"刚聊完之后的倾倒"照样会吐出多年前形成、只是刚被召回的旧记忆；另一个端晚几分钟倾倒，也可能只是重新描述更旧的状态。**包的产生背景不能变成包内每个条目的事实时间。**

增量包也不行。"这条第一次出现在增量包里"只证明**本次召回了它**，不证明它是这段时间新形成的——上次没吐出来可能只是没召回。

能裁决的依据见 `consolidate.md`，都是条目级的。

### 正文结构

```markdown
## 导出边界与已知限制

## 可访问的持久记忆
### 身份与事实
### 正在进行的事
### 判断方式与价值排序
### 明确否决、负向约束与原因
### 沟通偏好与用户纠正
### 零散但可能跨场景复用的信息

## 记忆中的过期项、矛盾与不确定项

## 非原生记忆来源
### 当前会话现场推断
### 已加载的知界文件
### 项目文件、自定义指令或其他外部资料

## 本端无法确认的内容
```

**"持久记忆"和"当前会话或外部文件中现推的"必须分开。** 来源不确定时放进"非原生记忆来源"或"无法确认"，不许冒充原生记忆——混在一起，冲突消解那步就没法工作。

条目尽量带：原话、事实发生时间或用户陈述时间、`supersedes` / `retracts` 关系。这些是唯一能参与裁决的信息，采集时多要一点，整合时少一次待确认。

## 消费 manifest

`dumps/processed/manifest.md` 记录**哪个统一版本消费了哪些 `dump_id`**：

```markdown
## v7 · 2026-08-11 · 协调者：claude-code
消费：
- d86d62ca-23a5-4d28-8a1d-25774f150cec  (chatgpt-web, baseline)
- 4f1e7b90-88c2-4a13-9e55-0b2c6d31aa87  (codex-cli, incremental)
拒绝（终态，不再进候选集）：
- 9c02f5aa-1d34-4bb7-8e61-77ab0d9e4c15  (claude-code, verification)
  —— 探测包，用户明确不批准入档 · 2026-08-11
```

**记账一律用 `dump_id`**，括号里的端和类型只是给人看的。

三种状态，缺一不可：

| 状态 | 含义 |
|---|---|
| **未列出** | 还在候选集里，下一轮合并要处理 |
| **消费** | 已被某个成功发布的版本吸收 |
| **拒绝** | **终态**。用户明确不要它入档，不再进候选集 |

**"拒绝"这一档必须有。** 没有它，用户否掉的探测包每一轮都会重新冒出来要求处理——用户拒绝一次，就得永远拒绝下去。拒绝要写日期和原因。

**一个包只有进了消费或拒绝，才算处理完。** 在那之前它一直在候选集里，无论后面又来了多少新包。

这条和"包不可变"是一对：不可变保证信息不丢，manifest 保证不重复消费。缺任何一半都不成立。

### 第一版发布门槛：两个不同端的 baseline

实例仓还没有当前统一版本时，第一次发布必须同时满足：

- inbox 中至少有两个**不同 `endpoint_id`** 的格式合规 baseline；同端多包只算一端
- 这些 `endpoint_id` 已登记在 `config.md`；未登记端的包不能凑数
- 已有 profile、记忆导出和其他旧资产只作为合并原料，不能替代第二端
- 空内容的 baseline 只要格式合规就算完成——它是“该端当前没有可输出记忆”的真实结果

用确定性检查先拦一遍：

```text
python scripts/validate_dump.py --cold-start-ready <实例仓路径>
```

脚本负责校验包并按 `endpoint_id` 去重；协调者再对照 `config.md` 确认这些端都已登记。任一条件不满足时，**不发布统一文件、不写消费或拒绝状态**，所有包继续留在候选集。

这不是日常合并的批量门槛。第一版统一资产存在后，一个端的新 incremental 可以单独触发下一版发布。

### 脱敏记账：`redaction_events`，跟消费状态平行

**脱敏不是第四种消费状态。** 一个已经被消费的包照样可能在几个月后被脱敏——两件事发生在不同时间轴上，塞进同一个字段就表达不了。

所以 manifest 里单开一节，跟上面那三种状态平行：

```markdown
## redaction_events

- dump_id: d86d62ca-23a5-4d28-8a1d-25774f150cec
  redacted_at: 2026-09-03T14:22:00+08:00
  published_in: v11                      # 承载这次脱敏的统一版本
  scope: "「身份与事实」下 3 个条目"       # 粗粒度，不含原文
  content_revision: 2                    # 首次入库隐含为 1，第一次脱敏记 2
```

**不要在这里写这次发布的 commit hash。** hash 由提交内容算出，而把 hash 写进 manifest 又会改变提交内容——自引用，同一个提交里不可能满足。也不需要：**manifest 本身就在那个提交里**，Git 历史自然能定位到引入该事件的 commit。条件发布要用的是**已知的 `base_commit`**（发布前读到的那个），不是尚未产生的新 commit——那个在 `config.md` 里。

**`content_revision` 让同一个 `dump_id` 的内容修订可追踪。** `dump_id` 仍然表示**逻辑包身份**（消费记账、`previous_dump_id` 引用都不受影响）；有了这个字段，"这个包的内容跟首次入库时不一样"就成了一件被声明过的事，而不是一个悬案。

**但它证明不了合法性。** 有写权限的人可以在改内容的同时把这个字段一起改掉，而校验器目前也不交叉验证它。**变更是否合法，依据是 Git 历史、原子发布记录和用户的确认记录**——`content_revision` 只是让人知道该去查这几样东西。

**脱敏走完整的发布流程**：改原包、`evidence.md`、`review/`、manifest、版本号必须在**同一个提交**里，并接受基础版本检查。理由跟普通发布一样，而且更急——脱敏做到一半被别人读到，部分文件已经指向不存在的内容了。

## 发布：基础版本检查

**一次发布是一个不可拆分的提交。**

一次发布至少要改三样东西：统一文件、`config.md` 里的当前版本号、`dumps/processed/manifest.md`。**它们必须落在同一个 commit 或同一次 PR 合并里。**

**脱敏也是一次发布**，同样规矩：原包、`evidence.md`、`review/`、manifest、版本号一起进同一个提交，被基础版本检查拦下就重读重来。

逐文件提交会产生外人可见的中间态：

> 另一端在两次提交之间读到了**新画像 + 旧 manifest** —— 它会认为那些包还没被消费，于是重新合并一遍。
> 或者反过来：**旧画像 + 新 manifest** —— 那些包被当成已处理，内容永远进不了档案，**而且没有任何痕迹**。

后者是静默丢数据，比重复消费严重得多。

**所以"能不能多文件原子提交"是一条端能力，必须实测**，进 GH-04。

> **下游后果**：如果某个端的连接器只能逐文件提交，它就**不能当协调者**——只能当倾倒端。这可能砍掉"任意端可接任协调"对网页端的适用性，让协调实际上只发生在本地端。真测出来是这样，就在 `config.md` 里如实记下哪些端有协调资格，不要嘴上说"任意端"、实际只有一个端能干。

---

**核心约束：读取当前版本、合并、写回，这三步之间锚点不能被别人动过。**

版本号本身只提供**观察**，不提供**互斥**。两个端都读到 v5、都确认"仍是 v5"、然后分别覆盖同一份文件——最后写的那个仍然会静默盖掉前一个。这是经典的检查-写入竞态，多加几行"再查一次"也解决不了。

**所以锚点必须提供可验证的条件写入，这是锚点准入的第三条能力**（前两条是读得到、写得进）。

MVP 锚点是 GitHub 私有实例仓，三条可用路径，选一条并记进 `config.md`：

| 路径 | 怎么保证 | 代价 |
|---|---|---|
| **条件直写** | 提交时带 base commit，远端已前进则拒绝（非强制推送本身就是一次比较并交换） | 需要该端的连接支持带 base 的提交 |
| **端专属分支 + PR** | 每端只写自己的分支，合并动作串行 | 多一步合并 |
| **仓库自动化串行发布** | 发布交给唯一的自动化通道 | 依赖平台自动化 |

**被拒绝不是错误，是协议正常工作。** 撞上版本前进时：重新读取当前版本、重新合并、重新提交。不许强制覆盖，不许"合并结果已经算好了，直接推上去"。

其他后端以后各自实现同一个接口。**在实现之前，一行台账版本号不等于满足了这条**——别用它假装安全。

## 通道验证：能看见 ≠ 能写入

每个端首次接入必须实际跑一遍，**不接受模型口头声称"我可以访问 GitHub"**。

| # | 动作 | 通过条件 |
|---|---|---|
| **GH-01** | 通过仓库所有者与名称或链接找到实例仓，读取协调端预先创建的检查文件 | 不同端从同一默认分支读到同一唯一内容和提交标识 |
| **GH-02** | 在自己的 `dumps/inbox/<endpoint-id>/` 创建一份唯一文件并提交 | 文件出现在正确目录，取得可回查的提交或 PR 标识 |
| **GH-03** | 立即重新读取 GH-02 那份文件 | 内容可读，没有被格式转换或截断到影响解析 |
| **GH-04** | 逐项测读取、搜索、创建提交、更新文件、创建 PR、合并 PR，**以及一次提交里改多个文件** | 逐项记录。只能读不能提交倾倒包的连接**不算完成接入**；不能多文件原子提交的端**没有协调资格**，只能当倾倒端 |
| **GH-06** | 用一个过期的基础版本尝试发布 | **必须被拒绝。** 拒绝是协议正常工作；直接覆盖成功说明这一端的发布路径不安全，不能让它协调 |
| **GH-05** | 确认仓库保持私有 | 未把仓库或倾倒内容公开。**路径级写权限隔离不用逐端测——GitHub 给不了，见下** |

结果写进 `state/endpoints/<endpoint-id>.md`。

### "来源端只写自己的收件区"在 GitHub 上永远是协议约束

**[实测 2026-08-12]** 两条路都试过，都不通，但不通的原因不同：

- 免费账号的**私有**仓配不了分支保护，`PUT /repos/.../branches/main/protection` 和 `POST /repos/.../rulesets` 都返回 403，要求升级 GitHub Pro
- **但升级也解决不了。** 分支保护的粒度是**分支级**——谁能推、要不要 PR、要不要审查——**GitHub 没有路径级 ACL**，做不到"这个协作者只能写 `dumps/inbox/<他自己的 id>/`"

加上多数平台的 GitHub 连接是**仓库级授权**，给的就是全仓写权限。所以这条在 MVP 里是**协议约束，不是技术隔离**，而且不是"暂时配不上"，是**这条路本身不通**。

真正的技术隔离只有一条路：**服务端校验**（GitHub App 或 Action 检查本次提交只动了自己 id 的目录，越权就拒）。要写代码、要部署，**MVP 不做**。

**必须对用户说明白两件事**：这道墙不存在；以及**别为这个升级 Pro，升了也没用。**

**但单一信源不变量不依赖它。** 防静默覆盖的是**条件写入**（基础版本检查，GH-06），那由 Git / API 层保证，跟分支保护无关。ACL 缺失只放过一种情况：某个没有协调资格的端"好心"改了统一文件，而基础版本恰好没被人动过——条件写入拦不住这种，只能靠协议纪律拦。代价可控，因为**实例仓是 Git，越权写入事后可完整回溯和回滚**，而这里的威胁模型是"模型走错格子"，不是恶意协作者。
