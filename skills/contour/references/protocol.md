# 协议 · 数据面与介质边界

这份文件管**格式与发布安全**：倾倒包长什么样、什么时候算被处理、发布怎么避免静默互相覆盖。

它是 `dump.md`（写方）和 `consolidate.md`（读方）共享的唯一规范——两边有分歧时以本文为准。语义判断（这条归哪层、冲突怎么解）在 `consolidate.md`，触发时机（谁在什么时候跑）在 `drive.md`。

## 核心契约

知界核心只要求：配置记录用户选择的**档案位置**及实际使用过的接入方式；执行者能读取已发布档案、提交记忆存储的内容、读取待处理内容，并在有满足发布条件的方式时发布新的统一结果。发布条件见下文「发布条件」：统一结果与消费记录同时生效、基于过期内容的发布被拒绝或串行化、发布后可回读核对。

工具和通道由执行者按现场条件选择，只要保持同一授权范围、同一档案位置和相同数据语义；能否做到，以实际操作和回读结果为准。

## 档案文件布局

```text
<档案根目录>/
├── config.md                          # 稳定实例配置
├── profile.md                         # 慢变画像
├── now.md                             # 快变用户状态
├── routing.md                         # 常驻：沟通路由 + 记忆关注策略
├── sources.md                         # 动态信源路由 + 知识资产路由
├── evidence.md                        # 证据、来源、取代与撤回关系
├── tests.md                           # 隐藏题库，不进被测端上下文
├── state/
│   ├── stores/<store-id>.md           # 每个记忆存储一份：采集记录与倾倒游标
│   └── endpoints/<endpoint-id>.md     # 每个使用端一份：送达、读取与加载状态
├── dumps/
│   ├── inbox/<store-id>/<captured-at>__<dump-type>__<dump-id>.md
│   └── processed/manifest.md          # 哪个统一版本消费了哪些包
└── review/                            # 冲突、待确认、撤回、失败恢复
```

当前文件布局使用小写文件名，保持跨平台引用一致。

**按写入范围分开文件是布局的骨架：**

| | 写入内容 | 冲突面 |
|---|---|---|
| `config.md` + 七份统一文件 | 当轮发布统一结果的执行者 | 靠基础版本检查串行 |
| `state/stores/<id>.md` | 只写该记忆存储的采集状态 | 存储之间无冲突；**同一存储并发见下** |
| `state/endpoints/<id>.md` | 只写该使用端的加载状态 | 使用端之间无冲突；**同一使用端并发见下** |
| `dumps/inbox/<id>/` | 只放该记忆存储的包，且只新建 | 无冲突——只新建，不改旧的 |

**记忆存储与读取者分开记录。** `store_id` 和收件区表示内容属于哪个记忆存储，`collected_via` 记录由谁读取。经用户授权的任何端或工具（例如 MCP 服务或自动化）都可以读取某个存储、提交它的包或维护它的状态，但必须保持该存储的来源语义；不能把一个存储的内容记在另一个存储名下。

把游标塞进任何一份共享文件（`now.md` 或 `config.md` 都一样）会制造并发热点：一次正常同步同时改统一画像、处理状态和中央台账，冲突面无谓地扩大。**倾倒游标属于记忆存储，加载状态属于使用端，各住各的文件。**

**"每个存储或使用端一份文件"不等于没有并发。** 同一个产品可以同时开两个会话——两个 Claude Code 窗口各跑一次同步，写的是同一份 `state/stores/claude-code-local.md`，后写的会盖掉先写的游标，于是有一次倾倒的记录凭空消失，下一轮该存储看起来落后了一版。

所以**状态文件的写回也要走条件写入**，跟统一文件同一条规矩：读的时候记下基础版本，写的时候带上，被拒就重读重写。它比统一文件便宜得多——冲突时直接重取当前状态、重新填自己这一轮的字段即可，不需要重新合并任何东西。

倾倒包不受影响：它只新建、不改旧的，两个会话各产一个包都进候选集，正是想要的行为。

## 记忆存储与使用端

知界分开两种标识：

- **记忆存储**（`store-id`）：某个 AI 实际保存用户记忆的位置。倾倒包、首发门槛和倾倒游标都按它记。
  - **本地存储**：本机上的记忆文件或目录，例如 Claude Code 的 `~/.claude/`、Codex 的 `~/.codex/`。
  - **云端存储**：某个账号在平台上保存的记忆。
- **使用端**（`endpoint-id`）：用户实际使用、需要读取统一结果的产品入口。送达、当前会话读取和原生记忆状态都按它记。

本地或云端只描述记忆所在位置，不决定采集方式，也不预设哪种工具可用。执行者根据用户授权和该存储当前实际可访问的途径选择方式，例如直接读取文件、平台对话中自述、官方导出、接口或 MCP；授权不等于已经具备访问能力。无论用哪种方式，都在包里如实记录 `collected_via`、`source_method` 和覆盖范围，不把部分可见的资料说成完整记忆。

每个使用端默认有自己的记忆存储。不按账号、厂商推定两个使用端共用记忆；只有用户明确确认两个端是同一份记忆时，才把它们登记到同一个存储。

登记示例：

```text
记忆存储              类型    对应使用端
claude-code-local     本地    claude-code
codex-local           本地    codex-cli
claude-ai-personal    云端    claude-ai-web
chatgpt-personal      云端    chatgpt-web
```

两种标识都不含模型名。模型名、版本、账号范围、项目范围都是**每次倾倒的元数据**。换个模型不是换了一个存储或端——把模型写进 ID，换模型时全部历史游标会突然失配，看起来像新存储接入。

同一产品用两个账号（个人 / 工作）是两个云端存储，后缀区分。

## 倾倒包

### 身份：`dump_id`，不是文件名

**包的唯一身份是 frontmatter 里的 `dump_id`，一个 UUID4。** 文件名、时间戳、路径都只是让目录可读，**任何地方记账都用 `dump_id`**——消费 manifest、`previous_dump_id`、状态文件里的游标，一律如此。

文件名把它带上，是为了肉眼也能对上号：

```text
dumps/inbox/<store-id>/<captured-at>__<dump-type>__<dump-id>.md
```

`captured-at` 用带时区的 ISO 8601；文件系统不接受冒号时用连字符替代。

**`store-id` 会被拼进路径，所以字符集必须封死**：小写字母、数字，单个连字符分隔；`endpoint-id` 与 `collected_via` 沿用同一字符集（`\A[a-z0-9]+(?:-[a-z0-9]+)*\Z`）。不限制的话 `../escaped` 这种值会把包写到收件区之外，而校验只扫收件区，看不见它。

同一批输入中的 `dump_id` 必须唯一，防止消费记录混淆。

**包一旦写入就不可变。** 不改内容、不删除、不因为有了新包就退出候选集。

**唯一的例外是用户明确要求的脱敏。** 不可变是**合并流程的纪律，不是对抗数据所有者的权利**——用户要清掉自己的数据时必须能清。

它是一个需要单独确认的独立动作，走完整的发布流程（满足下文的发布条件），并在 manifest 的 `redaction_events` 里留痕。代价和保证边界见 `consolidate.md` 的撤回一节。**脱敏过的包，`content_revision` 会 +1**（首次入库隐含为 1）——它让"内容与首次入库不同"成为一件被声明过的事，至于那次变更合不合法，查档案位置的版本记录和用户确认记录。

自述可能只召回部分内容，新包不保证包含旧包；未处理的旧包继续保留。

**去重在条目层做，不在文件层做。** 重复条目合并来源引用，包本身各自留着。

同一存储由不同端读取的多个包，来源都记在该存储名下；它们不会因为读取者不同而变成两个存储，内容也不会因此被丢弃。

### frontmatter

```yaml
---
schema_version: contour-dump-v2
dump_id: <全局唯一>
store_id: <记忆存储标识>
collected_via: <执行读取的使用端 endpoint-id 或工具名；未知写 unknown>
provider: <记忆存储所属厂商；未知写 unknown>
model: <执行采集的模型；未知写 unknown>
captured_at: <带时区时间>
dump_type: <baseline / incremental / verification>
trigger: <user / probe>
memory_scope: <global / project / workspace / mixed / unknown>
source_method: <native-view / model-self-report / export / file-memory / mixed>
contour_context_loaded: <true / false / unknown>
last_contour_revision_read: <该存储所在的使用端最后读到的统一版本；没有写 null>
previous_dump_id: <增量包引用同一存储的上一个包；没有写 null>
---
```

`contour-dump-v1` 的旧包仍然有效，也不改写。它按端记录（`endpoint_id` 与 `surface`），端标识与存储标识不同，计数前须按 `config.md` 的使用端表换算成 `store_id`，才能和 v2 包一起去重；对应关系无法确定时，该包的存储身份待确认，不计入首发门槛。`surface` 只是 v1 字段，当前生成器不再使用。新包一律使用 v2。

三类 `dump_type`：

- **baseline** —— 记忆存储首次纳入，描述该存储当前可访问的全部记忆视图
- **incremental** —— 后续，输出自上次成功倾倒以来新增、更正、失效或值得重新确认的内容
- **verification** —— 探测用，不进正式画像，除非用户明确批准

`trigger` 记录本次倾倒由什么发起：`user` 是用户在本轮的请求，`probe` 是探测检查。它不表示授权依据，授权范围见 `config.md` 与 `drive.md`。

`contour-dump-v2` 只定义这两个值。定时任务或钩子自动发起的倾倒属于后续范围；需要支持时以新的 schema 版本增加取值，不把自动发起的包记为 `user` 或 `probe`。

### `captured_at` 和 `trigger` 不能裁决事实新旧

**这两个字段只用于审计、调试和分析召回条件。** 写进 schema 是为了能回答"这个包是怎么来的"，不是为了给它裁决权。

理由：一次"刚聊完之后的倾倒"照样会吐出多年前形成、只是刚被召回的旧记忆；另一个端晚几分钟倾倒，也可能只是重新描述更旧的状态。**包的产生背景不能变成包内每个条目的事实时间。**

增量包也不行。"这条第一次出现在增量包里"只证明**本次召回了它**，不证明它是这段时间新形成的——上次没吐出来可能只是没召回。

能裁决的依据见 `consolidate.md`，都是条目级的。

### 正文结构

```markdown
## 导出边界与已知限制

## 可访问的持久记忆
### 身份与事实
### 正在进行的事
### 判断方式与价值排序
### 明确否决、负向约束与原因
### 沟通偏好与用户纠正
### 零散但可能跨场景复用的信息

## 记忆中的过期项、矛盾与不确定项

## 非原生记忆来源
### 当前会话内容与推断
### 已加载的知界文件
### 项目文件、自定义指令或其他外部资料

## 本端无法确认的内容
```

**"持久记忆"和"当前会话或外部文件中现推的"必须分开。** 来源不确定时放进"非原生记忆来源"或"无法确认"，不许冒充原生记忆——混在一起，冲突消解那步就没法工作。

自述提示中的来源标注按以下方式归入正文：未推断的 `[记:原生记忆]` 进「可访问的持久记忆」；其他 `[记:<类型>]` 进「项目文件、自定义指令或其他外部资料」；`[会话]` 和带 `[推]` 的条目进「当前会话内容与推断」；`[来源不明]` 进「本端无法确认的内容」，保留未知，不改记为推断。

条目尽量带：原话、事实发生时间或用户陈述时间、`supersedes` / `retracts` 关系。这些是唯一能参与裁决的信息，采集时多要一点，整合时少一次待确认。

### 包的确定性校验

任何工具都可以执行下列检查，只要给出同样的结论。

**内容与来源字段**（包放在哪里都适用）：

- 文件能按 UTF-8 读取；无法解码时记为不合规输入，不猜测编码，也不当成空内容；
- 以 frontmatter 开头，上文字段齐全，枚举字段取值在上文范围内；
- 必填字段都有值：`provider`、`model`、`collected_via`、`memory_scope`、`contour_context_loaded` 未知时写 `unknown`，`last_contour_revision_read`、`previous_dump_id` 没有时写 `null`，其余字段不能留空；空白不算未知；
- `dump_id` 是 UUID4，`captured_at` 是带时区的 ISO 8601；
- `store_id` 与 `collected_via` 符合上文字符集，且不含模型名（v1 包检查 `endpoint_id`）；
- `incremental` 包带 `previous_dump_id`；
- 正文包含「导出边界与已知限制」「可访问的持久记忆」「记忆中的过期项、矛盾与不确定项」「非原生记忆来源」「本端无法确认的内容」五个二级章节。

**批次**：同一批输入中 `dump_id` 不重复；撞号的各个包都不计入门槛，也不进入消费记录。

**入库位置**（只适用于受管收件区中的包）：包位于 `dumps/inbox/<store_id>/`，目录名与 `store_id` 一致（v1 包为 `endpoint_id`）。临时下载或工具返回、尚未入库的包只做前两类检查。

校验通过只说明格式合规，不能代替来源真实性、存储登记或发布结果的核对。不合规的包不进入本轮整合，原因记入 `review/`，由用户决定重新提交还是标为拒绝；它不影响其他相互独立的有效包。

`scripts/validate_dump.py` 是这些检查的本地实现：

- 给出单个或多个路径时做内容与批次检查，路径位于 `dumps/inbox/` 下时加查入库位置；一个文件读取失败不影响其他文件继续检查。
- `--inbox <档案根目录>` 检查整个收件区。
- `--cold-start-ready <档案根目录> [--store-map <endpoint-id>=<store-id> ...]` 先输出“格式检查”，再输出“首发门槛”：按存储去重计数合规 baseline；v1 旧包用 `--store-map` 给出的对应关系换算成 `store_id`，没有给出时列为“存储身份待确认”，不计入。

退出码：0 通过（`--cold-start-ready` 时表示已有至少两个不同存储的合规 baseline）；1 有不合规，或门槛未满足、存储身份待确认；2 用法错误。`[READY]` 不包含存储是否已登记的核对。

`scripts/new_dump.py` 生成带新 `dump_id`、带时区时间和收件区路径的空包；`collected_via` 与 `source_method` 须由调用者按实际采集给出。

## 消费 manifest

`dumps/processed/manifest.md` 记录**哪个统一版本消费了哪些 `dump_id`**：

```markdown
## v7 · 2026-08-11 · 发布者：claude-code
消费：
- d86d62ca-23a5-4d28-8a1d-25774f150cec  (chatgpt-web, baseline)
- 4f1e7b90-88c2-4a13-9e55-0b2c6d31aa87  (codex-cli, incremental)
拒绝（终态，不再进候选集）：
- 9c02f5aa-1d34-4bb7-8e61-77ab0d9e4c15  (claude-code, verification)
  —— 探测包，用户明确不批准入档 · 2026-08-11
```

**记账一律用 `dump_id`**，括号里的端和类型只是给人看的。

三种状态，缺一不可：

| 状态 | 含义 |
|---|---|
| **未列出** | 还在候选集里，下一轮合并要处理 |
| **消费** | 已被某个成功发布的版本吸收 |
| **拒绝** | **终态**。用户明确不要它入档，不再进候选集 |

用户明确拒绝的包不再进入后续候选集；拒绝记录包含日期和原因。

**一个包只有进了消费或拒绝，才算处理完。** 在那之前它一直在候选集里，无论后面又来了多少新包。

这条和"包不可变"是一对：不可变保证信息不丢，manifest 保证不重复消费。缺任何一半都不成立。

### 第一版发布门槛：两个不同记忆存储的 baseline

档案还没有当前统一版本时，第一次发布必须同时满足：

- inbox 中至少有两个**不同 `store_id`** 的格式合规 baseline；同一存储的多个包只算一个，无论由哪个端读取
- 这些 `store_id` 已登记在 `config.md`；未登记存储的包不能凑数
- v1 旧包先按 `config.md` 对应到 `store_id` 再与 v2 包一起去重计数；对应关系无法确定时存储身份待确认，不计入
- 能核对出自某个存储的记忆文件、官方导出或接口返回，可以作为该存储的 baseline，`source_method` 按实际方式如实填写
- 用户自己的画像，以及来源或日期无法核对的旧资料，只作为合并原料，不算记忆存储
- 空内容的 baseline 只要格式合规就算完成；它只记录本次未导出内容，不证明该存储没有其他记忆

不合规或撞号的包按上文「包的确定性校验」排除，不计入门槛；它们不阻断其他存储的有效 baseline。

本地能运行 Python 时，可以先用脚本校验包并按存储去重，再由执行者对照 `config.md` 确认这些存储都已登记；有 v1 旧包时，把 `config.md` 中的对应关系逐个传给脚本：

```text
python scripts/validate_dump.py --cold-start-ready <档案根目录> [--store-map <endpoint-id>=<store-id> ...]
```

不能运行时，用能给出同样结果的其他方式核对。任一条件不满足时，**不发布统一文件、不写消费或拒绝状态**，所有包继续留在候选集。

这不是日常合并的批量门槛。第一版统一资产存在后，一个存储的新 incremental 可以单独触发下一版发布。

### 脱敏记账：`redaction_events`，跟消费状态平行

**脱敏不是第四种消费状态。** 一个已经被消费的包照样可能在几个月后被脱敏——两件事发生在不同时间轴上，塞进同一个字段就表达不了。

所以 manifest 里单开一节，跟上面那三种状态平行：

```markdown
## redaction_events

- dump_id: d86d62ca-23a5-4d28-8a1d-25774f150cec

```

**`published_in` 写统一版本号，不写这次发布自身的存储版本标识。** 有的档案位置用保存内容算出版本标识，把它写进 manifest 会改变内容本身，无法自洽。条件发布要用的是发布前读到的基础版本，不是尚未产生的新版本。

**`content_revision` 让同一个 `dump_id` 的内容修订可追踪。** `dump_id` 仍然表示**逻辑包身份**（消费记账、`previous_dump_id` 引用都不受影响）；有了这个字段，"这个包的内容跟首次入库时不一样"就成了一件被声明过的事，而不是一个悬案。

**但它证明不了合法性。** 有写权限的人可以在改内容的同时把这个字段一起改掉，而校验器目前也不交叉验证它。变更是否合法，依据档案位置的版本记录、发布记录和用户的确认记录；所选档案位置须保留这些可审计的依据。`content_revision` 只是让人知道该去查这些记录。

**脱敏走完整的发布流程**：改原包、`evidence.md`、`review/`、manifest、版本号必须作为同一次发布同时生效，并接受基础版本检查。理由跟普通发布一样，而且更急——脱敏做到一半被别人读到，部分文件已经指向不存在的内容了。

## 发布：基础版本检查

### 发布条件

任何档案位置、任何工具的发布都要满足：

1. **同时生效**：统一文件、当前版本号和消费记录一起生效，其他端不会读到只更新了一部分的中间状态；
2. **不覆盖**：基础版本在读取之后发生变化时，这次发布被拒绝或进入串行队列，不静默覆盖；
3. **可回读**：发布后读回实际保存的结果并核对。

选择发布方式看能否满足这三条，不看工具名称或是否暴露某个特定接口。

### 为什么要同时生效

一次发布至少要改三样东西：统一文件、`config.md` 里的当前版本号、`dumps/processed/manifest.md`。脱敏也是一次发布：原包、`evidence.md`、`review/`、manifest、版本号一起生效。

逐个文件分别生效，会产生其他端可见的中间态：

> 另一端在两次写入之间读到了**新画像 + 旧 manifest** —— 它会认为那些包还没被消费，于是重新合并一遍。
> 或者反过来：**旧画像 + 新 manifest** —— 那些包被当成已处理，内容永远进不了档案，**而且没有任何痕迹**。

所以一组互相依赖的统一文件不能逐个分别写入。只往收件区新建一个倾倒包这类单文件写入，本来就不需要同时生效。

### 为什么要条件写入

**核心约束：读取当前版本、合并、写回，这三步之间档案不能被别人改过。**

版本号本身只提供**观察**，不提供**互斥**。两个端都读到 v5、都确认"仍是 v5"、然后分别覆盖同一份文件——最后写的那个仍然会静默盖掉前一个。这是经典的检查-写入竞态，多加几行"再查一次"也解决不了。

发布要用档案位置提供的条件写入或串行机制：写入时带上发布开始时读到的基础版本，基础版本已经变化就拒绝这次写入。

```text
发布者 A                         发布者 B
读到基础版本 X                    读到基础版本 X
合并，带着 X 写入  ✅
   档案变为 Y                     合并，带着 X 写入  ❌
                                    基础版本已是 Y → 拒绝
                                    → 重读 Y，重新合并，重来
```

`config.md` 里的版本号给人看这是第几版，不承担互斥。**一行台账版本号不等于满足了条件 2**——别用它假装安全。

**被拒绝不是错误，是协议正常工作。** 撞上版本前进时：重新读取当前版本、重新合并、重新发布。不许强制覆盖，不许"合并结果已经算好了，直接写上去"。

当前工具不能满足发布条件时，改用其他能提供同等保证的工具或方式，并在 `config.md` 记录其依据；仍无法发布时保留待处理状态并说明缺口。

## 来源端写入范围

某个记忆存储的包只提交到该存储的收件区，无论由哪个获授权的端或工具写入；统一结果按发布规则修改。不要假设档案位置的整体写权限已经提供按目录隔离；权限范围以实际授权和所用执行机制为准。

需要技术隔离时，由所选实现校验写入范围，并记录其实际能力。
