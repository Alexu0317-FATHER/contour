# 实例文件的结构与写作规范

空白骨架在 `assets/templates/`；档案文件布局的完整结构和写入范围在 `protocol.md`。本文件定义字段及跨文件写作约定。

---

## 通用约定

### 时效标记

事实型条目后缀写明何时为真：`小学三年级（2025-07 时点）`。

时效不明的条目可能在后续使用时被误当作当前事实。知道确切时间就写；不知道时可写模糊时间（如 `2025 年初`）或标为未知。

### 待确认

来自冲突消解、尚未得到用户答复的条目，写成：

```
[待确认] 主力 AI 工具  ← Codex 记为 A，Claude Code 记为 B，两边都没有条目级时间依据
```

标记要带**冲突的双方和来源**，不能只写"待确认"。下次问用户的时候，你需要的正是这些。

明细放在 `review/`，正文保留待确认标记和引用。

### 取代与撤回

```
superseded by E-041 · 2026-08-11        # 正常演化，旧条目留着
[已撤回 2026-08-11] · 主题：<粗粒度>     # 用户要求移除，原文不保留
```

两者语义不同：取代是"这条过时了"，撤回是"这条不该在这儿"。**不要用取代来实现撤回**——取代会把原文留在文件里。

### 证据编号

`evidence.md` 用 `E-001` 起递增，**编号永不复用**（归档压缩后也不回收）。结论侧用 `← E-023, E-041` 回指。

### 断言句，不是建议句

写「不要用鼓励式话术开场」，不写「他可能不太喜欢被鼓励」。

对需要执行的约束，使用能明确表达动作和边界的句子。

### 别写礼貌话

直接写需要执行的动作、条件和依据，省略寒暄及重复提醒。

### 语言

采用用户日常使用的语言，保留必要的技术名称和原始引用。

## 各文件要点

### `profile.md` —— 慢变人格层

四节：**价值排序 / 判断路径 / 能力画像 / 负向约束**。

价值排序要写成有序的，不是并列的形容词堆。「稳定性 > 收益」比「重视稳定，也追求收益」有用得多——冲突的时候前者能判，后者不能。

判断路径写他**怎么**做决定，不是他决定了什么。

能力画像要带证据强度：亲眼见过成品的，和他自己提过一句的，不是一回事。

负向约束单列一节，避免与正向偏好混写。

每条结论带 `← E-xxx`。追不到出处的不进这个文件。

### `now.md` —— 快变用户状态

**文件头第一行写"最后更新：YYYY-MM-DD"。** 它帮助判断状态是否可能过期，但不替代来源、条目时间和实际查证。

按条目实际变化频率和问题对最新性的要求决定是否查证。有明确有效期或更新周期时记录；无法确定时标明资料时间，不推定固定过期天数。

内容：活跃项目、当前目标进度、健康与精力、家庭动态。**只装用户状态**——基础设施状态（档案位置、各端游标、探测结果）不在这里，见下面 `config.md` 和 `state/`。

条目可以删。过期状态在 `evidence.md` 留下必要出处后，可从正文移除，避免新旧状态并列。

### `sources.md` —— 两个分区

记录查询入口、资料位置及适用范围，不复制完整外部资料。最后验证时间表示最近一次实际核对；位置或权限变化后按需重新核对。

写法见 `consolidate.md` 第五节。两个区的结构不同：

**动态信源路由**（去哪拿最新事实）用表格，按信息领域组织，每条至少：识别线索、首选权威来源、需要时的深入来源、最后验证时间。`来源不可用时` 一列只在该领域有指定的备用来源或特殊处理时填写，通用的查找与恢复由模型现场判断。

**知识资产路由**（已经沉淀过什么）用记录块，编号 `A-001` 起递增、**永不复用**（跟 `E-xxx` 同规矩）。必填五键：

```text
### A-003 · <主题>
- **调用线索**：主题词、同义说法、场景、用户对它的模糊指称
- **权威资产**：<系统 + 位置 + 标题>
- **覆盖范围**：正面覆盖什么，**以及不含什么**
- **来源记录**：<端> <创建/更新> <日期> · <dump_id>（可多条）
- **最后验证**：YYYY-MM-DD
```

可选键：

- `超出覆盖时`：这份资产指定了下一跳时才写，例如用户约定超出范围先查某份文档。
- `来源不可用时`：这份资产有指定的备份位置或恢复方式时才写。
- `特殊说明`：这份资产独有的使用限制。
- `状态`：`待复核 · <日期> 收到更新报告`、`superseded by A-007 · <日期>` 或 `[已撤回 <日期>] · 主题：<粗粒度>`。

通用的查找与恢复不逐条写入记录。

**修改报告不等于验证。** 只能看到某端“我改过”的倾倒时，追加来源记录并标 `待复核`，不要改覆盖范围，也不要刷新最后验证；实际重新读取资产后才更新这两项并移除待复核状态。

五个必填键都保留；缺信息时写 `未知` 或 `未验证`，不要省略该行。

**超出覆盖和来源不可用是两种情况，分开处理。** 前者是资产可读但不覆盖问题；后者是原位置无法读取，需要报告并检查路由。

### `config.md` —— 稳定配置

档案位置类型与位置、存储布局／格式约定、实际使用过的接入方式及结果、纳入的记忆存储与使用端、权限边界、发布方式及其依据、初始化状态、当前统一版本。

档案位置记录用户的选择，不以已有专属实现的名单限制可选位置。存储布局／格式约定记录同一档案的逻辑对象如何落在该位置；接入方式和发布方式按实际操作记录。接入记录不能用初始化时的一次能力探测锁定后续执行端的路径；每个端在需要读取、整合或发布时重查当前可用能力。发布方式须满足 `protocol.md` 的发布条件，并写明依据和验证日期，尚未验证写“未验证”。

记忆存储与使用端分两张表登记：存储表记类型（本地 / 云端，只描述位置）、位置或账号、baseline 的 `dump_id` 与状态；使用端表记产品表面和它使用的记忆存储。每个使用端默认有自己的存储，不按账号或厂商推定共用，规则见 `protocol.md`。v1 旧包按使用端表换算成 `store_id`。

权限边界分开记录日常同步可直接采集的存储与范围、每次需确认的范围和明确排除的来源。已登记不等于已授权采集；已写明的日常授权在同步时直接复用。

每个纳入的记忆存储都要记录 baseline 的 `dump_id`，不能只写一个无法追责的“已完成”。基线取得、统一版本保存和各使用端加载分开记录：前两项在本文件，存储的采集记录在 `state/stores/`，使用端加载在 `state/endpoints/`。初始化状态只描述前两项，只允许三种语义：

- **等待第二个记忆存储**：还没有两个不同的已登记记忆存储有合规 baseline；只保存配置、状态和未消费包，不得生成统一文件、草稿画像或消费包
- **暂定版本**：统一版本已按发布条件保存并回读核对，消费了至少两个不同已登记记忆存储的 baseline；仍有已登记存储没有 baseline，或其 baseline 尚未被统一版本消费
- **冷启动完成**：所有已登记记忆存储的 baseline 都已被一个保存并回读核对的统一版本消费，无法解决的冲突已记入 `review/`

这些状态不表示各使用端已送达或已读取统一结果；报告完成情况时，加载状态按使用端分别说明。

第一版统一资产尚未发布时，当前统一版本明确写“尚未发布”，不要用 `v0` 假装已经有可加载的统一结果。两个存储的门槛不区分本地或云端；空内容但格式合规的 baseline 也算，但不代表该存储没有其他未导出的记忆。

配置变更记录时间和原因。

**这里不放游标。** 游标频繁变化且每个存储、每个使用端各写各的，塞进共享文件就制造了并发热点。

### `state/stores/<store-id>.md` —— 每个记忆存储的状态

**每个存储一份，只记录该存储的采集状态**，所以存储之间无冲突。任何获授权的端或工具都可以读取该存储并写入这份文件，写明实际读取者。内容：类型与位置、对应的使用端、本轮采集记录（读取者与通道、结果、`dump_id`、未完成原因）、最后一次倾倒、未提交的包。

**但同一个存储可能同时被两个会话倾倒**，写的是同一份文件，后写的会盖掉先写的游标。所以这份文件的写回也要走条件写入——只是冲突代价低，重取当前状态、重填自己这一轮的字段即可。

### `state/endpoints/<endpoint-id>.md` —— 每个使用端的状态

**每个使用端一份，只记录它的加载状态**。可由该端或获授权代为操作的执行者写入，并写明实际执行者。内容：使用的记忆存储、本轮读取与发布操作（所用通道、结果、版本、未完成原因）、加载方式、送达、当前会话读取、原生记忆状态、最后读到的统一版本，以及按需检查得到的能力观察。

能力观察是可更新的证据，不是执行资格。某条通道一次失败只记录那次操作的结果，不据此判定该端以后不能执行。同一使用端并发写回同样走条件写入。

两类状态文件中未检查的项都标为“未测”，保留未知状态。

`store-id` 和 `endpoint-id` 都不含模型名——换模型不是换存储或换端，模型名放每次倾倒的元数据里。

### `evidence.md` —— 证据仓

**日常只追加，不改不删。** 正常演化用取代关系表达：旧条目留着，标 `superseded by <编号> · <日期>`。

**但用户明确要求撤回时必须能撤。** 撤回的条目替换成不含敏感原文的墓碑：`E-023 · [已撤回 <日期>] · 主题：<粗粒度主题>`，并在 `review/` 留记录供下次整合拦截。

撤回同时移除统一档案中的当前内容，并在 `evidence.md` 留撤回标记；原始包中的明文需按单独确认的脱敏操作处理。范围见 `consolidate.md` 第七节。

按"支持哪条结论"组织，不按时间流水。每条：编号 · 日期 · 来源 · 内容 · `→ 支持：...`。

来源要具体到端和场景（`Claude Code 会话史 2025-07`、`ChatGPT 基线倾倒 2026-08-09`），因为冲突消解和体检都要用它追责。

体积会涨。定期把已被充分吸收的条目压缩归档，正文留摘要和编号——**编号不回收，链接才不会断**。

### `routing.md` —— 沟通与记忆策略

两张表：沟通路由（场景线索→策略→为什么）、记忆关注策略（信号→归哪层→为什么值得留）。写法见 `consolidate.md` 第四节。

**不承载信息源路由**，那是 `sources.md` 的活。这两件事混在一张表里，"怎么说话"和"去哪查"会互相稀释。

这份文件要控制长度，因为它常驻。判据：如果它长到让用户觉得每次对话都被它拖慢，就该精简了——留高频真实场景，把长尾挪进 `profile.md` 让模型按需读。

### `tests.md` —— 判断题与体检记录

两部分：题库、历次体检记录。出题与记录格式见 `audit.md`。

题目要标明对应 `routing.md` 的哪一条，这样不合格时能直接定位到要改哪行。

**这份文件不进被测身份的上下文，也不随公开技能分发。** 隔离的是身份不是端——同一产品可以在一个会话当主考、另一个会话当被测。
